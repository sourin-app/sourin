# Agent Note: 判据要能分辨"为什么"，也要能分辨"密文"与"长得像密文的明文"

Status: implemented

Independent: 与
[2026-10-19-dns-hijack-needs-authoritative-truth.md](2026-10-19-dns-hijack-needs-authoritative-truth.md)
是**同一条纪律的两个面**：那篇讲「判 DNS 劫持必须拿 DoH 真值对照，
不能只看 `getaddrinfo` 有没抛异常」（= 判据要分清**原因**），
本篇讲「加密门禁要能区分密文与长得像密文的明文」，
以及「门禁全绿 ≠ 用户看到的东西是对的」—— 共享同一个底座：
**判据必须能分辨被测的那个事实，而不是分辨它的表象**。
判别式本身的收归（脱敏掩码 vs markdown 粗体）落在
`test/_support/markdown_bold.dart`，是实现而非决定，不另立笔记。

## Problem

第 66 轮 CS-1（登录态随备份导出/导入）收尾时，**同一个族**的两个教训
在一天里各犯一次。两次的形态不同，但根子是同一句：

> **「门禁全绿」不等于「用户看到的东西是对的」。**

### 教训 ①：判据只到"结论"，到不了"原因"

凭据同步状态行有三档，其中**两档都以「凭据未同步」开头**：

```text
enabled && !passphraseSet ⇒ 「凭据未同步（未设置口令）」
enabled && passphraseSet 但本机无凭据 ⇒ 「凭据未同步（本机暂无登录态）」
```

第一版门禁只断言 `contains('凭据未同步')`。故障注入把 `statusLabel` 改成
忽略 `passphraseSet` ⇒ **19 条门禁全部仍然绿**。

文案并没有撒谎（都说"未同步"），但它**指错了行动** ——
用户看到"暂无登录态"会去查登录，而他该去**设口令**。

### 教训 ②：判据比的是"长得对"，不是"真的加密"

CS-1 的导出判据要求「导出的包内不得出现明文口令字段」。第一版门禁做的是
**逐字节搜明文字符串**（口令、合成令牌、合成密码、合成用户名）。

故障注入把 Rust 侧 `credentials::encrypt_bundle` 换成"假装加密"：

```rust
// 假加密：base64 明文
let _ = password;
Ok(b64_encode(&plain).into_bytes())
```

⇒ **判据全绿**。因为 base64 里当然搜不到 `fixture-token-aaaa` 这个**字面量**，
长度也 > 64，包也确实比不含凭据的包大。

真正的缺陷是：**"包里有密文"不等于"密文是加密的"**。
第一版比的是「导出的东西 == 我期望的样子」，而不是「加密真的发生了」。

### 教训 ③（同一个族的第三个形态，本轮 Lead 看截图发现）

用户可见文案里写了 Markdown 的 `**粗体**`，而渲染它是普通的 `Text` ——
**Flutter 不解析 markdown，星号原样显示**。

CS-1 的 +27 条门禁**全绿**，因为它们断言的是**行为**
（弹框 / 报错 / 不写入任何凭据），**没有一条断言"文案长什么样"**。

★ 这是 §3 缺口 ①「有截图 ≠ 看过截图」的又一次实例：
  门禁证明的是"该弹的弹了、该挡的挡了"，没人证明"屏幕上那句话是对的"。

★ 而且它**一次波及 8 处**（12 个字面量）：知情提示正文、两个口令框、
  面板上的两行操作指引、两条执行日志 ——
  只修 Lead 最初点出的那 2 处，剩下 6 处**照样露馅**。

★ 根因核到底：**本仓几乎没有 markdown 渲染器**
  （`grep -rn "markdown\|Markdown" lib/` ⇒ 5 个文件命中，但**全部只出现在注释里**）
  ⇒ 「凡是要显示给用户的 `**` 都是露馅」是**可判定的**，不是"可能"。

  #   `TextSpan(fontWeight: semibold)`。

  #   我据此断定"只有注释命中 ⇒ 没有渲染器"。

## Decision

### 一、判据必须精确到"原因"，不能只到"结论"

同一句结论若有多条到达路径，**每条路径要有一个只在它身上出现的词**，
并**成对断言**「该在的在」+「不该在的不在」（只断言存在会被无关变化满足）。

实例（`models.dart` 的 `CredentialsStatus.statusLabel`）：

```dart
expect(t.contains('凭据未同步'), isTrue);      // 结论
expect(t.contains('口令'), isTrue);            // 原因 ★
expect(t.contains('暂无登录态'), isFalse);      // 成对：不该在的不在 ★
```

★ 夹具必须让两档的**其它数字也一样**（`providers=4`），否则区分不出来。

### 二、加密类门禁必须能分辨「密文」与「长得像密文的明文」

不能停在"搜不到明文字面量"这一层。判据必须**解开它再看**：

```text
① 把密文段（如 `_v1`）当 base64 解开 ⇒ 解开后**不能**是能直接读的 JSON
   （是 ⇒ 它根本没加密，只是被 base64 包了一层）
② 解开后不许出现任何明文秘密
③ ★ 两次导出同一份数据 ⇒ 密文**必须不同**
   （真加密有随机 salt/nonce；base64 明文两次必然一模一样）
   —— 第 ③ 条最便宜，且**不需要**解包就能判
```

### 三、"界面出现某句话"必须读**渲染结果**，不许 grep 源码

- 判据要打在 **element 树 / 像素**上，不是源码字符串上。
- **不许把产品的对话框复制一份到测试里** —— 那是「门禁与实现漂开」，
  产品改了文案、测试里的副本没跟上，门禁照样绿。
- 若要断言"这段文字长什么样"，就渲染**真面板**，
  把树上**所有** `Text` 的内容读出来，断言**整棵树**不含坏字符 ——
  只断言那两条常量的话，改了一处漏了另一处也会绿（**假绿**）。

### 四、文案类缺陷的判据要「整棵子树」+「防空转自检」

```text
① 范围：断言**整棵树**所有可见 Text，不许只断言被点名的那几条常量
   —— 否则「改一处漏一处」会假绿（本轮真实发生：8 处，只改 2 处仍露馅）
② ★ 防空转：先断言树**非空**且含**已知文案**
   —— 本会话已出三次恒真判据；「不含 `**`」在空树上**也为真**
   ⇒ 没有这条自检，门禁退化成空转时**没有任何症状**
③ 静态兜底：源码字符串字面量里也不许有坏字符
   —— 覆盖「运行时才拼出来」的那条路（知情提示正文就是 `StringBuffer` 拼的）
```

### 五、强调用**中文引号「」**，不写 markdown、不上 `Text.rich`

`lib/shell.dart:6955` 已有**同族先例**并写明了理由：

```text
⚠️ 不要在这里写 Markdown 的 `**粗体**` —— 这是 `Text` 不是
   Markdown 渲染器，星号会**原样显示**出来（我第一版就写错了，
   截图里能看到字面的 `**已存在的文件**`）。
   要强调就用中文引号「」，视觉上同样醒目且不会露馅。
```

⇒ 新增/修改用户可见文案时，**照这条办**。

## Alternatives considered

- **"搜不到明文字面量"就够了**（只做 lesson ② 的第一版）——
  它的最强论据是"够用了，假加密不是现实威胁"。
  否决理由：本次故障注入**已经证明**它会全绿；而且"假加密"正是
  未来某次改算法/换库时最容易犯的错（为了省事把 `encrypt` 换成 `base64`）。
  ⇒ 判据必须能在**那种改动**发生时变红，否则它测不到它要防的东西。

- **给全仓加一个 markdown 渲染器**，让 `**粗体**` 真的变粗 ——
  它的最强论据是"一次修好，以后写 markdown 都能用"。
  否决理由：`Text.rich` 只能处理**有限几种**强调（粗/斜），
  而真正的 markdown 还有列表、代码块、链接 —— 半吊子渲染器比星号更坑。
  ⇒ 走本仓**既有先例**（`lib/shell.dart:6955` 的注释）：
    **要强调就用中文引号「」**，视觉上同样醒目，且绝不会露馅。

- **只改 Lead 点名的那 2 处**（`请输入**导出这个包时**` 与
  `口令不对时**整次导入会失败**`）——
  它的最强论据是"范围小、风险低、照指令办事"。
  否决理由：同一处 `**` 在这个文件里有 **12 个字面量 / 8 个位置**，
  改完那 2 处之后，**CS-1 最重要的那段知情提示**（"这个备份文件会
  **含登录态**"、"泄露的是**密码**"）**照样露馅** ——
  那比不改更糟（用户看到的是"半修好了"）。
  ⇒ ★ 判据：**改"用户可见文案缺陷"时，范围要按"同一渲染路径下会露出同样问题的全部位置"划，
    而不是按"谁先点出来的"划。**

- **在源码层加一条"不许出现 `**`"的静态断言**（grep 文件）——
  它的最强论据是"便宜、且能覆盖全文件"。
  否决理由：它拦不住**运行时拼出来的**带星号文案
  （本次的知情提示正文就是 `StringBuffer ..writeln(...)` 拼的），
  也会误伤注释与文档字符串。
  ⇒ 判据要读**渲染结果**；静态断言只能作为补充。

## Consequences

- **收益**：CS-1 这批门禁现在能抓住三类"看起来对"的问题：
  结论对但原因错、密文是假的、文案露馅。
- **代价**：门禁比第一版重（要解 base64、要渲染面板读整棵树）。
  且**多了一条纪律** —— 任何新增的用户可见文案，都要问"这句在屏幕上长什么样"。
- **产品侧的连带改动**：本条落地时改了 `lib/ui/widgets/backup_panel.dart`
  **8 处 12 个字面量**（`**粗体**` → `「粗体」`）。
  ⇒ 两条既有门禁的断言**随之过时**（它们断言的是旧字面量），
  按本仓规矩**改断言为新行为**，并**加一条阴性断言**
  （不许再出现旧写法）—— 使新断言在旧行为下必须红。
- **已知上限**：本条只覆盖 `Text` 系控件。
  ⚠️ 而"没有渲染器"这个前提**不是恒真的** —— 本仓**已经有**一个
  （`lib/ui/widgets/release_notes.dart`，只用于「发行说明」）。
  ⇒ 若将来把 markdown 渲染能力**推广到别的界面**，
  本条的断言要**改成"渲染后不含星号"**（而不是"源码里不含 `**`"），否则会假红。
  ★ 本条的静态判据（逐条字面量查）本身**不受**影响 ——
    它查的是"源码字面量里有没有 markdown 粗体"，
    而渲染器存在与否只影响**渲染后**长什么样。
- **重访条件**：markdown 渲染能力**推广到本条覆盖的界面**时，按上一条改判据；
  或出现第四例"门禁全绿但用户看到的东西不对"时，并进本条。
