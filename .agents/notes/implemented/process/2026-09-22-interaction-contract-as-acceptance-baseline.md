# Agent Note: 交互契约是验收基准，有意差异必须先问 Owner

Status: implemented

## Problem

重写期间 UI 可以优化，但**操作逻辑不能自己发明**。Owner 的要求是
「操作逻辑都还要原来的保持一样的」。

难点在于：什么算「优化」、什么算「改了操作逻辑」，边界靠记忆判断不住 ——
重写时每个页面都要重新决定一次，没有基准就会各自漂移。

## Decision

`PLAYER-CONTRACT.md` 与 `INTERACTION-CONTRACT.md` 逐条从原版源码提取，带源码行号，
作为验收基准。与基准的有意差异必须先问 Owner。

Independent: 验收基准的定义（交互契约）。它本身是流程基石，没有更上位的既有流程决定。

## Alternatives considered

- **以新版实现为准，边做边定** —— 它最强的论据是迭代快、不被旧实现束缚。
  否决理由：那等于让重写过程自己发明操作逻辑；同一功能在两处实现里会给出不同行为，
  用户迁移过来时体验断裂，且事后无法判断哪一版才是「对的」。

- **只凭记忆和截图复刻** —— 它最强的论据是成本低。否决理由：截图说不出时序、
  焦点与失败路径；没有源码行号锚点，争议时无法回溯到具体实现。

## Consequences

- **收益**：每条操作逻辑有可回溯的出处（源码行号），差异能被明确指认而不是各说各话。
- **代价与已知上限**：契约是迁移期的产物，迁移结束后它会与当前产品行为脱节 ——
  那时继续拿它当基准反而会挡住合理的演进。
- **重访条件**：迁移期结束（Flutter 版成为唯一实现）后，这两份文档降级为历史参考，
  以**当前产品行为**为准并重写契约。
