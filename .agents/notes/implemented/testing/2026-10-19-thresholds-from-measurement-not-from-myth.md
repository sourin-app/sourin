# Agent Note: 阈值按实测下调，而「改前对照」可能根本不可考

Status: implemented

Independent: 与本轮其它笔记都不同 —— 那几篇分别讲
[恒绿断言的四种形态](../testing/2026-10-19-four-shapes-of-always-green-assertions.md)、
[门禁红了该改谁](../testing/2026-10-19-when-a-gate-goes-red-after-your-fix.md)、
[断言钉机制](../testing/2026-10-19-assertions-pin-mechanism-not-implementation.md)。
那几篇讲**判据该不该存在 / 该怎么写**；本篇讲**阈值该定多少**，
以及一个更根本的问题：**你手里那个「改前读数」可能压根不可考。**

## Problem

`zz_t66_player_jank_test` 有 3 条红，队友建议「阈值紧了，调宽即可」。
我实测三次发现**三条各有不同成因**，其中两条该调、一条不该：

```text
T1 隐藏→hover 叫回   all=4    阈值 ≤3   ← 阈值低估
T2 隐藏光标          all=531  阈值 <400  ← 不是阈值问题（见下）
P0 仪器自检          all=1    阈值 =0   ← 仪器共性噪声
```

## Decision

### ① T2「隐藏光标 531」：不是回归，是**被 t118 钉住的既定设计**

```text
复核逐段拆开：531 = 527 + 4
  527 = `_autoHideNow()` 里那行 setState(() => _controlsVisible = false);
        ★ 它被 t118_control_bars_link_test.dart:819/833 **逐字钉住**
          （还要求它必须出现在 _applyControlsMotion() 之前）
        ⇒ 删了 t118 会红 ⇒ 不是本轮引入，也不该在此放宽
    4 = `_hideCursorNow` 的局部广播（N11 的成果，2 种 widget）
```

**我第一反应错了**：我以为「改前 190 → 改后 531」是 2.8 倍劣化，
差点建议按队友说的放宽阈值。核实后才知道 **527 那行是被测试钉住的**。

⇒ 阈值 `< 400` → `< 700`，并把注释里的 `190/193` 换成实测 `527/531`
**且写明 527 的出处**。

### ② ★★ 「改前 190」这个对照**根本不可考** —— 这才是根子

```text
硬证据三条：
 ① 引入本测试的 commit `e6458e5` **只加测试**（569 行，**零 lib 改动**）
    ⇒ 测试诞生时 lib 已经是 N11 之后的状态
 ② N11 的产品代码在它的父 commit `aedc29c`
 ③ 基线 worktree `bdf6435`（10-18 08:04）既没有这个测试文件，
    也没有 `_cursorLive` ⇒ **复现不出 190**
```

⇒ 「190」是「同一天、但**不在任何 commit 里**的中间态」读数。
它无法被复跑取证 ⇒ **不能当对照基线**。

★ 与[那篇笔记](2026-10-19-assertions-pin-mechanism-not-implementation.md)
  里我更正过的「23 条」是同一个病：
  **数字对上了 ≠ 口径对上了**。

### ③ T1 / P0：按实测下调，并**保留**断言

```text
T1 阈值 3 → 5：实测五次连跑 all=4 逐字一致；
  原注释写「理论下限 2 + 多留 1」⇒ 那条估算少算了 2
  放宽到 5 仍安全：改前 188 是**两个数量级**
P0 阈值 0 → ≤1：实测静置一帧恒为 all=1；
  ★ 决定性对照：`test/t72_jank_test.dart`（**轮前就存在的基线文件**）
    它的 P0 读数**同样是 all=1**，且它**同样是红的**
    ⇒ 两个不同文件、同一套仪器、同一读数 ⇒ **仪器共性噪声**
  ★ 没删掉这条断言 —— 它是下面「阳性对照 ≥1」的前置，
    删了整条 P0，阳性对照就没有「仪器有区分力」的证明。
```

## Alternatives considered

**A. 直接把阈值调到实测值上方，不改注释。**
最强理由：改动最小，门禁立刻绿。
否决理由：**注释里那个「190」还在**，下一个人会以为
「531 是劣化」并去改产品 —— 而那 527 是 t118 钉住的，
改产品会让 t118 变红，然后陷入「改产品还是改测试」的死循环。
★ 阈值与它的**出处**必须一起改。

**B. 把 T2 也放宽到 600（队友方案①）。**
最强理由：一次改完。
否决理由：**放宽阈值不是"处理"一个已知成因**。
527 的成因已经查清（被 t118 钉住的整页 setState），
把它写进注释，比把数字调大更有价值 —— 后者只让门禁闭嘴。

**C. 删掉 P0 那条断言（它在本机永远红）。**
最强理由：它本来就是自检，红着没用。
否决理由：它是**阳性对照**的前置。删了之后
「openHints 必须 ≥1」就没有「仪器有区分力」的证明了。

## Consequences

**结果**：`+7 All tests passed!`（三条红全绿）

**★ 一次失败的注入，如实记**

```text
我给 `_pushCursorLive` 加了 setState 想验证「阈值放宽后仍能抓回归」，
结果读数**完全不变**（T1 仍 4、T2 仍 5）。
```

原因：`ValueListenableBuilder` 订阅的值变化**本身就是**局部重建；
在那条路径上加 `setState` 不会额外产生重建计数。
⇒ **这个注入测不出东西** ⇒ 我没有据此宣称「阈值放宽后仍有判别力」。

★ 期间还踩了一次错锚点：`setState(() {})` 在该文件里**已有 6 处**，
我的 `replace(..., 1)` 改到的是别的地方。
判据：注入前先 `assert s.count(anchor) == 1`（我第二次做了，第一次没做）。

**★ 因此如实标注：T1/T2 的阈值放宽后，我**没有**找到能证明
「它仍能抓住真实回归」的注入手段。**
现有保障只有「改前 188 是两个数量级」这个静态推理。

**★ 后续：找到了能红的注入（复核 + 我独立复现）**

```text
我原先那个注入（给 _pushCursorLive 加 setState）选错了点：
  那条路径的值变化**本身就是**局部重建，多加的 setState 被覆盖 ⇒ 读数不变。
★ 「读数不变」不等于「阈值失效」，只等于「这个注入点在该窗口不产生额外计数」。

复核找到 4 个有效注入，其中最有说服力的是**注入 C**（我已独立复现）：
  把 `_resetCursorIdle` 里的 `_cursorIdleStale = false;`
  退回 `setState(() => _cursorIdleStale = false);`
  实测：T2 恢复段 all 5 → **527**、pageBuild 0 → **1** ⇒ 门禁红 ✔
  ⇒ **放宽后的阈值确实仍能抓住真实回归。**

另有「注入 D」更能说明阈值 5 的价值：多推一次 `_controlsLive.notifyListeners()`
  ⇒ all 4 → **73**、pageBuild 仍 0（整页没重建）⇒ **阈值 5 照样抓住**。
```

⇒ 上面「判别力未经注入验证」那条**已关闭**。
