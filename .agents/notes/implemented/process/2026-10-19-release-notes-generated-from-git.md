# Agent Note: 更新说明从 git 历史生成，缺说明时 CI 直接红

Status: implemented

Independent: 本篇讲的是**发版链路**（release body 从哪来、缺了怎么拦住），
与既有三篇都不同 —— [../bug-fix/2026-10-19-hijack-verdict-only-wired-to-one-path.md](../bug-fix/2026-10-19-hijack-verdict-only-wired-to-one-path.md)
讲弹幕探测的归因接线；[../testing/2026-10-19-criteria-must-distinguish-cause-and-ciphertext.md](../testing/2026-10-19-criteria-must-distinguish-cause-and-ciphertext.md)
讲判据要分清「原因」与「密文」；[../bug-fix/2026-10-19-r5-evidence-was-a-transition-frame.md](../bug-fix/2026-10-19-r5-evidence-was-a-transition-frame.md)
讲 R5 证据是一张过渡帧。三篇都不涉及发版流程。

## Problem

Owner 2026-10-19 反馈：「最近发的几个版本都没有更新说明，全都是默认的」。

取证（不是猜）：

```text
① .github/release-notes.md 原先是**静态模板**，172 行里没有一节是"这一版改了什么"。
② 线上 v1.3.0 的 release body 实测 2974 字符 —— 内容是
   **下载表格 + 安装说明 + 平台注意事项**，没有任何版本差异信息。
   ⇒ 用户看到的"更新说明"等于没有。
③ 模板 `## 关于本版本` 那段写的是「**首个公开版本**」，
   从 v1.0 到 v1.3 一直是同一句话。
```

⇒ 根因不是「忘了写」，而是**流程里根本没有"写"这一步**：
`build.yml` 每次发布都 `sed` 同一份模板上传，模板里没有位置放版本差异，
也就没有任何环节会因为"这一版没写说明"而失败。

## Decision

三件事一起改，缺一件这个缺陷都会回来：

1. **模板加一节 `## 本版更新`**，内容由占位符 `{{CHANGELOG}}` 承载。
2. **`tools/gen_release_notes.py` 从 git 提交归纳**：
   上一个 tag 到本 tag 之间的提交 → 按前缀分类（`修：`/`优化：`/`feat:`…）
   → **剔除开发用语与残句** → 注入占位符。
3. **CI 在"说明为空"时报错退出**（`build.yml` 的 `建 Release` 步骤）：
   - 生成器归纳为空 ⇒ 脚本 `exit 1`（除非显式 `--allow-empty`，仅首个 release 用）；
   - 产物里仍残留 `{{CHANGELOG}}` ⇒ CI `::error::` + `exit 1`。

### 三条硬约束（都有实测依据）

```text
① 占位符用 `{{CHANGELOG}}`，**不用**下划线包夹形态（如 __CHANGELOG__）。
   原因：那与 `__VERSION__` 同族，CI 里 `sed "s/__VERSION__/…/g"` 会把它
   一并当替换项。第一版就踩了：注释里的占位符被替换成整段更新说明，
   注释结构被撑坏（实测注释块里塞进了 29 行 changelog）。

② 生成器**只读模板、写独立输出**，绝不回写模板。
   第一版是就地改写 `release-notes.md` ⇒ 模板被某一版的更新说明污染，
   下一版会拿**上一版的陈旧内容**当模板，而且没人会注意到。

③ 必须清洗**开发用语**。实测 v1.2.0..v1.3.0 归纳出的 29 行里有 **14 处**
   命中：`CR #29`、`t1015`、`门禁`、`探针`、`假绿`、`bili`…
   ⇒ 这些不许出现在用户能读到的文案里（AGENTS §4 铁律）。
   清洗后从 29 行降到 19 行；再滤掉「删掉编号后读不通」的残句（如
   「在 macOS 上跑不动」——原本主语是 `t1015`）后降到 **17 行**。
```

## Alternatives considered

**A. 每次发布让人手写更新说明。**
最强理由：手写能写清"用户能感知到什么"，而 git 提交标题是给开发看的。
否决理由：**这正是当前失败的原因** —— 流程里没有强制点，靠自觉的步骤在
连续 4 个版本里一次都没被执行。而且它无法机械检查"写没写"。
本方案不是因为它更好，而是因为它**有强制点**：归纳为空 ⇒ CI 红。

**B. 在 CI 里调 GitHub API 拿上一个 release 的 body 做 diff。**
最强理由：不依赖仓库内的提交历史规范。
否决理由：本机实测 **API 长期被限流**
（`API rate limit exceeded for 67.159.48.147`），
且给 CI 增加一次网络依赖只为读一份自己刚发的文本，不划算。

**C. 引入 conventional-commits 规范 + 生成工具（如 git-cliff / semantic-release）。**
最强理由：成熟工具、格式统一、可配置模板。
否决理由：本仓提交信息**已经是**分类中文（`修：`/`测试：`/`优化：`/`开发：`），
规范事实上已存在，只差一步归纳；为这一步引一个外部依赖 + 新配置文件，
比 261 行脚本更重，且工具默认输出面向开发者（英文分类、含 scope），
仍需二次清洗才能给用户看。

**D. 只改模板（把「首个公开版本」换成占位），不做生成器。**
最强理由：改动最小，一次性解决"永远说首个公开版本"。
否决理由：占位符没人填 ⇒ 发出去的会是 `{{CHANGELOG}}` 字面量或空白。
**没有强制点的方案不算修好**，本缺陷的本质就是缺强制点。

## Consequences

**收益**

```text
· 每个 release 的「本版更新」自动来自真实提交，不再需要人记得写。
· 归纳为空 ⇒ CI 红 ⇒ 从结构上防止再发一版没有说明的 release
  （这条是本轮唯一的"强制点"，也是整个改动的核心价值）。
· 清洗规则让用户可见文案不含 `CR #29` / `t1015` / `门禁` / 站点名。
```

## 批末复查发现并修掉的六个缺陷（同一轮内，都是实测出来的）

初版上线前由独立复核（`release-verify`）逐条实测，查出六处会**再次产生"没有更新说明"**的缺陷。
全部已修，逐条记录如下（含修法判据）：

```text
① ★★★ CI 的 checkout 无 fetch-depth ⇒ 浅克隆无 tag ⇒ describe 必失败
   ⇒ 被误判成"首个 release" ⇒ 要么 exit 2 发不出去、要么输出
     「本版无用户可见变更」照常发布 —— Owner 的抱怨原样复现。
   修法：checkout 加 `fetch-depth: 0`；且**不再用 `describe || true`**，
        改用 `git tag --sort=-v:refname | grep -v "^$TAG$" | head -1`，
        让"真的是首个"与"拿不到历史"在代码里可区分。

② ★★ 模板里 `{{CHANGELOG}}` 出现 2 次（注释里写了一份说明 + 真占位）
   ⇒ 全局 replace ⇒ 更新说明被**同时注入注释** ⇒ 正文翻倍；
     且提交标题含 HTML 注释结束符时注释提前闭合，副本泄漏成用户可见正文
     （实测：标题写 `A --> B` 就把注释截断）。
   修法：注释里不再写那个占位标记本身（改用文字描述"双花括号包住 CHANGELOG"）。
   现在模板里占位符 **恰好 1 处**。

②b ★★★ **注释自己踩了同一个坑**（修 ② 时新引入，当场抓到）
   ```text
   我在注释里解释「若标题含注释结束符会截断注释」时，
   把那个结束符**原样写了进去** ⇒ 注释在那一行提前闭合
   ⇒ 之后的说明全变成用户可见正文（含 `**` 标记）。
   实测：模板 `<!--` = 1 但 `-->` = 2 ⇒ 不平衡，一读就知道。
   ⇒ 判据：**注释里永远不要写出注释结束符本身**，用文字描述它。
   ```
   ★ 这是一个**自指陷阱**：为了说明某个符号会破坏结构，而使用了那个符号。

③ ★★ 「新增」一节**在任何区间都从未出现**
   `USER_FACING` 只有英文 `feat`，没有中文 `新增`/`功能`
   ⇒ 本仓以中文前缀为主 ⇒ 头条新功能被静默丢弃。
   修法：补 `新增`/`功能`/`改进`/`调整`/`回退`。

④ ★ 整条丢弃词**误伤 11 条真修复**
   如「修复：片头自动跳过可能整段漏跳 + 行为门禁」只因尾巴有"门禁"就整条消失。
   修法：开发用语改为**从正文删掉**（而非整条丢），只有站点名仍整条丢
        （删掉站点名会指代不明）。

⑤ ★ 残句规则误杀合法句
   `_ORPHAN_PREFIXES` 里是 `"在 "`（带空格）⇒ 中文无词间空格 ⇒
   「在 macOS 上不再崩溃」被误杀，而「在播放页…」能过。
   修法：只在「词 + ASCII」**且中文部分 < 6 字**时才判残句
        （「在 macOS 上跑不动」7 字 ⇒ 丢；「在 macOS 上不再崩溃」11 字 ⇒ 留）。

⑥ ★ scope 剥离漏网
   `fix(player): xxx` 的 `(` 被前缀匹配吃掉 ⇒ 正文从 `player): xxx` 开始 ⇒
   英文 scope 残渣出现在用户可见文案里。
   修法：两种形态都剥（`(scope)` 与裸 `scope)`）。

★ 另修：`classify` 返回 None 时**打一行 stderr** ——
  原来 43/156 条被静默丢弃，写「功能：」的人不会知道它进了黑洞。
```

**★ 新增第三条守卫（这才是 Owner 真正要的判据）**

```text
原有两个守卫实测**都不可达**：
  · `__VERSION__` 残留：sed 全局替换 ⇒ 恒 0 ⇒ 永不触发
  · `{{CHANGELOG}}` 残留：生成成功则恒 0；生成失败则 bash -e 已中止 ⇒ 不可达
⇒ 而「### 本版无用户可见变更」能通过全部守卫**照常发布**。

⇒ 加：**说明里必须至少有一条 bullet**（首个 release 除外）。
  故障注入：无 bullet ⇒ exit 1；有 bullet ⇒ 放行（不误报）。

### ★★★ 这条守卫我第一版写错了（复核抓出，Lead 修）

```text
第一版：grep -qE '^\s*-\s+\S' "$NOTES"
★ 作用域是**整份文件**，而模板的「## 功能」小节**自带 30 条** bullet
  ⇒ 空说明 + 30 条模板 bullet ⇒ **恒 PASS，永不触发**

实测（「本版更新」节内 0 条，全文件 30 条）：
  改前判定 ⇒ PASS（本该 FIRED）
  改后判定 ⇒ FIRED  ✅
```

⇒ 修法：把作用域收进那一节

```bash
CHANGELOG_SECTION=$(sed -n '/^## 本版更新/,/^---$/p' "$NOTES")
printf '%s\n' "$CHANGELOG_SECTION" | grep -qE '^\s*-\s+\S'
```

★ **教训**：一条守卫的作用域必须与它要守的对象**同范围**。
  全文件级判据在「模板本身有内容」时恒真。

### ★★★ 「回退/调整」分类被静默丢弃（复核抓出，Lead 修）

```text
上一轮我给 USER_FACING 加了 ("回退","调整") 与 ("调整","调整")，
但 build_changelog 的 order = ["新增","改进","修复"] **没有「调整」**
⇒ classify 正确分类进「调整」桶 ⇒ 渲染层没有桶名能命中 ⇒ 整桶丢弃

实测：build_changelog(['回退：切 tab 的离场页快照…'])
  改前 => '\n'        ← 一个换行符，而换行符是 truthy
  ⇒ 连 `if not changelog` 的兜底都不触发
  ⇒ 端到端产物是**一个只有标题、一个字都没有的空节**
改后 => '### 调整\n\n- 切 tab 的离场页快照（…）\n'
```

★ 这是「静默丢弃」**换了个位置**：上一版在 `classify` 丢，
  这一版在 `build_changelog` 丢。**分类对了不等于输出里有。**

修法两条：

```text
① order 补上「调整」
② ★★ 加自检：USER_FACING 的每个桶名必须出现在 order 里，
   否则直接 raise AssertionError。
   ⚠️ 自检必须在**函数入口**，不能在 `if not buckets: return ""` 之后 ——
   我第一版放在后面，注入坏 order 后自检「没触发」，
   差点让我以为它恒真。判据：**守卫代码在任何 early return 之前**。
   注入验证：order 去掉「调整」⇒ AssertionError；还原 ⇒ 通过
```

### ★★★ `PREV` 取错：重跑旧 tag 会红（复核抓出，Lead 修）

我第一版为了避开 `describe || true` 吞错误，改成：

```bash
ALL_TAGS=$(git tag --sort=-v:refname | grep -v "^${TAG}$" || true)
PREV=$(echo "$ALL_TAGS" | head -1)
```

★ 这取的是「**最新的**其它 tag」，不是「本 tag 的历史前驱」。

实测（本地 4 个 tag）：

```text
TAG=v1.0.0 ⇒ PREV=v1.3.0   区间 [v1.3.0..v1.0.0] 反向
TAG=v1.2.0 ⇒ PREV=v1.3.0   区间 [v1.3.0..v1.2.0] 反向
TAG=v1.3.0 ⇒ PREV=v1.2.0   ← 只有最大 tag 才碰巧对
⇒ 重跑任何旧 tag 都会让生成器 exit 1
```

★ **最讽刺的地方**：`build.yml:1560` 那段注释明写
  「修好 CI 之后必须重跑同一个 tag 才能补齐」——
  而我的写法**恰好把那条补救路径堵死**。

同样会坏的是 rc：`sort -V` 把 `v1.4.0-rc1` 排在 `v1.4.0` **之前**
⇒ rc 会把自己选成前驱 ⇒ rc 发布必红。

修法（回到 `git describe`，但**保留**它与「真首个」的区分）：

```bash
if git rev-parse -q --verify "refs/tags/$TAG" >/dev/null 2>&1; then
  ANCHOR="$TAG";  DESCRIBE_FROM="${TAG}^"
else
  ANCHOR="HEAD";  DESCRIBE_FROM="HEAD"      # ← 2026-10-21 补的：tag 还不存在
fi
PREV=$(git describe --tags --abbrev=0 "$DESCRIBE_FROM" 2>/dev/null || true)
```

实测四个 tag 全部正确，且 `v1.4.0-rc1` **不会选自己**。

**为什么 describe 起点不能像 `--to` 那样直接用 `$TAG`**：
`git describe` 对一个**已经被打上 tag 的提交**会返回**它自己**
⇒ 区间 `$TAG..$TAG` 为空 ⇒ 生成器 exit 1。原来写 `$TAG^`（父提交）正是为这个。

### 2026-10-21 补：`$TAG` 在 publish job 跑的时候**还不存在**

上面那段的 `"${TAG}^"` 有一个前提：**本地已经有这个 tag**。
而本 flow 的设计恰好相反 —— `docs/RUNBOOK.md` §1 写的是
「填了 `release_tag` ⇒ 构建完**自动建** Release 并上传」，
tag 是最后那步 `gh release create "$TAG" --target "${{ github.sha }}"` **才创建**的。

⇒ 全新 tag 必红，实测（run `39546013679`，三个平台全绿，只死在 publish job，9 秒）：

```text
##[warning]历史里没有更早的 tag ⇒ 按首个 release 处理，更新说明留空
[gen_release_notes] 命令失败: git log --no-merges --pretty=%s v1.4.0-rc3..v1.4.0-rc3
fatal: ambiguous argument 'v1.4.0-rc3..v1.4.0-rc3': unknown revision or path not in the working tree.
##[error]Process completed with exit code 2.
```

注意它**先掉进了"首个 release"分支**：`"${TAG}^"` 解析不了 ⇒ describe 失败 ⇒
`PREV` 为空。而那条分支的 `--from "$TAG" --to "$TAG" --allow-empty`
**同样要求 `$TAG` 能被解析** ⇒ 连"留空"也走不通。
「describe 失败」在这里同时覆盖了「真首个」与「tag 还没建」两种状态，
和本篇前面批评过的「`|| true` 把失败吞成首个 release」是同一个病，只是换了个入口。

⇒ 用 **ANCHOR** 把两者分开：
tag 在 ⇒ `ANCHOR=$TAG`（重跑旧 tag 的语义**一个字没变**）；
tag 不在 ⇒ `ANCHOR=HEAD`（= `github.sha` = 一会儿要被 `--target` 打上 tag 的那个提交）。
`--from` / `--to` / describe 起点全部跟着 ANCHOR 走。

⚠️ 这是个**好失败**（红得响、不产出错内容）：它不会发一个说明空白的 Release，
只是发不出去。所以它的优先级低于「静默降级」类缺陷 ——
但 RUNBOOK 承诺的「填了 tag 就自动发」必须真的能自动发，否则承诺是假的。


★ **教训**：我为了修 A（失败被误判）而引入 B（取错前驱）。
  ⇒ 改判据前先问「原来的写法到底错在哪一行」，
  而不是「怎么绕开它看起来错的地方」。

### ★★★ Owner 指出第二半：「关于本版本」也是默认文案

```text
Owner 原话：「更新说明全都是默认的」⇒ 我第一轮只修了「没有内容」那一半。
另一半是 `## 关于本版本` 那段 —— 它从 v1.0 到 v1.3 **一字未变**。

★ 更严重的是里面写死的数字（队友 `git log -S` 定位到出处 2114efe，
  2026-10-08 建 CI 时手填）：
    「全量 Dart 测试 **2243 通过 / 47 跳过 / 0 失败**」
    ├ 11 天、约 50 个 commit 一次没更新（实测已 4600+，规模翻倍）
    └ ★★ 「0 失败」是**向用户作出的不实陈述**：实测 -37
```

⇒ 改法（Owner 确认「一起改」后动手）：

```text
① 「首个公开版本」⇒ 换成与版本无关的准确表述
② ★ 删掉 2243 / 47 / 0 失败 —— 改成「全部自动化测试通过」
   理由：写死数字必然腐烂，而腐烂后还在**承诺**一个已不成立的事实。
   「通过」这种不变量不需要每次发布更新。
③ 删掉我们的内部细节：`flutter analyze` / `Rust 单元测试` / `nm` /
   `aapt` / 「导出符号 ≥ 7」
   ★ 原则：**保留承诺，删掉手段**。
     nm 数符号 → 用户语言是「核心库确实打进了应用包内」
     aapt 双入口 → 用户语言是「同一个 APK 手机电视都能用」（这还是选型信息）
④ 保留「三个平台装的是同一份代码」—— 全段唯一不可替代的信息，
   竞品通常不说，而用户真的关心
```

★ **否决了队友建议的 CI 守卫**（grep 测试条数并 `exit 1`）：

```text
理由① 那段**不随版本变**（不是「本版更新」那种每版都填的内容），
      所以它需要的不是「生成器 + 强制点」，而是「别写会腐烂的常量」——
      而这已经靠「删数字」从结构上解决了。
理由② build.yml 已有 40 处 `exit 1`。为一段静态文案再加一条，
      是拿**流程复杂度**换一个人人看得懂的编辑纪律。
理由③ 它自己就有个洞：`grep -E '测试 *[0-9]{3,}'` 会命中
      「本次测试 42 项」这类将来合理的写法 ⇒ 守卫会变噪音，
      而噪音守卫的结局是被加 `--invert` 或注释掉。
⇒ 判据：守卫要拦的是**结构上会复发**的东西，不是**一次性能删干净**的东西。
```

### ★★★ 批末复核第二轮：清洗层两个根因（比原登记严重得多）

我登记为「前缀贪婪」的那条，复核实测发现**是两个缺陷叠加**：

```text
① scope 剥离吃掉了 `round-66)` 却**留下 `: R3-④ …`**
   ⇒ 冒号还在 ⇒ 判残句 ⇒ 整条丢
   量化：最后 120 条提交里 classify()==None 的 **92 条（77%）**
② 同一根因的**另一方向**：另有 18 条带 `round-66/xxx): ` 的**残渣
   漏进用户可见正文**
   ⇒ 同一根因同时造成「丢好的」与「漏坏的」
```

修法：scope 后面的分隔符（`:` / `：` / 空白）**一起吃掉**。
★ 第二轮又发现仍吃不掉 `round-66 任务B-2): xxx`
（scope 里有空格且非 ASCII 开头）⇒ 补第三条：
`^[^\n]{0,40}?\)\s*[:：]?\s*`（`)` 是强锚点，正文不会随便出现孤立的 `)`）。

### ★★★ 「有没有动词」这个判据被**换掉**了

```text
原判据 _has_meaningful_verb：查动词词表 ⇒ **两头都错**
  该拦的没拦：'苹果小' → True、'天气多' → True、'abc大' → True
             （词表混进了「小/大/多/少/白/黑/花」这类**单字**）
  该留的丢了：'透传守卫' → False、'CS-1 凭据平面' → False
```

⇒ 换成 `_is_readable_enough`：**长度 + 可读性**，不查词表。

```text
为什么换而不是补词表：「有没有动词」本质需要分词，
而本脚本不引依赖 ⇒ 词表必然两头错。

新判据：中文 ≥ 4 字 且 含 ≥2 字的中文连续块
  9 例回归全对：
    保留：透传守卫 / CS-1 凭据平面 / 这是一句没有动词的胡话 / 缓存持久化到磁盘
    丢弃：苹果小 / 天气多 / abc大 / 弹幕 / 设置页
    （原判据把前三个放行、后两个拦掉 —— 正好全反）
```

★ 刻意保留的代价：它会留下一句**语义上无意义**的话。
  这是**选择**：宁可多留一句，也不误删一条真修复。
  ⇒ 与本轮早先那条「宁可丢多了」**方向相反**，两次取舍的理由不同：
     这一次是实测发现「丢多了」的代价更大。

**修完的端到端效果**

```text
区间              改前 bullets  改后 bullets  残渣
v1.0.0..v1.1.0        19           27          0
v1.1.0..v1.2.0        18           25          0
v1.2.0..v1.3.0        15           19          0
v1.3.0..HEAD          —            81          1（内部类名，属另一类问题）
```

**代价 / 已知上限（如实记）**

```text
· 提交标题的质量直接决定更新说明的质量。标题写得含糊（如「修：一堆问题」）
  就会原样出现在用户面前 —— 脚本无法判断"这句话对用户有没有意义"。
· 只认**中文前缀 + 少数英文前缀**；不符合的会被丢弃（现在至少会打一行 stderr）。
· 残句过滤是**启发式**（按"词 + ASCII + 中文字数"判断），可能仍有误删/误留。
  当前口径是"宁可多留一句读得通的，也不要丢掉用户真正关心的修复"。
· 不做语义合并：同一功能的多条提交会并列出现，不会归纳成一句话。
· rc → 正式版的区间会被 rc 截断（`describe` 返回 rc 而非上一个正式版）
  ⇒ 走 rc 流程时正式版说明会残缺。**未修**，需改用"上一个正式版 tag"。
· `sed "s/__VERSION__/$VER/g"` 会**静默改写提交标题**里恰好含 `__VERSION__` 的字样。
  **未修**，属低概率但会让用户看到错误内容。
```

**何时该翻案**

```text
· 若将来更新说明需要按"用户能感知的变化"重写（而不是照搬提交标题），
  本方案应降级为"给写的人一份草稿"，强制点改成"发布前必须有一份人工确认的说明"。
· 若提交信息规范实际没有被遵守（大量提交无前缀而被丢弃），
  说明本方案的前提失效 ⇒ 应先修提交规范，而不是放宽清洗。
· 若引入 git-cliff 之类的工具，需确认它的输出同样能过
  「不含开发用语 / 站点名」这条门禁，否则仍要保留本脚本的清洗层。
· 若走 rc 流程成为常态，必须先把"上一个正式版 tag"的定位逻辑补上。
```

## 2026-10-21 追加：Owner 读不懂更新说明 ⇒ 从「结构闸门」补到「词面」

**Problem（实测复现）**

Owner 2026-10-21 反馈：v1.4.0-rc3 的更新说明「全是开发用语，用户读不懂」。原样引用
当时那 93 行里的条目：

```text
新增：能力位文档⇄代码接线软报告 + CI 三档退出码
新增：CS-1 登录态同步接线到底 + N15 能力位撒谎被抓
新增：CS-1 凭据平面（Rust）+ R3-④ 透传守卫 + 跳过点写路径失败态
新增：SOURIN_YIELD_PROBE —— 让路生效的行为观测点
新增：detail_page 的 3 个 AlertDialog 换成自建 AppGlassDialog（M2 第 4 步）
修复：D-2 的期望值改用 Sp.x4，不再写死 32（假阳性）
修复：恢复 round-66 的 A17/B19/C28 副产品里被误删的 C28 行
```

**根因：闸门只判"像不像一句中文"，从不判"这话对谁有意义"**

`_is_readable_enough()` 的全部判据是 `_MIN_CJK_CHARS = 4`（够 4 个汉字就算可读），
加上若干符号/悬空判定。于是下面四类**结构合法但语义对用户无意义**的东西全部放行：

```text
① 工单号不是切口，是「单位」：判据只认 `CR #29` / `t1015` / `R3-④` 这种**带符号**
   的写法，而 `M2 第 4 步` / `N15` / `D-2 的期望值` 里工单号是**光秃的字母数字**，
   混在正常中文里 ⇒ 不命中任何规则。
② 内部清单本身被写进了白名单：`能力位` / `透传守卫` / `凭据平面` / 假阳性
   被当成"可能是产品术语"而放过 —— 判据分不清"少见的真术语"与"只有我们仨懂的缩写"。
③ 一条提交塞多个不相干改动（`A + B + C`），任何逐词清洗都只能洗掉角上的编号，
   句子主干还是内部说法 —— 这类**只能整条丢**，不能靠删词救。
④ 同一个词在标题里被当成"修复动作"：`修 gate 脚本…` 里的 `gate` 是闸门自己。
```

**Decision（三段流水线，顺序有意义，全部落在 `tools/gen_release_notes.py`）**

```text
① `_strip_internal_ids()`：内部标识**剥掉**，不是删词。
   `_TICKET_RE` 认 CS-1 / D-2 / R3-④ / N15 / M2 / H1 / t74 / ⑪ / round-66 /
   「第 4 步」「第 1 件」「轨道 E」/ 工单日期 2026-10-21；
   `_SYMBOL_RES` 认 xxx.dart / Cargo.toml / SOURIN_YIELD_PROBE / set_prefetch_disabled /
   AppGlassDialog / Sp.x4 —— 判据是**形态**（中文正文里不会自然出现这些形态），
   不是清单，所以下次起新代号也吃得住。
   ★ 例外表 `_KEEP_TOKENS`（H264 / 4K / macOS / YouTube…）原样保留 ——
     它们长得像编号但用户认识，剥掉反而更看不懂。

② `_drop_internal_segments()`：内部工程词**按段删**，不是整条丢。
   `_ENGINEERING_TERMS`（门禁/探针/断言/落盘/接线/透传/归一/假阳性/凭据平面/
   能力位/软报告/观测点…）命中则该段消失；段边界只切**顶层** `+` / `＋` / `；`
   （`_SEG_SEPS`），括号里的 `/` 不切。
   ★ 为什么按段而不是整条丢：本仓 2026-10-19 的实测结论是「整条丢弃词误伤
     11 条真修复」—— 典型「片头自动跳过可能整段漏跳 + 行为门禁」只因尾巴有
     "门禁"就整条消失。按段删能同时做到"用户看得见的那半句留下"。

③ `_has_user_surface()`：**必须命中一个用户可感知面**（`_USER_SURFACE`：
   弹幕 / 播放 / 搜索 / 设置 / 深色 / 海报 / 追更…），没命中就整条丢。
   这是把"用户能不能感知"从建议变成判据的那一步 —— 前两步只做减法，
   减完还剩一句"接线到底"的话，靠这一步拦住。
```

配套的形态闸门（都不是新维度，只是把"读得通"落实）：

```text
· `_has_code_glue()`：英文标识符紧贴中文（`AlertDialog 换成`、`raw-deflate ⇒`）⇒ 丢。
· `_final_form_ok()`：句子不许以英文标识符 / 括号 / 冒号开头。
· `_strip_impl_asides()` + `_MEDIA_FORMAT_TOKENS`：剥掉实现侧注
  （「（加可选 glass 档）」式补充说明），但保留 `1080p` / `HDR` 这类真格式词。
· `_fix_user_words()`：**词面**收口，只改词不改结构 —— 禁用词只在引号/括号后
  或句末才删（AGENTS §4 的「缺陷」），内部术语换用户语言
  （`发现点` → `看得见的位置`）。放在结构闸门之后：先判结构合格再换词，
  否则会把一条本该丢的残句修得像合格句。
```

数量读数（同一区间 `bdf64357..4b3b514`，315 条提交）：

```text
改前：93 行，其中开发用语约 40 行
改后：18 行，逐行人工过了一遍 —— 剩余 0 行含工单号 / 内部缩写 / 文件名 / 符号
```

**Alternatives considered（先写它们最强的理由）**

```text
A. 继续加黑名单词，不上"单位切分"（最小改动，风险最低）
   最强理由：黑名单是纯加法，改一条漏一条也能立刻补上，不会误杀真条目；
   而"工单号按单位切"必须靠启发式（哪些字母数字算工单），一旦切歪会吃掉
   `4K` / `HDR10` / `265` 这类真用户术语。
   否掉它的理由：实测里 3 个必丢样本（`M2 第 4 步`、`N15 能力位撒谎`、
   `D-2 的期望值`）的共同点不是"某个词坏"，而是**整句的主语是一个工单**——
   黑名单永远追不上工单命名法，且这些条目丢不丢取决于我们下次起什么代号。
   故采"单位切分 + 残句即丢"，并把 `4K`/`HDR`/`1080` 这类已知真术语写进
   `_KEEP_TOKENS` 白名单挡住误杀。

B. 让 LLM 在发布时把 93 行改写成用户语言（质量最好）
   最强理由：这是唯一能真正"按用户视角重写"的方案，规则永远做不到归纳
   （同一功能的 5 条提交合成一句"弹幕面板重构"）。
   否掉它的理由：发布链路是**离线的、可复现的、无密钥**的（本 note 的 Decision
   就是为此选的 git log 生成）；引入模型意味着发版依赖外部 API、
   同一区间两次跑出的说明可能不同，而"说明必须存在且不含开发用语"是**门禁**
   不是**创作**。→ 见"何时该翻案"第 1 条：若真要按用户视角重写，
   应改成"生成草稿 + 人工确认"，而不是把门禁换成模型。

C. 只保留 `feat`/`perf`，把 `fix` 全丢（简单、绝对不会出现开发用语）
   最强理由：`fix` 是开发用语的绝对重灾区（上面 93 行里 61 行来自 fix）；
   而用户对"哪里坏了被修好"的感知本来就弱，少报修复的代价比让人读不懂小。
   否掉它的理由：实测最好的几条样本恰好都是 fix ——
   「进详情页暂停后返回仍在播放」「宿主解不开 raw-deflate ⇒ 弹幕功能整个失效」
   「设置页「播放器缓存 0 B」永久误导用户」。整类丢掉等于把最有价值的说明删掉。
```

**Consequences**

```text
收益：用户视角的说明从"93 行里 40 行看不懂"变成"18 行逐条能懂"；
      判据冻结成 `--selftest` 的 48 条用例（含 18 条必丢 / 30 条必须保留的逐字期望），
      以后改规则时"手滑放宽"会当场红 —— 这是本轮唯一能防再犯的机制。
代价：① 会误丢一部分真实改动（多主题条目只留第一段，其余丢）；
      ② `_KEEP_TOKENS` 是白名单，新术语（如新分辨率）可能被当工单误切，
         需要人工发现后补进去；
      ③ 18 行对 315 条提交是**严重压缩**，若将来 Owner 需要"完整变更列表"，
         本脚本给不了 —— 那份东西应该由 GitHub 的 compare 页承担。
```

**何时该翻案**

```text
· 若 Owner 说"太少了 / 我想知道更多细节" ⇒ 说明压缩过度，
  应改为"按模块分组 + 每条保留"，而不是放宽清洗（否则回到 93 行）。
· 若出现"同一功能被拆成 6 条独立 bullet"的观感问题 ⇒ 需要语义合并，
  即方案 B，且必须配人工确认环节。
```

### 2026-10-22 更新：自动归纳旁边多了「人工确认稿」通道

本篇「何时该翻案」第 1 条要求的形态已经落地，但**不是**放宽清洗、
也**不是**把模型放进发版链路 —— 落地形态见
[./2026-10-22-release-notes-manual-override.md](./2026-10-22-release-notes-manual-override.md)：

```text
· 自动归纳仍是默认路径，本篇的强制点（归纳为空 ⇒ CI 红）仍然有效。
· 另加 `docs/release-notes/<TAG>.md` 人工确认稿通道：
  稿子存在 ⇒ 用它当本版更新；不存在 ⇒ 走自动归纳。
· 触发原因是实测：v1.4.0-rc3..HEAD 的 7 条真修复在自动归纳下**一条都产不出来**
  （「健康检测」里的「检测」被工程词表按段删空；产品名不在 ASCII 白名单 ⇒
  `_final_form_ok` 判 False）。这不是词表漏词，是结构性问题。
· 人工稿仍被机械校验（条目 / 表格 / 开发用语 / 占位符 / 站名 / 英文词），
  规则写在生成器的 `validate_manual_notes()` 里，CI 门禁**调用它**而不是复刻它。
```

★ 本篇的 Decision **不变**：默认路径、强制点、占位符纪律都维持原样。
