# Agent Note: 鼠标一动就卡 —— 把整页重建压到局部，重建次数 1624 → 20

Status: implemented

> 同域：[2026-10-18-bottom-bar-unmount-per-hover.md](../bug-fix/2026-10-18-bottom-bar-unmount-per-hover.md)
> 两篇是**先后关系**：本篇（`e6458e5`，重建 1624→20）修掉「整页 setState」；
> 那篇接着修「结构存在但装卸代价仍在」（`pageBuild` 已 0 而仍有 1624 次重建的部分）。
> 判据也不同：本篇看**重建次数**，那篇看**子树装卸**。

## Problem

Owner 反馈「播放页鼠标移动卡顿」，并要求「必须死磕」。

实测到的因果链不是"性能不好"，而是一个具体的结构错误：

```text
鼠标移动 ⇒ 控制条显隐状态变化 ⇒ 一路 setState 到**播放页整棵子树**
⇒ 每次移动都重建整个播放页（含视频区、弹幕层、右侧面板）
```

更糟的是底栏那一处：

```text
底栏用 `shrink ⇄ child` 的方式切换两种形态
⇒ 每次切换都**卸载再挂载**子树
⇒ 实测一次鼠标移动触发 **1624 次**重建
```

## Decision

### ① 光标 / 控制条态局部化

`e6458e5`：把「鼠标位置」「控制条可见」两个高频状态从 `setState` 改为
`ValueNotifier` + `ValueListenableBuilder`，只重建真正依赖它们的子树。

```text
改前：一次鼠标移动 ⇒ 播放页整棵树 rebuild
改后：只 rebuild 控制条那一层
```

判据不是"变快了"，而是**重建次数**：
```text
zz_t66_player_jank_test.dart（569 行）钉住重建计数上界
⇒ 这是可机械验证的，不受机器性能影响
```

### ② 底栏停止 `shrink ⇄ child` 反复装卸

`ddb0794`：底栏不再通过切换 widget 形态来实现两种状态，
改为**同一个 widget** + 属性变化。

```text
实测：一次鼠标移动的重建次数 **1624 → 20**
```

★ 关键点：`shrink ⇄ child` 这种写法看起来只是"换个布局"，
但它的代价是**子树整个重建**（state 丢失、动画重置、图片重新解码）。
这类代价在代码里完全看不出来 —— 只有计数才能暴露。

## Alternatives considered

- **加 `RepaintBoundary` 挡住重绘** —— 它最强的论据是改动极小（一行包裹），
  且能立刻减少重绘范围。
  否决理由：它挡的是**重绘（paint）**，而本处的问题是**重建（build）**。
  加多少层 `RepaintBoundary` 都不会减少 build 次数 —— 这是一个典型的
  "用对了工具但用错了层"。

- **给鼠标事件加节流 / 防抖** —— 它最强的论据是立刻见效，
  且不需要改数据流结构。
  否决理由：节流只是把 N 次重建变成 N/k 次，**单次重建的代价没变**。
  而且会引入可感知的延迟（控制条跟不上鼠标）。属于把问题推后而不是修好。

- **保持 `setState`，只把播放页拆成更多 StatelessWidget** —— 它最强的论据是
  符合 Flutter 常规做法，拆分本身也是好实践。
  否决理由：拆成 Stateless 不会阻止父级 `setState` 传递下去 ——
  父级重建时所有子级都会重建，除非用 `const` 或状态提升。
  真正起作用的是**把状态本身搬出这一层**，而不是拆组件。

- **不做门禁，靠人肉觉得"变流畅了"** —— 它最强的论据是体感就是最终判据。
  否决理由：体感受机器、构建模式（debug/release）、当前负载影响。
  本轮的做法是**用重建计数作为代理判据**，再配合真机体感确认 ——
  前者能进 CI，后者只在收尾做一次。

## Consequences

- **收益**：重建次数从 1624 降到 20（两个数量级）；鼠标移动不再触发整页重建；
  有 569 行门禁钉住这个上界，回退会被发现。
- **代价**：控制条相关状态从"页面级 setState"变成"notifier + builder"，
  多了一层间接；新读者需要理解「哪些状态是高频的、为什么不能 setState」。
  ⇒ 已在代码里对每个 notifier 写了「为什么它是高频状态」。
- **已知上限**：重建计数是**代理指标**，它不等于帧耗时。
  若将来出现「重建次数很低但依然卡」的情况，说明瓶颈移到了布局/绘制阶段，
  那时需要补帧耗时门禁（`FrameTiming`）。
- **重访条件**：当播放页新增高频交互（如拖动进度条预览）时，
  应沿用本模式而不是回退到 `setState`；若有人用 `RepaintBoundary` 来"修"
  重建问题，应指回本篇。
