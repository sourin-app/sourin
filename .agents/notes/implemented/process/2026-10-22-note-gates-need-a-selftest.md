# Agent Note: 笔记门禁需要自己的自测与空集合外壳

Status: implemented

## Problem

那三道 verify 脚本在**空集合**上都 `exit 0`：笔记目录改名、glob 写错、脚本只匹配到
0 个文件，它们会打印 `ok: 0 note(s)` 然后成功退出。对脚本本身这是合理语义
（「这个仓库还没有笔记」不该报错），但对 CI 是灾难 —— 三道门禁会一起变绿，
而它们本该挡的东西一件都没挡。

同一类问题的另一面：**门禁的判据写错时没人会发现**。2026-10-22 实测到
supersession 的链接正则漏认两种合法写法、archived 对基线缺失一律放行，
两处都不是「脚本坏了」——脚本正常退出、正常打印，只是判错了。
没有任何测试会让它们变红，所以它们可以一直错下去。

原有的 CI 步骤只做两件事：`test -f` 检查脚本存在、`node --check` 检查语法。
两者都只能抓「脚本坏了」，抓不到「判据错了」。

## Decision

补两层，都不复制门禁自己的规则：

1. **`notes-gate.mjs`（空集合外壳）**：先数笔记篇数，`0 篇 ⇒ exit 1`；
   否则依次跑 tree / format / archived，任一道非零即透传其退出码。
   它不判断笔记内容 —— 格式与树结构完全交给原脚本，免得「壳里的规则与脚本里的规则各说一套」。
   顺带做 runner 探测：写一个带类型标注的临时 `.ts` 真跑一次，
   能跑就用 `node`，否则回落 `npx --yes tsx`。CI 与本地因此可以用**同一条命令**。
   CI 的 ①.5 步已改为只调它。

2. **`notes-selftest.mjs`（判据自测）**：在临时 git 仓库里现造夹具、跑完删除，
   逐条断言**具体退出码**，正向（应 0）与反向（应非 0）成对出现：
   - supersession：三种合法链接写法各一条（都应 0）、真正没声明的一条（应 1）、
     `Independent:`（应 0）、`proposed/` 豁免（应 0）；
   - format / tree：缺 `## Decision` 的笔记、非法 class 目录（都应 1）；
   - archived：封印与基线一致（0）、全零基线（1）、拼错的 ref（1）、
     封印相对基线被改写而磁盘 manifest 同步更新过（1）、基线里 manifest 是坏 JSON（1）；
   - notes-gate：空树（1）、正常树（0）。

   每个用例失败时把该用例内每条命令的退出码与输出前几行打出来 ——
   只有「✖ 名称」时，看不出是门禁判错还是夹具写错。

CI 挂成独立一步 `笔记门禁自测`（①.7），与门禁本体分开：自测红 = 判据坏了，
门禁红 = 笔记内容坏了，两者的处理人不同。

## Alternatives considered

- **把空集合判据直接改进三个 verify 脚本里。**
  最彻底，但三个脚本是 vendored 副本（由 `dsh-agent-notes` 插件的
  `tools/sync-upstream.mjs` 管理上游），手改会被哈希比对拦下；而且
  「空仓库应当失败」是**本仓的 CI 策略**，不是脚本的通用语义 ——
  一个刚 adopt 这套方法论的仓库在笔记树建起来之前，脚本报 red 反而是错的。
  策略放壳里，语义放脚本里，这个分层后来证明是对的。
- **只在 CI 里加一句 `test $(find .agents/notes -name '*.md' | wc -l) -gt 0`。**
  能做，且比壳更短。否决理由是它只覆盖空集合，而自测要覆盖的是一整类
  「判据错了」。既然已经要为自测写夹具，顺手把空集合也做成一条用例更省。
- **用真正的测试框架（vitest/node:test）写自测。**
  这个仓库没有 `package.json`、没有 `node_modules`，为几个断言引入依赖与锁文件
  不划算（同一理由已写在 `verify-notes.yml` 模板的注释里）。
  `node:test` 倒是零依赖，但它的表格式输出不如「✔/✖ 一行一条 + 失败贴命令输出」
  直观，而这些用例的读者是**排查门禁的人**，不是看覆盖率报告的人。
- **让自测断言「退出码非 0 即可」，不写具体码。**
  最省事，也最没用：一个因为参数拼错而崩溃的脚本同样返回非零，
  于是「门禁会红」这条断言永远成立，包括门禁被删掉、被改成 `process.exit(1)` 恒红时。
  断言具体码（0 / 1 / 2 各有含义）才让它可证伪。

## Consequences

- **收益**：门禁的否定面从「据说会红」变成 19 条可执行断言；空集合这条
  从此不会静默变绿。判据再被改错时，`笔记门禁自测` 会先红，而不是等到某天
  有人手动试出来。
- **代价与已知上限**：
  - 自测跑一次约 10–20 秒（要建 git 夹具、跑十几道脚本），CI 时间增加有限；
    本地改笔记脚本时值得跑，改 Markdown 时不必。
  - 夹具里手搓的 archived 笔记必须**与真实格式一致**才能过 format/archived 两道判据。
    第一次就是被这个挡下的：`line 3 must be Status: implemented` /
    `line 4 must be Archived: YYYY-MM-DD`。所以夹具内容是从真实归档篇复制的头部，
    不是凭印象写的 —— 手搓 ≠ 真格式，这条教训也适用于任何「用假数据测门禁」的场合。
  - 自测只证明**这些用例**会红，不证明门禁覆盖了所有漏洞。
    新增判据时要同时加一条用例，否则新判据仍然是不可证伪的。
    2026-10-22 晚补记：这条警告当天就应验了 —— format 门禁的遮蔽器只认围栏代码块、
    不认行内代码，一篇记录 HTML 注释语法的笔记把自己后面的 `## Consequences` 遮掉，
    门禁报「缺小节」。自测当时 15 条全绿，因为夹具里没有「笔记正文出现自己的元字符」
    这种形态。补了两条对照用例（正向：行内 `<!--` 未闭合必须绿；反向：真未闭合注释
    必须红），详见 [../bug-fix/2026-10-22-note-format-gate-masks-inline-code.md](../bug-fix/2026-10-22-note-format-gate-masks-inline-code.md)。
    当天第二轮评审又把这两条用例各自的**判别力**问题挖出来了：正向夹具里写了
    行内 `` `-->` ``，旧实现同行闭合也能过 ⇒ 夹具区分不了新旧；而遮蔽器不认转义反引号、
    关注释时又拿遮蔽后的文本找 `-->`，各造成一个假绿一个假红。补成 4 条对照
    （正向 / 反向 / 转义反引号 / 注释内的 `-->`），每条都用 `git show <旧提交>` 取旧版
    脚本跑同一夹具做「旧红新绿 / 旧绿新红」对照。**教训**：夹具不仅要「能过」，
    还要能在旧实现下**红**；否则它测的是自己的假设，不是被测对象。
    重访信号：`notes-coverage.mjs` 目前还没有对应自测（它的 `--range` 语义依赖
    暂存区与提交区间，夹具成本更高），哪天它出问题就得补上。

```bash
node .agents/notes-scripts/notes-selftest.mjs   # → notes-selftest: 19/19 通过
AGENT_NOTE_ROOT=.agents/notes-nonexistent node .agents/notes-scripts/notes-gate.mjs   # → exit 1
node .agents/notes-scripts/notes-gate.mjs       # → notes-gate: 三道门禁全部通过（139 篇笔记）
```
