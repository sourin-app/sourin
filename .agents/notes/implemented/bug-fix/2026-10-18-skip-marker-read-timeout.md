# Agent Note: 读取跳过点没有超时 —— 故障被画成「未设置」

Status: implemented

> 同域：[2026-10-18-settings-direct-entry-and-unified-toast.md](../feature/2026-10-18-settings-direct-entry-and-unified-toast.md)
> 那篇把 `skip_marker_dialog.dart` 里的 SnackBar 收拢到 `showAppToast`
> （**提示机制**的接线）；本篇处理同一个文件里的**读取超时与失败态**。
> 两者机制不同（一个是提示出口，一个是数据加载状态），但都在同一个弹窗的
> "用户看得到的反馈"这条线上 —— 那篇管"说什么"，本篇管"说不说得出"。

## Problem

`SkipMarkerDialog` 打开时读一次已存的跳过点：

```dart
// skip_marker_dialog.dart  _loadExisting()
final m = await SourinApi.getSkipMarker(widget.provider, widget.id);
```

这条链是 `SourinApi.getSkipMarker` → `SourinCore.callAsync('get_skip_marker')`
→ FFI 线程池 → Rust 侧读一条记录。**全程没有 `.timeout()`。**

### 后果一：核心层卡住 ⇒ 永久转圈，没有出路

`_loading` 只有在「成功返回」或「抛异常」时才被置 false。若那个 Future
**永不完成**（核心层死锁 / 线程池排队满 / 数据库文件被锁），则：

```text
_loading 永远 true
  ⇒ build 走「_loading ? SizedBox(200, AppLoading()) : Padding(...)」
  ⇒ 用户看到：一个只有转圈的空白弹窗，永远转下去
  ⇒ 没有报错、没有出路、也看不出"是坏了还是在加载"
```

### 后果二（更糟）：失败被画成「未设置」，可能引发覆盖写

改前 `catch` 分支里是 `_loading = false`，之后四个值保持 `null`，
而 UI 照常渲染 ⇒ 显示「片头未设 / 片尾未设」。

```text
⇒ 「读取失败」和「用户从没设过」在屏幕上一模一样
⇒ 用户明明设过片头片尾，看到「片头未设」会以为**配置丢了**
⇒ 很可能重新设一遍 ⇒ **把真实配置覆盖掉**
⇒ 一次误读，引发一次真写入
```

这条是本缺陷真正的危险所在：**它把故障伪装成了正常状态**，
而用户对这个"正常状态"的合理反应（重设）会破坏数据。

### 触发面比想象的大

同一条链路上的 `getProgress`（详情页 `:1411`/`:1892`、缓存页 `:463`/`:553`）
同样没有超时，且 `getSkipMarker` 在全仓的**所有**调用点都没有超时
—— 本仓从来没有"读跳过点该多久"这个数。

## Decision

### 三态取代 `bool _loading`

```dart
enum _LoadState {
  loading,  // 还在读 —— 只转圈，**不渲染**四行
  ok,       // 读成功 —— 四行照常；此时 null 才真的表示"未设置"
  failed,   // 读失败/超时 —— 错误 + 重试，**绝不**渲染"未设置"
}
```

渲染从 `_loading ? 转圈 : 正常` 改成三路 `switch`，`failed` 走独立面板：

```text
[⚠]
读取跳过点失败：核心层 10 秒无响应
（不是「没设置过」—— 请重试，或关闭后重新打开）
[重试]
```

★ 文案里「不是「没设置过」」这句是关键：主动排除用户最可能的误解。
风格与同文件既有的「预览不可用：…（不影响设置）」保持一致 —— 两处判据是同一句：
**故障不许伪装成正常状态。**

### 超时 10 秒，且理由写进代码

```dart
static const Duration _kLoadTimeout = Duration(seconds: 10);
```

```text
· 这条路径的目的是**兜底不挂死**，不是 SLA 守护
· 正常耗时：FFI 线程池 + 读一条记录，毫秒级 ⇒ 真到 10 秒说明已经异常
· 不用 2~3 秒：那会拿一个**从未实测过 p99** 的操作去卡阈值，
  可能把"慢但正常"的用户打成"读取失败"，反而制造新问题
· 不用 5 秒：那是从探针里的原生调用类推的，无依据
· 10 秒在本仓有 8 处使用，是有先例的数
```

⚠️ 注释里写明：将来若做了 p99 实测，应按 p99 × 10 调整。

### 重试必须真的重发请求

```dart
void _retryLoad() {
  setState(() { _loadState = _LoadState.loading; _loadError = null; });
  unawaited(_loadExisting());     // ★ 真的重新调用
}
```

只把状态改回 `loading` 而不重新发请求的话，用户会看到转圈然后再次失败
（或永远转圈），等于按钮没有作用。

## Alternatives considered

### ① `onTimeout: () => null`（最初的建议，已否决）

```dart
.timeout(const Duration(seconds: 5), onTimeout: () => null)
```

看似最省事：超时当"没有跳过点"。**但这是静默降级** —— 正是本缺陷本身的形态。
`null` 在这个类型的语义里明确是「未设置」（见 `int? _introStart` 的注释），
所以超时返回 null 会让用户看到「片头未设」，后果与「不修」完全一样。

⇒ 否决。**能兜住转圈，但把危险转移到数据上。**

### ② 2~3 秒超时

本仓最常用的值是 `seconds: 2`（27 处）。但这条路径的操作从未实测过耗时，
用一个小数去卡它，会把"慢但正常"打成"失败"。
⇒ 否决，取 10 秒。

### ③ 只加超时，不改 UI（超时后仍走"正常渲染"）

最小改动，但保留了「故障伪装成正常」这个核心问题。
⇒ 否决。

### ④ 一并改同链路的 `getProgress` 和其它调用点

改动面大且没有真机证据说明那些路径也会挂。
⇒ 本轮只改 `SkipMarkerDialog` 的读路径；写路径（`:1284`/`:1312`）留下一轮。

## Consequences

### 门禁

新建 `test/zz_t66_skip_load_trstate_test.dart`，5 条：

```text
① 正常返回 ⇒ ok 态，四行标签都在
② 超时 ⇒ failed 态，**UI 上不出现「未设置」**
③ 重试 ⇒ 真的重新调用 fetcher（calls == 2），成功后进 ok 态
④ 阴性对照：真·未设置 ⇒ **必须**显示「未设置」
⑤ 源码级：三态分支齐全 + .timeout() 真接线 + 重试真调用
```

★ ②④ **必须成对**：只测②的话，把 UI 整个删空也能通过；
必须同时测④，才能证明这是**两种不同的显示**，而不是一种被删掉了。

### 两次故障注入（都已验红并还原）

```text
注入 A：failed 分支改回渲染「片头未设」（缺陷复活）⇒ ②③ 红
注入 B：删掉 .timeout()（**定义常量但不接线**）    ⇒ ②③⑤ 红
```

注入 B 守的是「写了 ≠ 接线了」：光定义 `_kLoadTimeout` 不算数。

### 数据安全影响

```text
改前：核心层卡住 ⇒ 用户看到"没设置过" ⇒ 可能重设 ⇒ 覆盖真实配置
改后：核心层卡住 ⇒ 用户看到"读取失败，请重试" ⇒ 不会去重设
```

这是本改动最重要的收益，不是"少转一会儿圈"。

### 还没覆盖的

```text
· 写路径 :1284 setSkipMarker / :1312 clearSkipMarker 同样无超时。
  挂住后：_saving 永不复位 ⇒ 按钮文案永久「保存中…」，
  且因 _canSave 不含 _saving，按钮**仍可点**但 _save 内部静默 return
  ⇒ 用户看到"保存中…"，怎么点都没反应。
  ★ 比读路径更隐蔽：读路径的弹窗是"空的"（明显不对），
    写路径看起来一切正常（按钮在、字也在），只是永远不生效。
· getProgress 的 4 个调用点（详情页 / 缓存页）同样无超时。
· 10 秒是兜底值，不是实测值。
```

### 何时该翻案

```text
① 若真机实测出 get_skip_marker 的 p99 ⇒ 按 p99 × 10 调整 _kLoadTimeout
② 若 Rust 侧改成保证不阻塞（比如全部走有界队列 + 显式超时）⇒
   本层的超时可以退化，但**三态仍要保留**（失败态与未设置态必须可区分）
③ 若将来接入真正的 zh 本地化或错误码体系 ⇒ 失败文案应改用错误码而不是异常字符串
```
