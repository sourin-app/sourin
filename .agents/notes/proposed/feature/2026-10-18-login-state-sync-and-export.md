# Agent Note: 登录态随 WebDAV 同步 + 全量导出导入

Status: proposed

> ⚠️ 文件名用「登录态」而不是「凭据」：`.gitignore:127` 有一条 `*credential*`
> 安全规则（防真实凭据进库），会误伤文件名。**不要为了过 git 而削弱那条规则**，
> 改文件名即可。正文里讨论凭据本身没有问题。

## Problem

当前同步只覆盖三类数据，**凭据完全不在其中**：

```text
rust/sourin_core/src/sync/mod.rs 现有的同步平面：
  favorites.jsonl          收藏 + 追更
  progress/{provider}/…    播放进度
  backup/{provider}/history-{device}.jsonl   平台历史镜像
⇒ **没有任何凭据平面**。
```

后果：

```text
· 换一台机器 ⇒ 收藏、进度、追更都在，但每个源的登录态要**重新登一遍**
  （弹幕发送、需要登录的源、B 站等全部失效）
· 用户有多台设备时，登一次只在那一台上有效
· 这与"云同步"这个功能对用户的心理预期严重不符 ——
  他以为同步了就是这个软件的状态都过去了
```

同时，**导出/导入**现在只有 `backup_page.dart` 这一条手动的整包备份路径，
与云同步是两套互不相干的东西：用户要迁移到新机器，得先手动导出、
再拷 U 盘、再导入，而云端明明已经连着。

## Proposal

### 一、凭据同步（WebDAV）

```text
1. 新增一个**独立的同步平面** `credentials`，与 favorites / progress 并列
2. 内容 = 现有的凭据存储（钥匙串里的那条记录 + plugins/.data/ 下的登录态）
   ★ 具体格式在实现时按现有凭据模块定，不在本提案里拍
3. 加密：
   · 用一个**用户口令**派生的密钥加密（口令不进云端）
   · 不能用固定密钥 —— 那等于把凭据明文放 WebDAV
   · 派生参数（算法/迭代次数/salt）写进文件头，便于将来升级
4. 口令生命周期：
   · 首次开同步时要用户设一次
   · 保存在本机钥匙串（不随同步走，否则失去意义）
   · 换了设备 ⇒ 首次同步要用户**再输一次口令**（这是特性，不是麻烦）
5. 冲突策略：
   · 凭据是「后写覆盖」语义，不做合并（合并凭据没有意义）
   · 但覆盖前必须记录被覆盖的是哪台设备、什么时间，
     否则用户会发现"我明明在 A 机登过，B 机一同步就没了"
```

### 二、导出 / 导入（本地文件）

```text
1. 导出：一个文件（zip 或单文件带内嵌分节），内容与云同步平面一致
   · **必须包含凭据**，且同样用口令加密
   · 明确提示用户：这个文件含登录态，别随手传
2. 导入：三种粒度
   · 全部覆盖
   · 只导入某几个平面（收藏 / 进度 / 凭据 …）
   · 合并（同 id 取 updated_at 新的）
3. 与云同步共用同一套序列化格式 —— **不要写两套**
   （否则"本地导出的文件"和"云端拉下来的包"结构不一致，
     将来一定会出现"导入后行为和同步后不一样"的诡异 bug）
```

### 三、UI

```text
· 设置 → 数据与同步：在现有"云盘同步"下面加"凭据"开关 + 状态行
· 导出/导入入口放同一页，避免用户以为它们和云同步是两件事
· 凭据未设口令时，同步状态必须显示"凭据未同步"而不是"同步完成"
  ★ 这一条是硬要求：显示"完成"但凭据没走，就是本仓反复出现的假绿同类
```

## Alternatives considered

- **把凭据也做成明文平面，跟 favorites 一样** —— 它最强的论据是实现最省事，
  与现有平面完全同构、零新概念。
  否决理由：WebDAV 是用户自己填的第三方存储，可能是别人的 Nextcloud、
  可能是共享盘。明文放登录态等于把账号交给那个存储的管理者。

- **不做口令，用系统钥匙串里已有的某把密钥加密后同步** —— 它最强的论据是
  用户完全无感，不用记任何东西。
  否决理由：那把密钥在**每台机器上是不同的**，换机后解不开 ⇒ 同步过去也没用。
  要让它跨机可用，就得把密钥本身也同步上去 ⇒ 等价于明文。

- **只做导出/导入，不做云同步** —— 它最强的论据是攻击面小得多
  （文件在用户自己手里，不经过第三方）。
  否决理由：Owner 明确要求两者都要；且只做导出的话，多设备日常使用
  仍然要反复手动搬文件，"云同步"这个已存在的功能就始终差一块。

- **凭据和普通数据混在一个平面里同步** —— 它最强的论据是只需一次上传、
  一次下载，没有"部分成功"的中间态。
  否决理由：混在一起就没法单独关掉凭据同步。而"我只想同步收藏，
  不想把登录态放到网盘"是完全合理的诉求。

## Acceptance criteria

```text
① 新机器首次同步：输入口令后，各源登录态可恢复，无需逐个重登
② 口令错 ⇒ 明确报"口令不正确"，不许静默跳过凭据只同步其它平面
③ 未设口令 ⇒ 同步状态显示"凭据未同步"，不许显示为完成
④ 云端凭据文件被替换/损坏 ⇒ 走明确的失败路径，不静默用旧缓存
⑤ 导出的文件在另一台机器导入 ⇒ 结果与云同步一致（同一套格式的验证）
⑥ 故障注入：把凭据平面从同步清单里删掉 ⇒ ① 必须变红
⑦ 导出文件里 grep 不到任何明文的 cookie/token/SESSDATA 形态
   ★ 这一条要用真实导出物验证，不是读代码
```

## Risks

```text
· 安全责任转移：一旦凭据上云，泄露面从"本机"扩大到"用户选的存储"。
  缓解：强制口令加密；UI 必须让用户在开启前明确知道这一点。
· 口令遗忘 = 凭据不可恢复（设计如此，不提供后门）。
  ⇒ 必须在设置口令时提示"忘了只能重新登录各源"。
· 与现有 credentials 模块的耦合：实现前必须确认凭据当前存在哪
  （钥匙串 / plugins/.data/ / 两者都有），格式不能想当然。
· 本提案**未确定**凭据存储的确切格式与加密参数 —— 那是实现阶段的事，
  但必须在动手前查清，否则会做出"加密了但解不开"的半成品。
```
