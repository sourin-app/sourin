# 插件规范对照：WebHome Devkit → 本仓

> 起因：Owner 提供了 `cnb.cool/fish2035/ext`（WebHome Devkit），要求"同步到我们的插件开发仓库模板上"。
> 本文是**逐条对照与取舍结论**，不是搬运。
> 相关：[PLUGINS.md](PLUGINS.md)（本仓插件开发的权威文档）｜[ARCHITECTURE.md](ARCHITECTURE.md)

---

## 0. 先说结论：两套东西**不是同一种插件**

| 维度 | WebHome Devkit（`ext`） | 本仓插件 |
| --- | --- | --- |
| 运行位置 | 真实网页的 **WebView 注入**（`document-start/end/idle`） | **rquickjs 沙箱**，无 DOM |
| 输入 | 一个真实 URL + 页面 DOM | 宿主给的 `req` 对象（分类/列表/详情/取流） |
| 输出 | 调 `fm.play()` 等 SDK 推给原生 | 返回 JSON（`{ok, data}`） |
| API 风格 | 油猴（`GM_addStyle` / `GM_getValue` / `GM_xmlhttpRequest`） | 自定义 `host.*` |
| 能操作网页 | ✅ 能改 DOM、注入样式、拦点击 | ❌ 完全没有 DOM |
| 典型用途 | 给某个网站加"App 播放"按钮、嗅探媒体地址 | 把某个站点的接口适配成本仓的数据模型 |

⇒ **不能照搬**：`fm.ui.*` / `GM_addStyle` / `document-start` 注入时机 / `fmresume`
这些概念在本仓**没有对应物**，搬进来只会是死文档。

⇒ **但有三块真的值得学**，见下。

## 1. 逐条对照

| # | WebHome Devkit 的做法 | 本仓现状 | 取舍 |
| --- | --- | --- | --- |
| 1 | 扩展对象 `id/name/version/runAt/cspKeyRegex/js/code/depends/updateUrl` | 有 `@id/@name/@version/@author`（脚本头注释） | **部分借鉴**：见 §2.1 |
| 2 | `depends` + 版本约束（`id@>=1.2.0`）+ 拓扑排序 + 级联跳过 | **完全没有** | **不引入**：见 §2.2 |
| 3 | 扩展状态机（`unmatched/matched/skipped/ready/injected`） | 有 `PluginSourceStatus` 但**不是这个语义** | **借鉴命名与可诊断性**：见 §2.3 |
| 4 | 包装层 `try/catch` + `//# sourceURL=fm-ext-<id>.js` | 有超时与错误包装，但**报错定位不到插件行号** | **借鉴**：见 §2.4 |
| 5 | `GM_getValue` 等**返回 Promise**（异步存储） | `host.store` 是同步的 | **不适用**：本仓沙箱内同步存储没有宿主阻塞问题 |
| 6 | 三层来源（全局 / 站点 / 用户）与"全局默认禁用" | 单层（用户安装的 `plugins/*.js`） | **不适用**：本仓没有"配置下发"这个渠道 |
| 7 | `runAt` 三档注入时机 | 无（插件在调用时执行） | **不适用**：没有页面生命周期 |
| 8 | `cspKeyRegex`（按站点 key 正则匹配） | 无（插件自己就是站点） | **不适用**：本仓一个插件对应一个源 |
| 9 | 文档开头就写"脚本适合做什么 / 不适合做什么" | 无对应章节 | **借鉴**：见 §2.5 |
| 10 | 每条 API 都标注"失败会怎样" | 部分有 | **借鉴**：见 §2.5 |

## 2. 真正该补的 5 块

### 2.1 清单字段：补 `@depends` 之外的两个说明字段

本仓已有 `@id/@name/@version/@author/@description/@homepage`。
对照下来缺的不是字段，而是**语义约束**：

- `@version` 目前**只用于展示**（卡片上的版本号），**不参与任何判断**。
  这一点必须在文档里写明，否则插件作者会以为"版本小改一下就能触发更新"。
- `@id` 必须**全局唯一且稳定**。WebHome 那份文档点出了一个我们没写的坑：
  > id 为空时按 `来源 + 序号` 自动生成 ⇒ **配置顺序变化会改变 id 并丢失用户状态**

  本仓 `@id` 缺失时按什么生成，也要写清楚（见 PLUGINS.md 的实现），
  并且明确警告：改 `@id` = 用户已保存的该源配置/收藏全部失联。

### 2.2 `depends` 与拓扑排序：**不引入**

**最强理由（为什么不引入）**：
WebHome 的扩展是**注入到同一个页面的多段脚本**，它们共享 `window`、需要
"A 先跑装好 `window.fmTvHelper`，B 再读它"—— 依赖是**真实且必需**的。

本仓插件是**彼此独立的数据源**：每个插件自己抓自己的数据、返回自己的 JSON，
宿主按源路由。**没有任何一个插件需要另一个插件的产物才能工作**。
（唯一像"共享"的场景——多个站共用同一套解析逻辑——正确解法是抽公共片段
复制进各插件，而不是让插件在运行时互相 require：沙箱里没有模块系统，
硬加一套依赖解析等于自造包管理器。）

⇒ 引入 `depends` + 版本约束 + 拓扑排序，会得到一套**没有用例的机制**：
代码要维护、门禁要写、文档要解释，而没有任何插件会用到它。
**这是"为对标而加"，属于过度设计，明确拒绝。**

若将来真的出现插件互相依赖的用例（例如"通用弹幕适配器"被多个站复用），
届时应先重新评估**架构**（是否该把这些逻辑下沉到宿主），而不是先加依赖系统。

### 2.3 状态机：把"为什么没生效"变成可查

WebHome 的六态（`unmatched/matched/skipped/ready/injected`）本仓没有对应物，
但它解决的那个**用户痛点**我们有：

> 插件装上了，卡片也显示了，但搜不到东西 / 取流失败 —— 用户不知道卡在哪一步。

本仓可落地的等价物（三态，对应真实的失败点）：

| 状态 | 含义 | 用户能做什么 |
| --- | --- | --- |
| `load_failed` | 脚本语法错 / 顶部注释缺 `@id` | 打开插件文件看报错行 |
| `declared` | 清单解析成功，但**没验证过** | 点"健康检测"真跑一次 |
| `working` / `broken` | 健康检测的结论（已有 `ProviderManifest.working` / `broken_reason`） | 看具体原因 |

⇒ 结论：**不新造状态机**，而是把既有的 `working` / `broken_reason`
在 UI 上说成人话（"从未检测" ≠ "可用"）。这是补文档与文案，不是加机制。

### 2.4 `sourceURL`：让插件报错能定位到插件自己

**这是本次对照里最有实际价值的一条。**

WebHome 给每段注入脚本加 `//# sourceURL=fm-ext-<id>.js`，
于是 Console 里的报错会显示 `fm-ext-srcl.js:12:5` 而不是 `VM123:1`。

本仓现状：插件抛错时，`call_js` 只能给出 `Runtime`/`Context` 层的错误文本
（形如 `Error: xxx`，**没有行号指向插件文件**）。插件作者拿到
"TypeError: undefined is not a function" 完全不知道是自己哪一行。

**已实测（2026-10-25），结论与预想相反，但找到了更好的办法。**

探针一：`//# sourceURL=plugin-probe.js` 注释 ——
```text
[EVIDENCE] source_url error = Exception generated by QuickJS
[EVIDENCE] source_url recognized = false
```
⇒ **QuickJS 不认 `//# sourceURL`**（那是 V8/浏览器的约定）。
更糟的是默认 `eval` 返回的错误只有一句 "Exception generated by QuickJS"，
**连异常类型和行号都没有** —— 对插件作者的信息量为零。

探针二：在 JS 层包 `try/catch`，把 `e.stack` 取出来 ——
```text
[EVIDENCE] js_stack =     at <anonymous> (eval_script:3:20)
    at <eval> (eval_script:7:16)
```
⇒ **能拿到精确到行:列的堆栈**。

所以正确方案不是 sourceURL，而是**在包装层 try/catch 并透出 `e.stack`**。
注意两点：
1. 包装层会让行号**偏移**，必须记录偏移量并在展示时减掉，
   否则插件作者按报的行号去看会看错行 —— 那比没有行号更坏。
2. `eval_script` 是 QuickJS 的默认文件名，改不了（sourceURL 无效），
   所以展示时应替换成 `<插件 id>` 才不让人困惑。

实施见 §3。

### 2.5 文档结构：补"该做什么 / 不该做什么"与"失败会怎样"

WebHome 的文档有一段我们完全没有的内容：

```text
脚本适合做的事：…
脚本不适合做的事：
  · 不应在没有用户动作的情况下批量打开播放页
  · 不应把账号、Cookie、隐私数据输出到远程日志
  · 不应为了"万能"而破坏网站自己的搜索/筛选/分页
```

本仓插件同样有"写歪了会坑用户"的形态，值得逐条写清（已补进 PLUGINS.md，见 §3）：

- 不要在 `list()` 里发 N 次请求去补全每一条的封面（一次翻页 = N+1 次网络）
- 不要在 `detail()` 里把整季剧集全解析成直链（用户点开一集却拉了几十个地址）
- 不要在插件里硬编码 Cookie / token（插件是纯文本文件，会跟着备份导出）
- 不要为了"兼容所有站"把字段映射写得层层兜底（错了要能看出来，而不是"总能返回点什么"）

## 4. 一句话总结

WebHome Devkit 是**浏览器注入式**规范，与本仓**数据源式**插件架构不同。
值得拿的只有三样：**报错定位到插件行号**、**"该做/不该做"的写作结构**、
**id 稳定性警告**。其余（`depends`、`runAt`、`cspKeyRegex`、`GM_*` 异步存储）
在本仓没有对应机制，硬搬只会得到没有用例的代码与看不懂的文档。
