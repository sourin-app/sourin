# Agent Note: 作废一个数字时，要 grep 它的全部出现位置

Status: implemented

Independent: 与
[thresholds-from-measurement-not-from-myth](2026-10-19-thresholds-from-measurement-not-from-myth.md)
是**同一件事的两半**：那篇讲「阈值该按实测定」，
本篇讲「**把一个旧数字从代码里彻底清除**」时容易漏的地方。

## Problem

`test/zz_t66_player_jank_test.dart` 里有一个作废的基线数字 `190`。
我改了它出现的三处中的**两处**：

```text
✓ :63   基线表里的「E 隐藏光标 … all=190」        改了
✗ :438  print('…（改前：page=1 all=190）')       ★ 漏了
✓ :443  注释里的「hideAll 仍是 ~193」            改了
```

★ 漏掉的那处是**运行时 `print`** —— 它每次跑测试都往日志里印一个
**已经被证伪**的数字。⇒ 读日志的人（人或 CI）会继续拿它当对照。

而且翻出第二件事：**同一份基线表里，`190` 与 `~193` 并存**
（`:63` 写 190、`:443` 写 193），而复核实测
「worktree 里缺 `sourin_core.dll` 时读数正好是 **193**」
⇒ 我当时的推断是「190 是 193 的手抄」。

★★★ **复核把这个推断推翻了，并给出更严重的机制**：

```text
A/B 各 2 次实跑（同一个 worktree，只差 DLL）：
  补齐 sourin_core.dll ⇒ T2 all=**531**（红，2/2 稳定）
  缺件                  ⇒ T2 all=**193**（★ 全绿，2/2 稳定）
```

**⇒ 193 来自「缺 DLL 的降级环境」，而那个环境让整个文件全绿（+7）。**
**⇒ 所以问题不是「抄错了一个数」，而是「一个假绿环境的读数被当成了对照基线」。**

★ 且机制比我原先写的更广（实测）：

```text
我写的：核心加载失败 ⇒ `_playing` 置位路径不同 ⇒ 树规模不同
实测：listProviders / 取源能力 / **阴性对照** 全部退化
      P0 阴性对照 all 从 **1 变成 0** ⇒ 什么都没发生
      ⇒ 是**整条异步链路不执行**，不是单点不同。
```

## Decision

```text
① 把 :438 的运行时 print 也改掉，并写明「已作废 + 为什么作废」
   —— 一个每跑一次就印一次的假数字，比注释里的假数字危害大得多
② :443 的注释同样改成「实测 531 + 作废理由 + 193 的来源是**假绿环境**」
③ 在注释里把「为什么缺 DLL 会让读数变」写清楚
   ⇒ 且必须写清它**让整个文件全绿**（实测 193 环境是 +7 全绿）
   这是 MEMORY 里「worktree 只 checkout 受版本控制的文件」那条的又一实例
```

## Alternatives considered

**A. 只改「看起来是主结论」的那一处（我第一版）。**
最强理由：那一处是三条断言的依据，改了它门禁就正确了。
否决理由：**运行时 `print` 也在印那个数**。
读日志的人看到「改前 all=190」与屏幕上的 531 并列，
会以为两者可比 —— 而它不可比。

**B. 把 `190` / `193` 全仓删干净，一个字不留。**
最强理由：彻底。
否决理由：需要在注释里**说清它为什么作废**，否则下一个人会
「好心」地把它当成有效基线恢复回去。删除 ≠ 澄清。

**C. 用脚本批量替换这两个数字。**
最强理由：快。
否决理由：**这两个数字可能是别处的合法值**（比如某个计数恰好是 193）。
⇒ 必须逐处判断语境，不能批量。

## Consequences

**判据（这次真正学到的一条）**

```text
作废一个数字时，`grep` 它的**全部出现位置**，不要只改
「看起来是主结论」的那处。

★ 尤其注意这三类位置：
  ① 断言的依据（最显眼，通常先改）
  ② ★ 注释 / 文档（容易漏）
  ③ ★★ 运行时 print / 日志输出（**最容易漏，且危害最大** ——
     它每次跑都在制造新的假证据）
```

**★ 更一般的一层**

```text
一个数字被写进基线表，意味着它在替某条断言背书。
作废它 = 撤掉那条背书 ⇒ 必须同时撤掉
  · 断言的阈值
  · 注释里的引用
  · 日志里的打印
三处缺一不可，否则下一个人会拿「注释里的 190」当默认值。
```

**★★ 环境陷阱（本篇最有价值的一条）**

```text
「worktree 里缺 sourin_core.dll ⇒ 读数 531 变 193，★ 而且整个文件全绿」

A/B 实测（各 2 次稳定）：
  有 DLL ⇒ all=531（红）   无 DLL ⇒ all=193（★ +7 全绿）

根因（复核实测，比我原先写的广）：
  核心加载失败 ⇒ listProviders / 取源能力 / **阴性对照** 全部退化
  P0 阴性对照 all 从 1 变成 0 ⇒ **什么都没发生**
  ⇒ 是**整条异步链路不执行**，不是 `_playing` 单点不同

⇒ 两个环境给出的数「长得一样」（都是 pageBuild=1、all 三位数）
⇒ 不记录环境，就会把「**假绿环境的读数**」当成「历史基线」。

★ 判据：**任何写进基线表/对照的数字，都必须同时记录
  「在什么环境下测的」，且那个环境要可复现。**
  「同一天测的」不算 —— 这正是 190 不可考的根因。
```

**★★★ 而「190 不可考」有一条更硬的证据，不需要 fsck**

```text
复核指出队友的判据 `cursorLive=8` 是**循环论证**：
  `_cursorLive` 是 `aedc29c` 引入的（git log -S 实测），
  而 aedc29c 在 e6458e5 **之前** ⇒ 用它判「已含 N11」不成立。
  （结论侥幸没错，因为 39 个悬空 commit 确实都在 aedc29c 之后。）

⇒ 换成一条**结构性事实**，不需要任何历史搜索：
  ① `git show --stat e6458e5` ⇒ **只加 569 行测试，零 lib 改动**
     ⇒ 测试诞生时 lib 已经是 N11 之后的状态
  ② `git log -S "_cursorLive"` ⇒ 只命中 `aedc29c`
     而那个 commit 的标题是「弹幕发送栏」——★ **N11 的产品代码被混进了一个
     标题完全无关的 commit**
  ⇒ 「有测试、而无 N11」这个状态**在历史上从未作为任何 commit 存在过**
  ⇒ 连 39 个悬空 commit 的搜索都不需要。
```

★ 附带纠正一处表述：说「在 `aedc29c` 上跑 T2 得到 531」不严谨 ——
`aedc29c` 里**没有这个测试文件**（测试是 `e6458e5` 才加的），
所以那是「`aedc29c` 的产品代码 + `e6458e5` 的测试」上跑的。

★★ 验证「缺件类守卫」时，**先数清它有几个落点**（我今天因此栽了两次）

```text
第一次（libmpv）：`_libmpvCandidates()` 返回**两个**路径，
  我只移走第一个 ⇒ 测试从第二个找到 ⇒ 守卫**没触发**，我却以为它有效。
第二次（sourin_core）：`DynamicLibrary.open('sourin_core.dll')` 走系统
  DLL 搜索路径，而 AGENTS §8 要求 CI 把它拷到 `windows/` ⇒ 实际有三个落点：
    ./sourin_core.dll   ./windows/sourin_core.dll   ./build/.../Release/
  我漏了 `windows/` ⇒ 移走仓库根那个后防护没触发。

⇒ 判据：**验证「缺件 ⇒ 应当跳过」的守卫时，
  必须把全部候选路径都移走，否则你测的是"缺了一个"而不是"缺了"。**
```

★★★ ★★ 由此引出一条**必须记住的操作纪律**

```text
我用 `for f in <三个同名文件>; do mv "$f" /tmp/mv_$(basename $f).bak; done`
⇒ ★★ basename 对同名文件产生**相同的目标名** ⇒ 三次 mv 互相覆盖，
  只剩最后一个备份；还原时又把同一个备份mv回三次 ⇒ **两个文件永久丢失**。

⇒ 判据：**备份文件名的每一段都必须唯一**。
  正确做法：用路径而非 basename 命名（/tmp/bak/libmpv__a.dll），
  或在循环里加序号（/tmp/bak.$(echo $f | tr / _)），或**不要在循环里做备份**。

★ 这次没造成损失的原因（不是运气好，是可核对的）：
  `rust/sourin_core/target/release/sourin_core.dll` 的 md5 与仓库根那份相同
  （666b2e0926c001bd12a52142c6f511b8）⇒ 可从 canonical 落点重新拷出。
  ⇒ ★ 这也说明：**产物应当有一个 canonical 落点**，
  其余都是它的副本 —— 否则丢了就得重编。
```

**何时该翻案**

```text
· 若将来有了 CI 产物能记录环境（commit + DLL hash + 平台），
  基线表就应当只存「带环境指纹的数字」，
  手写的裸数字应当被门禁拒收。
· 若 `debugOnRebuildDirtyWidget` 将来变更语义（它现在是内部钩子），
  本文件全部读数都要重测 —— 因为它们量的是这个钩子。
```
