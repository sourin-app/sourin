# Agent Note: 笔记覆盖门禁在「一个长分支的合并 PR」上会审判史前史 —— 给它划出生点，并让后补的笔记能认领旧提交

Status: implemented

> 同域：[笔记树是唯一的决策记录处](2026-10-17-notes-tree-is-single-decision-record.md)
> —— 本篇不改变「要不要写笔记」，只改变**门禁把审查的起点放在哪里**。
> 同域：[门禁要的「提交区间」在 `fetch-depth: 1` 的检出上根本不存在](2026-10-21-ci-gate-needs-full-git-history.md)
> （同一个 job 的邻居：门禁要么真在跑，要么红着把原因说清）。
> 同域：[CI 上「静默 skip」比「红」更危险](2026-10-19-silent-skip-is-worse-than-red-in-ci.md)
> （同一族：本篇里两处「收窄」都必须**打印出来**，否则就是静默 skip 换了个形状）。

## Problem

`notes-coverage.mjs` 的判据是**逐提交**的：一个提交改了受管路径（`lib/`、`rust/`、`test/` …）
就必须自带一篇决策笔记，或者写 `Note-Skip:` 说明为什么不必。这条判据本身是好的
——「一个提交带的笔记不能替另一个提交顶账」正是为了防「批量 push 时一篇笔记掩护一大片」。

问题出在**区间怎么取**：

```text
.github/workflows/build.yml:373-383  笔记覆盖门禁
  NOTES_COVERAGE_BASE: ${{ github.event.pull_request.base.sha || github.event.before }}
  ⇒ pull_request 事件：base.sha = **main 的当前顶端**
  ⇒ push 事件：before = 这次推送前的那个提交
```

而本仓 workflow 的触发条件是 `on: push: branches: [main]` —— **推分支根本不跑 CI**。
两者叠起来的结果是：

```text
分支上的每一个提交，从诞生起就没有任何 CI 在检查它有没有笔记
  ⇒ 等到这个分支第一次提 PR，base.sha 指向 main
  ⇒ 门禁一次性审判整条分支的**全部历史**
```

本轮实测（2026-10-21，PR #32，run 39550083454 Windows job）：

```text
NOTES_COVERAGE_BASE = bdf64357（main 顶端）
区间 = 319 个提交
  ✔ 已用 Note-Skip 放行   15 个
  ✖ 改了受管路径却没带笔记  80 个 —— exit 1
```

★ 关键事实：这 80 个提交里绝大多数**不是「作者偷懒」**，而是「门禁在它们诞生时还不管它们」
—— 门禁 2026-10-18 才接进 CI（`e0ab611`），且接进的是一个**从不被 CI 检查的分支**。
拿门禁回头审判它出生之前的历史，只有两种结局：**永远红**，或者**被人绕过**。
本仓已有的证据是后者：`docs/AGENTS.md` 里记着「CI 绿了也不许自己合」的同类经验。

⇒ 一门永远红的门禁不会被遵守，只会被删掉或 `--no-verify`。这是**判据的射程问题**，不是执行问题。

## Decision

两处改动，都在 `.agents/notes-scripts/notes-coverage.mjs` 里，都不放宽「一个提交一篇笔记」这条判据本身。

### 一、门禁自限出生点：出生之前的提交不归它管

```text
出生点 = 最早一次**新增**本脚本的那个提交
         git log --diff-filter=A --format=%H %cs -- .agents/notes-scripts/notes-coverage.mjs
区间起点早于出生点 ⇒ 收窄到出生点之后，并且**打印收窄幅度与出生点**
```

本轮实测读数（本地 `--range bdf64357..HEAD`）：

```text
ℹ 区间起点早于门禁出生点（e0ab611 2026-10-18）
  ⇒ 前 126 个提交不归本门禁管，只检查其后的 193 个
⇒ 失败数从 80 降到 1
```

★ 为什么「收窄」必须打印，而不是静默跳过：静默收窄会让日志看起来像「全区间通过」。
打印之后它读作「**前 126 个不归它管，后面的 193 个逐个查过**」—— 这跟
[CI 上「静默 skip」比「红」更危险](2026-10-19-silent-skip-is-worse-than-red-in-ci.md) 是同一条。

### 二、`covers:` —— 后补的笔记可以认领它之前的提交

`explainFailure` 里一直写着「补法：可另起一个『补笔记』提交」。在逐提交判定之下
**那句承诺是假的**：后补的笔记落在新提交里，认领不了任何更早的提交。现在把它补成真的：

```text
笔记正文里写一行   covers: 6106c84
⇒ 该提交被这篇笔记认领，放行，并打印「由哪篇笔记认领」
```

防滥用三条（缺一条都会变成后门）：

```text
① 只有**本次区间内**的笔记才算（区间外的不认）
② 认领的 sha 必须能在本区间里找到（区间外的一律无效）
③ 每一次认领都打印出来（谁认领了谁）
```

## Alternatives considered

**A. 给那 80 个提交逐个补一篇笔记（把欠账真的补上）。**
最强理由：这是唯一**不改变判据射程**的解法 —— 门禁原来想说什么就还是说什么，
不需要任何「出生点」概念，也不需要为将来的分支解释一遍为什么它豁免。
否决理由：80 篇笔记是**事后追写的 80 个决定**，而其中大部分提交的真实内容是
「按上一条笔记的结论继续改」。事后补出来的笔记只有两种：编造的（比没有更糟），
或者复述提交信息的（不构成决策记录）。⇒ 它会把笔记树从「决策记录」稀释成
「提交信息的副本」，而**稀释后的笔记树没人读**，这比缺 80 篇更接近真正的损失。

**B. 给 80 个提交逐个补 `Note-Skip:` 尾注。**
最强理由：`Note-Skip` 是本仓**已有**的合法路径，不需要新增任何机制；
且它要求写清「为什么这个提交不必立笔记」，等于逼人逐个过一遍 diff。
否决理由：`Note-Skip` 的语义是「**这个提交没有行为改动**」。这 80 个里相当一部分
**确实改了行为**（只是当时没被要求记）。用 `Note-Skip` 放行它们，
等于把一条判据的**豁免**当成**事实认定**来用 —— 一旦这么用了，
以后就没有人分得清「真的没改行为」和「当时没人查」。且 retroactive 改写 80 个提交
需要 rebase 整条分支，代价比新生 80 篇笔记还大。

**C. PR 事件上把区间改成 `HEAD~1..HEAD`（只查最后一个提交）。**
最强理由：最省事，改一行，`workflow_dispatch` 走的本来就是这个回落路径。
否决理由：这恰好**废掉**这条门禁存在的理由 —— 逐提交检查的全部价值就在于
拦住「一次 push 里混进 20 个改动、只写一篇笔记」这种形态。改成只看最后一个提交，
一个 PR 里前 318 个提交随便改都是绿的。⇒ 那不是修门禁，是把门禁换成一块绿布。

**D. 用管理员权限直接合并 PR，跳过检查。**
最强理由：本轮的目标是「把 232 个提交的成果合进 main」，而门禁红的是历史债、
不是这次的新代码 —— 从「这次改动有没有问题」这个角度看，跳过并不掩盖任何真实缺陷。
否决理由：分支保护开着 `enforce_admins`，就是为了让「这次先合了」不发生一次也不用发生第二次。
一次管理员绕过会被后来的人当成先例（「上次也这么合的」），
而**门禁的可信度只能整体存在，不能部分存在**。

## Consequences

- **收益**：门禁第一次在合并路径上**真的会红**（此前它只在 `workflow_dispatch` 的
  `HEAD~1..HEAD` 回落里跑，等于没跑过）。出生点划定之后，历史债被**命名**而不是被豁免：
  日志里写着「前 126 个不归它管」，可以核对、可以质疑。
- **收益**：`covers:` 让「补笔记」这条承诺变成可执行的 —— 本轮 80 个里的最后一个
  （`6106c84`，一条纯测试契约提交）就是用一篇新笔记认领掉的。
- **代价（已实测）**：出生点靠「本文件被新增」这个事件识别，**改文件名会让出生点后移**，
  从而放走一段本该受管的历史。⇒ 脚本头部注释与调用处都要求把出生点 sha 与日期打印出来；
  若哪天日志里的出生点比预期晚，先怀疑是重命名。
- **代价**：`covers:` 是一处**新增的自由声明**。它被限制在「区间内 + 必须是十六进制 sha
  + 每次打印」，但它仍然允许「一个人写一篇笔记认领别人 20 个提交」。
  这条边界写在这里，不当成不存在。
- **仍然存在的欠账**：`bdf64357` 之前、`e0ab611` 之后的提交里没有笔记的那些，
  现在被出生点**整体放走**了（126 个）。它们不会自动被补 —— 想补的时候，
  用 `covers:` 一篇认领一个，比事后编造 126 篇诚实。
- **何时翻案**：
  ```text
  · 若将来分支也会跑 CI（on: push: branches: ['**'] 或专门的轻量 job），
    那么「分支上的提交从没被检查过」这个前提消失，出生点收窄就该撤掉 ——
    那时它是纯豁免，不再有存在的理由。
  · 若本脚本改名，出生点会漂；改名时必须在同一次提交里把出生点写死成常量，
    否则一段历史会被无声放走。
  ```
