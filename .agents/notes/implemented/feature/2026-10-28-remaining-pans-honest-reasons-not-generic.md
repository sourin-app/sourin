# Agent Note: 剩下四家网盘不共用一句"尚未接入"—— 四种情况必须分开说

Status: implemented

> **后续（2026-10-28 晚，事实更正 —— 不改变本文当时的决定）**：光鸭/迅雷/天翼三家的"做不了"
> **依据**后来被证明是错的 —— 迅雷端点与光鸭参数是取证工具漏报，天翼"要 webview"是把提示文案
> 当协议。三家现已接通，另开一篇：
> [./2026-10-28-device-flow-and-tianyi-logins.md](./2026-10-28-device-flow-and-tianyi-logins.md)。
> 本文仍然成立的是：123 **没有**扫码这条路（后来补强了理由），以及"逐家说清区别、
> 不共用一句套话"这条纪律本身。

Independent: 本条不改任何已接通网盘（夸克/UC/百度/115/阿里）的代码路径，
只改**兜底分支的语义**：把 `qr_login_start` 里那句通用文案拆成四家各自的准确原因。
与 `2026-10-28-aliyun-qr-login-and-token-shape.md` 是同一批的收尾，但决定相反方向
（那条是"做出来"，这条是"说清为什么现在不做"）。

## Problem

Owner 的要求是「其余 7 家网盘登录扫码能出二维码」。做完 UC/百度/115/阿里之后，剩下
光鸭、迅雷、天翼、123 四家共用一句兜底文案：

```text
"XX 的扫码登录尚未接入（当前完成夸克/UC/百度/115/阿里；其余按批推进）"
```

这句话把**四种完全不同的情况**混成了一种：

```text
光鸭   OAuth 设备码。缺的是 client_id/scope（设备码申请那一步的参数）
迅雷   OAuth 设备码。缺的是**申请设备码的端点**（换 token 的端点与 client_id 反而有）
天翼   要网页登录（logbox → callbackUnify → getAccessTokenBySsKey），核心没有内嵌浏览器
123    只有 open-api 开发者令牌，**根本没有扫码这条路**
```

后果：用户以为"这四家都在排队等做"，我们自己也看不出"哪一家是永远做不到、哪一家只是缺一个读数"。

## Decision

兜底分支改成**按盘给原因**，每条都写清"缺的具体是什么"，并且让门禁钉住关键词：

```rust
PanKind::Guangya => Err("… 缺客户端参数（client_id/scope）…")
PanKind::Xunlei  => Err("… 申请设备码那一步端点没有取证 …")
PanKind::Tianyi  => Err("… 要网页登录，本核心没有内嵌浏览器 …")
PanKind::Pan123  => Err("… 只有 open-api 令牌，没有扫码端点 ⇒ 画一个码只会扫不动")
```

门禁 `unimplemented_kind_says_so_instead_of_pretending` 从"含『尚未接入』"升级为
**逐家断言关键词**，并额外断言"不许回落到通用文案"。

## Alternatives considered

### A. 猜参数把四家硬做出来（光鸭/迅雷设备码，天翼按 logbox 拼）

**最强理由**：Owner 的原话是"7 家都能出二维码"，硬做至少 UI 上看起来齐了；
实机验证留到批末，届时再修也行。

**否掉的原因**：

```text
① 设备码流程**第一步**就是"申请 code"。端点/参数猜错的表现是 404 或 200 但无码 ——
   UI 上不会报错，用户扫了没反应，比"明说做不到"难查十倍。
② 天翼与 123 **没有扫码这条路**：一个要 webview 会话，一个要开发者令牌。
   给它们画一个二维码是**假象**（扫了必然无效），违背"不伪造成功"。
③ 四条消息本身就是交付物的一部分：Owner 在批末验证时能立刻分清
   "这三家等读数" vs "123 永远不会有扫码"。
```

### B. 保持一句通用文案

**最强理由**：零改动、零风险。

**否掉的原因**：四种情况混成一句，等于把"能力边界"这件事糊掉 ——
本仓的既有纪律是"做不到要说清哪一步做不到"（`needs_ext` 逐类标注、网盘 `play`
如实报"取流链路未接通"都是同一条）。通用文案是这套纪律的例外，属于欠债。

### C. 给天翼内嵌一个 webview

**最强理由**：那是唯一能真正完成天翼登录的路（它的凭据要靠 sessionKey 换）。

**否掉的原因**：核心是 headless 的 FFI 库（`sourin_core` 被 Flutter 侧调用），
嵌浏览器属**架构级**改动（进程模型、权限、打包体积、macOS/iOS 的 WKWebView 差异），
不在本批收尾范围。若要做，应单独立项并先与 Owner 确认形态（另记在"何时该翻案"）。

## Consequences

**收益**

- 四家的文案各自回答了"缺什么、要等什么、有没有这条路"，UI 上不再是一团模糊。
- 门禁从"含某句套话"升级为"逐家关键词"，将来谁把某家接上、忘了改文案，会立刻红
  （关键词消失 ⇒ 断言失败）。
- 能力边界变得可盘点：读代码就知道"还差 4 家，其中 1 家永远不会有扫码"。

**代价与边界**

- 这四家**仍然不能登录**（本条只是把"不能"说准）。目标里"7 家都能出二维码"因此
  **没有达成**，剩下的是取证工作，不是编码工作：
  光鸭要 client_id/scope，迅雷要设备码申请端点，天翼若要支持得先定 webview 方案。
- 文案是用户可见文本，将来接上某家时要同步改文案与门禁关键词（两处必须一起动）。

## 验证结果（已发生）

```text
cargo test --lib pan_login --release → 35 passed / 0 failed
  改写：unimplemented_kind_says_so_instead_of_pretending
        逐家断言关键词（客户端参数 / 申请设备码 / 网页登录 / open-api），
        并断言"不许回落到通用文案"
故障注入（真红，已实测）：
  把光鸭那条文案里的「客户端参数」删成「客户端」⇒ 该用例 FAILED
```

## 何时该翻案

1. 光鸭：拿到 `client_id`/`scope`（真机抓包或参考实现方法体）后补 `guangya_start/poll`
   —— 结构可照抄迅雷那套设备码，凭据用 `access_token=` 约定键。
2. 迅雷：拿到**设备码申请端点**后同上（换 token 的端点与两个 client_id 已有）。
3. 天翼：只有确定"允许内嵌 webview 或改为让用户粘 ssKey"之后才谈实现。
4. 123：如果官方开放扫码登录，再补；在此之前保持"要开发者令牌"。
