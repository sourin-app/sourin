# Agent Note: bili 弹幕自动绑定 —— 按 manual 分流，而不是"一律不套用"

Status: implemented

## Problem

Owner 对同一件事说过两次，两次都指向"自动绑定"，但修法相反：

```text
第一次：> 就是不要自动绑定 已经绑定的不管
第二次：> 我的意思是bilibi不要再自动绑定,手动绑定的以后就自动更新
```

第一次之后，`_loadDanmakuNamed` 里"起播套用历史绑定"的那一段被**整段删掉**
（`player_page.dart` 2026-10-27 23:3x 的改动，只有注释、没留笔记）。这个改法有两个毛病：

```text
① 过度纠正：删掉之后「手动绑定的以后就自动更新」也一起失效 ——
   用户手绑过一部的第 3 集，起播第 4 集不会自动带上弹幕，得每集重新点。
   这正是第二次原话里明确要保留的行为。
② 漏了第二条消费路径：`_biliAutoRefresh`（切集 / 集列表变化时调用）仍然
   只要 `loadBinding(...)` 非空就套用，前置条件只有全局开关
   `biliAutoUpdateEnabled()`，**不看这一部是不是手绑的**
   ⇒ 早期自动流程残留的 `manual == false` 记录照样会在"切一集"时自动出现
   ⇒ Owner 看到的现象原样复现。
```

`bili_bind.dart` 里判据其实一直都在：`saveBinding` 把"手动绑过"单独存一个键
（`BiliPrefs.manualKey`，注释写明"这样自动流程改绑时不会把它抹掉"），
`isManualBinding(provider, id)` 一直可调用 —— 只是**起播与自动刷新两处都没问它**。

**用户机器上的真实分布（`.probe/n1run/data/ui-prefs.json`，只读统计）**：

```text
dsh.bili.bind.*    = 34 条
dsh.bili.manual.*  =  2 条
⇒ manual=1 的绑定 2 条 ｜ manual=0 的绑定 32 条（94%）
★ 这解释了 Owner 的观感：34 条里 32 条是早期自动流程建的，
  它们在他每次起播/切集时都被套用 ⇒ "又自动绑了"。
  而他那 2 条手绑的（第二句原话要保留的"以后就自动更新"）在本次改动后照旧生效。
```

## Decision

**"自动绑定"按数据来源分流，不按是否调用自动流程分流。**

`manual == true`（用户亲手绑过）⇒ 起播套用 + 切集自动更新；
`manual == false`（早期自动流程残留）⇒ 不套用、不自动更新，但**记录不删**；
没有绑定 ⇒ 永不自动建立（`_autoBindBili` 仍是死代码，零调用点）。

两条消费路径都按这个判据走：

```text
· `_loadDanmakuNamed`（起播）：`if (biliBind != null && !biliBind.isEmpty && isManualBinding(provider, id))`
· `_biliAutoRefresh`（切集）：方法开头 `if (!isManualBinding(provider, id)) return;`
```

全局开关 `biliAutoUpdateEnabled()` 与 `isManualBinding()` 是**两层**，不是替代品：
前者是"允许自动更新"（用户偏好，全局），后者是"这一部够格"（数据来源，逐作品），
两个都真才更新。

记录一律不清：弹幕信息面板仍读 `loadBinding` 展示、可解绑；用户若想启用，
走面板手动入口把它变成 manual。因为是"区分"不是"清除"，**不需要数据迁移**。

## Alternatives considered

1. **起播与自动刷新都不看绑定（= 第一次改法的延伸）**。
   最强理由：Owner 第一句话就是"不要自动绑定"，一刀切最省解释成本，
   而且能彻底消灭"我明明没绑它自己出来了"的观感。
   **否决** —— 与第二句原话直接冲突（"手动绑定的以后就自动更新"），
   且它把绑定数据变成只读展示，用户手绑的价值归零。
2. **维持原状（只要读到绑定就套用）**。
   最强理由：这是 `t73` 组2 早就在守护的既有契约（"外部视频站优先：绑了就一个
   dandanplay 请求都不发"），不动它最省事。
   **否决** —— 它是"自动绑定"观感的实际来源：`manual == false` 的残留会
   在起播/切集时自动生效，而 `manual == false` 恰恰说明**不是用户绑的**。
3. **加一个"是否自动套用历史绑定"的全局开关（默认关）**。
   **否决** —— 与 2026-10-18 那次删 `_autoBindBili` 同一条纪律：
   留一个开关（默认关）等于留一条随时被打开就复活的路；而且它按"全局偏好"
   表达一件**逐作品**的事实（这一部是手绑的还是自动残留的）。
4. **写一次迁移，删掉 `manual == false` 的历史绑定**。
   最强理由：残留没了，起播随便套用都不会出现"没绑也有"。
   **否决** —— 用户数据不该被静默删；而且无法区分"当年真手绑、但标记没写进去"
   的记录，删了就永久失去。分流两个分支的成本远低于一次不可逆迁移。

## Consequences

- 收益：Owner 两句话同时成立 —— 手绑的继续"以后自动更新"，非手绑的不再自己冒出来；
  两条消费路径共用同一个判据，不会出现"起播改了、切集没改"的半修状态。
- 收益：没有数据迁移，回滚只需把两个条件删掉（判据本身在同一处）。
- 代价：`t73` 组2 的语义必须同批改 —— 原来断言的是"起播段不许出现 `loadBinding`"，
  现在断言"起播段必须带 `isManualBinding` 且不带裸套用形态"，
  外加一条新的 ⑦（自动刷新必须先问 manual）。语义变更该被门禁看见，不是绕过门禁。
- 代价：`manual == false` 的残留记录会变成"看得见（面板展示）但不会生效"的东西，
  用户若想恢复需要点一次手动入口 —— 这是刻意的：它把"是否绑定"的决定权交回用户。
- 验证：注入两处（删起播的 manual 判据 / 删自动刷新的门控）都**真红**
  （①②⑤ 与 ②⑦），还原后 md5 一致、`t73` 回 +19 全绿；
  日志 `.probe/r2-5-manual-gate-inject.log`。
