# Agent Note: 直播分组从「按源」改成「按频道」，并给直播页补上搜索与冷启动快照

Status: implemented

## Problem

Owner 在本轮给了四条互相咬合的反馈（逐字）：

> 我第一次打开直播这个压面 显示0个,我打开第二次 又等了好久才显示出来

> 我要的是自建分组可以选择直播源下的具体的直播的房间，而不是选择直播源，这是错误的

> 自定义分组有了,但是配置的地方没有

> 直播源会返回具体的可播放的频道啊,然后可以选这些频道,直播也支持一下搜索好吧

读代码后核实，这是**四个不同层面的缺陷**，不是一个"没做好"：

```text
① 分组模型错了（结构性）
   live_groups_page.dart 存的是「源 id 列表」⇒ 一个分组只能表达
   「这个源的全部频道」。而本机一个直播源有 20~48 个台 ——
   用户想挑的是其中几个房间，模型**表达不出来**。

② 冷启动把"失败"画成"空"
   loadAll() 里：
       try   { final groups = await SourinApi.getLiveChannels(); … }
       catch { debugPrint(…); }              ← ★ 异常被吞
       finally { setState(() => _loading = false); }
   ⇒ 核心未就绪时 getLiveChannels() 抛异常 ⇒ _groups 仍是 [] ⇒
     build 走到 `_currentChannels.isEmpty` ⇒ **「没有可用的直播源」**。
   用户被引导去"设置里启用源"，而他的源明明是启用的。

③ 第二次仍然慢（真的重复全量拉取）
   LivePage 是保活页，但 shell 的 `_switchTo(AppTab.live)` 每次都调
   `loadAll(keepSelection: true)` ⇒ **又一次全量** `get_live_channels`
   （rust 侧 registry.live_all() 逐个插件执行 JS）。
   而"关掉重开"连内存都没有 ⇒ 只能再等一整轮。

④ 没有频道搜索，也没有分组入口在直播页
   工具栏只有一个源切换条里的搜索（那是搜**源名**，不是搜台）。
```

## Decision

### ① 分组数据模型：新增 v2 键，**不原地改 v1**

```text
v1  live_source_groups     {"常看": ["<源 id>"]}                        ← 保留
v2  live_channel_groups    {"常看": [{"p":"<源 id>","c":"<频道 id>"}]}  ← 新增
```
⚠️ 举例用占位符而非真实台名/源名：仓库有站名台名门禁（`t98`），
笔记里的举例同样在扫描范围内。

为什么不原地改 v1 的格式（这是本条最关键的取舍）：

```text
· 用户机器上已经有 v1 数据（真实 ui-prefs.json 里就有）。
  原地改格式 ⇒ 老数据解析失败 ⇒ 用户分组**静默消失**。
· 两个键可以共存：读的时候 v2 优先、v1 兜底
  （判据 = liveGroupAllowsChannel 的四条语义）。
  ⇒ 老分组照旧能用，用户在新界面改一次就自然升级成 v2。
· 回退成本 = 删掉 v2 的键，v1 原样还在（不破坏性）。
```

判据抽成**顶层纯函数** `liveGroupAllowsChannel`，四条语义：

```text
① group == null            ⇒ 全部放行
② 该组有 v2 数据           ⇒ 只放行被勾选的频道（按 provider + channelId 两个 id）
③ 没有 v2、但有 v1         ⇒ 回落到「这个源的全部频道」（老数据不静默失效）
④ 两个都没有 / 空组        ⇒ 全部放行（绝不筛成空）
```

为什么必须 (provider, channelId) **成对**存：

```text
`LiveChannel.id` 只在**同一个源内**唯一。实测本机两个直播源
都有 id 形如 `1` / `2` 的频道 ⇒ 只存 channelId 会让分组
命中**别的源**的同名频道（用户没选过的台）。
```

为什么判据要抽成顶层纯函数（这是本仓的结构墙）：

```text
`LivePage._groups` 只由 FFI 填，`flutter test` 里恒为空
（t48 开头记着这道墙）⇒ 整页层面喂不进数据。
⇒ 唯一能"真跑判据"的形态就是纯函数，否则测试只能读源码字符串（假绿）。
```

### ② 冷启动：三态分开 + 磁盘快照

```dart
enum LiveLoadPhase { loading, failed, empty, ready }
LiveLoadPhase liveLoadPhaseOf({loading, failed, channelCount})
```

顺序是 `loading → failed → empty → ready`，**failed 优先于 ready**：

```text
若把 failed 放在 channelCount 之后，一次失败但还留着旧 _groups 时
会显示"正常"，用户不知道数据已经陈旧。
⇒ failed 优先 ⇒ 明确给他一个能点的动作（重试）。
```

快照用**既有** `DiskCache`（不新造机制）：

```text
① initState 先 `_hydrateFromCache()` 读 <dataDir>/live-channels-cache.json
   ⇒ 首帧就有列表（本地文件读，毫秒级）
② 后台照常 getLiveChannels() 拉真数据 ⇒ 回来后替换并落盘
③ 写的是**后端原始 JSON 形态** ⇒ 读回来直接喂 LiveGroup.fromJson
   （不需要维护第二套映射，与 disk_cache.dart 文件头的纪律一致）
```

三个必须的细节（漏一条就是新 bug）：

```text
· **串行**而不是并列：并列时谁先回来谁算数 ⇒ 快照可能覆盖更新的真数据
  ⇒ 用户看到列表回退。用 `_hydrateFromCache().then(loadAll)`。
· 缓存里的台**不自动起播**：快照可能过期（那个台已下线）
  ⇒ 冷启动拿它取流 = "一进来就报错"，比"列表先出来"糟得多。
· 空结果**不覆盖**已有快照：一次抖动就把缓存清空是反向优化。
```

### ③ 重入保护

```text
shell 每次切到直播页都调 loadAll(keepSelection: true)，而本页是保活页。
用户快速"直播→首页→直播"时两次全量请求**同时在飞**：
  · 后到的 setState 覆盖先到的 ⇒ 列表闪
  · 两次 _select() 抢同一个播放器（取流两次）
⇒ `_inFlight` 标记：还在飞就不重复拉。
```

### ④ 搜索 + 分组入口

```text
· 搜索框放在**页头**（横跨两栏），状态由 LivePageState 持有、受控下传。
  为什么不放右栏工具条：右栏只有 300px，已有三格下拉 + 管理按钮，
  再塞输入框会把每格压到 60px 以下。
· 判据 liveChannelMatchesQuery：空查询放行 / 大小写不敏感 /
  同时匹配频道名与源名 / **不做拼音**（仓库没有拼音表，硬加会假命中）。
· 搜索放在四个维度（分组∩源∩分类∩搜索）的**最后**一道：
  放前面会让别的维度把用户刚搜到的台否决掉。
· 空态文案分**三种**：搜索空态 / 筛选空态 / 真无频道 —— 三种原因三种出路。
```

分组编辑 UI 从"一排源名胶囊"改成"按源分块的**逐频道**胶囊"：

```text
保留"按源分块"是刻意的：本机 4 个源 100+ 个台，
全平铺等于没有结构。源做**分块标题**（不可点），频道在块内可点 ——
这正是 Owner 说的"直播源**下**的具体房间"的字面形态。
"全选某个源"作为**快捷方式**保留（不是唯一入口，细粒度入口仍是主路径）。
```

## Alternatives considered

**原地把 `liveSourceGroupsKey` 的值格式改成频道 id**
最强理由：只有一个键，没有"两套语义"的心智负担。
否定原因：用户机器上已有 v1 数据 ⇒ 解析失败 ⇒ **分组静默消失**。
而分组是用户手工攒出来的东西，丢一次就再也不会信任这个功能。
两个键的代价（判据多两条分支）远小于那个风险。

**把分组语义改成"只能按频道，v1 一律不认"**
最强理由：模型干净，没有回落分支。
否定原因：老用户打开直播页会发现"我建的分组一个都选不出东西"
（v2 里没有他们的数据）⇒ 比"没有这个功能"更糟。

**给 `LivePage` 加一个可注入的频道源（为了测试）**
最强理由：整页可测，能验"真的渲染出列表"。
否定原因：那要改 `LivePage` 的公开构造签名，而 `shell.dart` 不在本批写入范围
（并行批次也在动 shell 附近）。判据层抽纯函数 + `LiveChannelList`（已是公开
组件）已能覆盖到"按钮真的接上了"。

**搜索用拼音/模糊匹配**
最强理由：中文用户可能打拼音。
否定原因：仓库里没有拼音表，硬加要引一个依赖或维护一张表；
而没表的模糊匹配会产生大量假命中（"tiyu"命中"体育"要表，"t"会命中一切）。
⇒ 明确只做字面子串，并在测试里**钉住**"不做拼音"（避免将来有人误以为漏了）。

**冷启动用内存缓存 + 只在同一次运行内生效**
最强理由：不碰磁盘，没有过期/损坏问题。
否定原因：Owner 说的"第二次"很可能包含**关掉重开**
（他就是这么描述"第一次/第二次"的）。内存缓存对那个场景零帮助。

## Consequences

**代价（必须说清）**

```text
· 两套分组键共存 ⇒ 判据多两条分支，将来要读分组的地方都得知道"v2 优先"。
  缓解：判据只有 liveGroupAllowsChannel 一处实现，别处都调它。
· 磁盘快照有"陈旧窗口"（最长 = 一次刷新周期）。
  ⇒ 页头**显式**标"正在刷新…（列表是 X 分钟前的快照）"，不假装是最新的。
· 快照里的台不自动起播 ⇒ 冷启动后有一小段时间"列表有内容但播放器空"。
  这是刻意的取舍（宁可空一瞬，也不要"一进来就报错"）。
· 设置页在**没有快照**时退回手输源 id（老路径）。
  两条路径并存 ⇒ 该页有两个编辑形态，文案要各自说清（已写在页内说明里）。
· 管理器对话框宽度 560 → 820：逐频道勾选 + 组内搜索需要横向空间。
```

**何时该翻案**

```text
· 若将来给分组加"排序/颜色/图标" ⇒ 该把值从"数组"改成"对象"，
  但那正是 v3 的事，**不要**在 v2 的数组里塞对象（会毁掉 v2 的解析）。
· 若 v1 数据在真实用户机器上确认已全部升级（可加一个"已升级"标记）⇒
  那时可以删掉 v1 回落分支。**在那之前不许删**。
· 若播放器能可靠地"先展示后校验"（例如取流失败自动重试一次）⇒
  快照里的台就可以自动起播，那条取舍会翻转。
```

## Verification

### 冷启动时序读数（真机 release 构建，隔离数据目录，1262 个频道 / 4 个源）

```text
构建：flutter build windows --release -t lib/shell.dart
      --dart-define=DATA_DIR_OVERRIDE=<隔离目录>
数据：tools/seed_dev_data.ps1 播种（真实插件的副本，真实目录只读）
读数：AppLog.write('LIVE', '[TIMING] …')  →  <dataDir>/logs/sourin-*.log
```

| 场景 | 快照命中（首屏有内容） | 真数据就绪 |
| --- | --- | --- |
| **首次运行**（无快照，插件未预热） | 无快照 ⇒ 骨架 | **4918 ms** |
| 无快照（进程内插件已预热） | 无快照 ⇒ 骨架 | **24 ms**（自页挂载 0 ms） |
| **有快照**（冷启动） | **0 ms** | **48 ms**（自页挂载） |

**怎么读这三个数（不要挑好看的说）**：

```text
· 4918 ms 是**真·首次**（换数据目录后的第一次）：要逐个插件执行 JS。
  这就是 Owner 说的"第一次打开显示 0 个"背后那段空白 ——
  改前它最终会画成「没有可用的直播源」（异常/长等待都被 catch 吞了）。
· 24 ms 的那次是**同一个进程/同一套预热过的插件**，不代表冷启动。
  它说明"插件预热后全量拉取并不慢"—— 慢的是**第一次**。
· 0 ms 是快照路径：`_hydrateFromCache()` 在首帧前读完本地文件就 setState。
  ★ "0 ms" 是 `inMilliseconds` 取整的结果（实际为亚毫秒级），
    不是"没花时间"，但确实远小于一帧。
```

**结论（能说什么 / 不能说什么）**：

```text
✅ 能说：有快照时首屏**不再等**那次全量拉取（0 ms 上屏，4918 ms 的那次挪到后台）。
❌ 不能说：冷启动总时长降低了 4918 ms —— 后台那次全量**照样发生**，
   只是用户不再对着空白等它。首次安装后的第一次仍然要付那 4918 ms。
```
