# Agent Note: 源个性化覆盖层（二次编排与劫持）挂在 call_js 之后

Status: proposed

## Problem

Owner 要求「JS 插件的可视化编排」要能做到：

> js插件也要支持,你想想方案吧,必须全部都可以,比如 只是链接,可以对数据二次编排修改,或者做劫持
> js,可视化可自由编辑支持的,但不能影响原有插件本身,属于是个性化
> 声明式还是一样,不修改本身
> 可视化编排还是属于二次修改劫持的产物需求

现有编排器（`lib/ui/widgets/source_composer_dialog.dart` + `source_composer_model.dart` 的 `ComposerDraft`）产物是**一份新的声明式源 JSON**，经 `importDeclarativeProvider` 落盘。它只能表达「站点结构 → 标准结构」的一次性映射，有两个根本限制：

1. **只能生成新源，不能"个性化改造已有源"**。而 Owner 要的是"不能影响原有插件本身"的**覆盖层**，与原件并存、可关可删。
2. **表达不了"对数据二次修改"与"劫持"**。`ComposerDraft` 只有 id/name/base/headers/endpoints 五个维度，没有任何"拿到返回数据后再处理"的位置。

同时 `_configOf` 对 js 插件只给 `_configPlugin`（按 `config` 声明渲染表单），而本机 37 个插件 config 声明全是 0 项 ⇒ 点「配置」只弹一句「没有声明可配置项」，还带着一句**方向错误的指引**（"可视化编排用于声明式源，请在「编辑」里打开"）。

## Proposal

新增一层**个性化覆盖层（Override Layer）**，独立于任何源，按 `targetId` 绑定，只读原件、只写自己的文件。

### 挂载点：`call_js` 之后、`from_str` 之前

```rust
// 现状（16 处完全一致的模式）
let json = self.call_js(&expr).await?;
serde_json::from_str(&json).map_err(...)
```

不逐个改 16 个方法，而是**在 `call_js` 内部**统一应用覆盖层。理由：本仓已有「单一写入路径」的教训——`save_hook` 的注释记着两条路径曾经发散；16 条链路各改一次必然漂移。

风险控制：`call_js` 也跑 `login` / `qr_login_poll` 等**非数据**调用，覆盖层必须按**表达式/方法名过滤**，只对数据类方法（`home`/`list`/`search`/`rank`/`detail`/`episodes`/`sources`/`resolve`）应用。

### 三层能力，同一份覆盖层文件

```text
plugin.xxx() → 原始 JSON 字符串
      ↓  L1 字段映射（可视化点选，不跑 JS）
      ↓  L2 数据变换（过滤 / 排序 / 替换 / 正则 / 去重）
      ↓  L3 JS 劫持（rquickjs 沙箱，输入输出都是 JSON）
      ↓  serde_json::from_str → 强类型 → UI
```

- L1/L2 **不跑 JS**：快、可静态校验、可视化编辑器能完整表达，覆盖不会写 JS 的用户。
- L3 复用宿主**已有的 rquickjs 0.14 沙箱**与 `SCRIPT_BUDGET_MS` 熔断，安全边界与插件本身一致，不另造引擎。
- 「只是链接」这种最弱形态也能接：L1 给「URL 模板 + 字段映射」即可产出可用覆盖层。

### 存储与回退

- 覆盖层存 `<数据目录>/overrides/<targetId>.json`，与插件文件、声明式源文件**物理分离**。
- 保存路径**只许**写 overrides 目录；删除该文件 = 完全回到原行为。

### 分期

- **P1**：覆盖层模型 + L1 应用（Rust 单点挂载）+ 门禁。
- **P2**：可视化编辑器（任意源，含「只有链接」）。
- **P3**：L2 数据变换。
- **P4**：L3 JS 劫持（含熔断阴性对照）。
- **P5**：声明式源接入。

## Alternatives considered

- **只给 js 插件加一个「编排」按钮，复用现有 ComposerDraft**：改动最小，能让 `_configOf` 对 js 也给两个入口。但 `ComposerDraft` 的产物是**新的声明式源**，无法表达「对已有源的数据二次修改」，Owner 明确要的是"个性化/劫持"，这个方案答不上。放弃。
- **把 `_configPlugin` 空态改成"可视化编辑 config 项"**：不动架构，但本机 37 个插件 config 声明全是 0 项 ⇒ 绝大多数插件仍然没有表单可渲染，治不了根本前提。放弃。
- **逐个修改 16 个 provider 方法各自应用覆盖层**：语义最清晰，每个方法能按自己的类型做校验。但 16 条链路必然漂移（本仓 `save_hook` 有过"两条路径发散"的实测教训），且新增方法时容易漏。放弃，改为 `call_js` 单点。
- **让覆盖层直接改插件 .js 源码**：实现最简单、能力最强。但直接违反 Owner 的"不能影响原有插件本身"，且一旦改坏无法回退。放弃。
- **用 Dart 侧改写（在 FFI 之后、UI 之前）**：不需要动 Rust。但 Dart 侧拿到的是已解析的强类型，丢失了原始 JSON 的未知字段（用户可能想读插件返回但宿主没建模的字段），且要改每一条 FFI 调用链。放弃。
- **L3 直接跑用户 JS 且允许访问 `host.store` / 网络**：能力最强。但把"数据变换"升级成"任意代码执行 + 网络"，权限面与插件本身等价却少了插件安装的显式授权环节。放弃默认放开，改为**默认只做纯数据变换**（是否放开网络待 Owner 确认）。

## Acceptance criteria

- 无覆盖层时，`call_js` 的输出与改造前**逐字节一致**（阴性对照）。
- 覆盖层 `enabled=false` 或 JSON 损坏时，**原样透出原始数据**，不静默清空。
- 删除覆盖层文件后，输出与"从未配置过"一致（可回退）。
- 三层叠加顺序固定为 L1→L2→L3：构造一个三层都改同一字段的 fixture，最终值必须是 L3 的。
- 覆盖层保存路径上 `writePlugin` / `installPlugin` **零命中**（源码断言）。
- 跑完覆盖层后插件文件与声明式源文件**零改动**（`git status` 断言）。
- L3 注入 `while(true){}` 必须在 `SCRIPT_BUDGET_MS` 内被中断并报错，不得挂死。

## Risks

- `call_js` 是通用执行入口，按方法名过滤若写错（如漏掉新方法），覆盖层会作用于非数据调用。缓解：白名单而非黑名单，新增方法默认不应用。
- 覆盖层让"同一次请求的返回值"依赖一个用户可编辑的 JSON，排障时需能一眼看出"是插件的问题还是覆盖层的问题"。缓解：覆盖层生效时在诊断信息里标注 `overlay=<targetId>`。
- L3 若放开网络，等价于任意代码执行。当前按"默认不放开"设计，放开前需单独评审。
- 用户忘记关闭覆盖层会导致数据长期异常。缓解：全局启用开关 + 覆盖层文件头记录创建时间与来源。
