# Agent Note: 门禁必须能真的变红 —— 新门禁先做故障注入

Status: implemented

## Problem

本仓出现过**从构造上不可能红**的门禁：探针实现成
`final v = s._controlsFade.value; return (v, v);` —— 两个分量同一个源，
断言「顶底栏透明度相等」恒真。它「验过」了一个真实缺陷很久。

一条不会红的门禁比没有门禁更糟：它让「已验过」成为结论，从而关闭了继续排查的可能。

## Decision

任何新增或改动的门禁，交付前必须把要防的缺陷**人为还原**，确认门禁变红；
还原后仍绿 ⇒ 判定假绿 ⇒ 重写。交付报告里必须附这次读数。

**不翻案。这是硬规矩。**

## Alternatives considered

- **只跑编译 / 只跑单测就宣称通过** —— 它最强的论据是这些信号廉价且自动。
  否决理由：它们证明的是「能构建」「某条路径在受控输入下走通」，
  不证明「要防的那个缺陷会被抓住」。

- **为消掉评审意见而放宽断言 / 加 skip / 加 ignore** —— 它最强的论据是让 CI 变绿。
  否决理由：那是把缺陷藏进绿里。评审意见指出门禁是假的时，正确处置是**改成硬失败**。

## Consequences

- **收益**：「已验过」这个结论重新可信；假绿有明确的判定方法与交付要求。
- **代价与已知上限**：每条门禁多一轮「还原缺陷 → 观察变红 → 恢复」的人工操作，
  且要留下读数。确实无法在测试里观测的（如真机引擎文本输入管线）必须改用
  可稳定观测的等价判据并在文件头写明理由 —— **不许**因为测不了就写一条恒真的东西充数。
- **重访条件**：不翻案。
