# Agent Note: 文档说「用户会看到 X」，而代码里零个消费者 —— 把这条对账机械化

Status: implemented

> 前两篇同母题，**方向各不同**，本篇是第三个：
> · [一个能力位可以「声明了但永不生效」](../feature/2026-10-19-capability-bit-can-lie.md)
>   —— **声明 true 但没有方法** ⇒ 用户点了必失败
> · [CI 上「静默 skip」比「红」更危险](../process/2026-10-19-silent-skip-is-worse-than-red-in-ci.md)
>   —— **整批用例没跑但 job 绿**
> · **本篇：文档承诺了界面效果，但代码里没有任何地方读那个位**
>
> 三者共同的形态是「**形式在，事实不在**」，但被骗的对象不同：
> 用户 / CI 读者 / 文档读者。

## Problem

2026-10-20 发现 `capability-bits.md` 里 `danmaku` 那一行是谎话：

```text
文档写的：「声明 false 时 ⇒ 不显示弹幕入口（但别的源/本地弹幕仍可用）」
实际实现：全仓 Dart 侧 `capabilities.danmaku` **零命中**，
          唯一消费者是设置页源卡片上的一枚小标签：
            lib/ui/settings_page.dart:4573
              if (c.danmaku) '弹幕',
```

真跑读数（widget test，两档对照）：

```text
[PROBE] danmaku=false ⇒ capabilities.danmaku=false
[PROBE] danmaku=true  ⇒ capabilities.danmaku=true
[PROBE] 面板 widget 总数：第一次=236 第二次=236   ← 两档**完全一致**
[PROBE] DanmakuInfoData 字段：source=none match=none count=null enabled=false
        ⇒ 面板入参里根本没有那个位
```

**这条矛盾是靠「人读文档 + 人读代码」对出来的。同类还有多少？不知道。**

而本仓的规矩是：**写在散文里的规矩等于没有规矩**。
⇒ 需要机械化。

### 机械化之前，先看清最大的坑

第一版脚本抽出 **35 个「能力位」，其中 21 个是假的**：

```text
codec / drm / hdr / statusCode / json / message / retryable /
playable / finalUrl / hosts / regex / verdict / streamFlags …
```

它们不是能力位，是 `docs/PLUGINS.md` 里代码示例中的
`StreamCandidate` / 错误对象**字段**：

```js
{ url, kind, quality, codec, hdr, drm, … }
```

**21 个假孤儿把真信号淹没了。**
而「每次都报一堆」的报告等于没有报告 —— 它训练人**忽略它**。

## Decision

### ① 判据：三个「不要」+ 三个「要」

```text
❌ 「孤儿位数量必须 ≥ 1」
   → 某天全部接好 ⇒ 永远红；某天扫描器坏了 ⇒ 永远绿（0 孤儿 = 通过）
❌ 「孤儿位数量必须 == 0」
   → 孤儿可能是合法设计（danmaku 只影响一枚标签就是）
   → 会逼人"给每个位加个读取点"，那是**为门禁写代码**
❌ 「必须解析到 N 个能力位」
   → N 随文档变化，写死就是定时炸弹

✅ ① 每个文档里出现的能力位都必须被**分类**（接线 / 孤儿 / 未映射）
✅ ② 扫描器必须证明自己工作过（硬判据，坏了要红）：
       · 至少一个文档存在
       · 至少扫到 1 个 dart 文件
       · 至少解析到 1 个能力位
✅ ③ 孤儿位如实列出，**不判红**（--strict 才判）
```

⇒ ①② 防「假绿」（扫描器空转），③ 防「为门禁写代码」。
**两者都不依赖数量** ⇒ 文档里 6 个位和 14 个位，脚本都成立。

### ② 退出码必须三档，`|| true` 是错的

```text
0 = 跑完了（不管有没有孤儿）
1 = **扫描器自己坏了**（文档不存在 / 没扫到 dart / 没解析到能力位）
    ⇒ CI 必须红：这不是"发现问题"，是"检查本身失效"
2 = --strict 模式下有孤儿
```

原 CI 写法 `node ... || true` **把脚本崩了也吞掉**。
而「脚本崩了」与「孤儿位存在」是两件事：

```text
· 前者 ⇒ 本次**没有产出可信报告** ⇒ 必须红
· 后者 ⇒ 可能是合法设计 ⇒ 只警告
⇒ `|| true` 让两者都变绿 ⇒ 扫描器坏掉时**静默**，
  而那正是这条报告要防的「静默降级」。
```

### ③ 覆盖度必须显式 —— 否则「6 个全绿」会被读成「全仓都接好了」

CI 上没有兄弟目录的私库文档 ⇒ 只扫 `docs/PLUGINS.md`（6 个位），
而 `capability-bits.md` 里的 8 个位**没被查**。

```text
④ 汇总：6 个能力位（**覆盖 6/14**）— 已接线 6 / 孤儿 0 / 未映射 0
   ⚠ 未覆盖的 8 个位（本次文档里没出现 ⇒ **未检查**）：
     epg, favorites, timeshift, serverSideHistory, loginSupported, ...
```

⇒ 与「状态④ 静默」是同一个病：**跳过即无声**。

### ④ 文档名 → 代码名 的映射表（否则必误报）

```js
loginSupported: ['showLoginEntry', 'capabilities.loginSupported', ...],
```

`loginSupported` 是最典型的陷阱：直接 grep 它在 UI 层几乎零命中，
因为它被 `Capabilities.showLoginEntry => loginRequired || loginSupported`
包了一层，UI 读的是 `showLoginEntry`。

**未在表里的位会显式报告「未映射」**，不静默当作「没读取点」。

### ⑤ 排除表自检：排除项必须有依据

`KNOWN_NON_CAPABILITY`（codec/drm/hdr/…）会腐化：
若将来真出现一个**叫 `drm` 的能力位**，它会被静默吃掉。

判据：

```text
排除表里的每个名字，若在文档的 `capabilities: { ... }` 代码块里出现
⇒ 说明文档把它当**能力位**在用 ⇒ 不该在排除表里 ⇒ 红
```

## 三个正则陷阱（都是实测打出来的）

### 陷阱 1：`[^\w.]` 排除点号 ⇒ 假阴性

```js
// 本意：防 research 命中 search
new RegExp(`(^|[^\\w.])${id}([^\\w]|$)`)

// 实际：danmakuSend 被判**孤儿**，真实读取点是
lib/ui/player_page.dart:20587
  return hit?.capabilities.danmakuSend ?? false;
                   ↑ 前面是 `?.`（null-aware）⇒ 永远匹配不到
```

修正：左侧用 `[^\w]`（**允许点号**）—— 防 `research` 命中 `search`
只需词边界，不需要排除点号。

### 陷阱 2：`capabilities\s*:\s*\{([\s\S]*?)\n\s*\}` 跨块 ⇒ 假阳性

```js
// 文档里有一处**单行内联块**：
capabilities: { vod: true },
                   ↑ 这行没有 `\n  }`，于是 `[\s\S]*?` 一路滑到
                     几十行之后的**下一个** `\n  }`
   ⇒ 把 `hosts:` / `async list()` 等**块外**的键也吞进 capabilities
   ⇒ 排除表自检报「hosts 是真能力位」—— 假阳性
```

修正：**必须配平花括号**（数 `{` 到回 0），不能用正则找 `\n}`。

### 陷阱 3：`### \`name\`` 小节标题 ⇒ 把字段当能力位

小标题格式在 `PLUGINS.md` 里也用于**字段说明**（如 `### \`codec\``）。
必须先判「该小节正文是否提到能力位语境」，否则 21 个假孤儿。

## Alternatives considered

### 不做（继续靠人读文档）

**最强的理由**：这类矛盾目前只有 3 个已知案例，人工核对成本不高；
且脚本本身写了三轮才对（21 个假孤儿 → `?.` 假阴性 → 括号跨块），
说明它的维护成本可能高于收益。

**否定的原因**：

```text
「人工核对」的前提是**有人会去核对**。
而能力位文档写在私库、代码在 app 仓 —— 改一边的人通常看不到另一边。
danmaku 那个谎话正是在这种割裂下躺了几天才被发现。
⇒ 不要求它判红，只要求它**每次都打印**，成本就低到可接受。
```

### 做成硬门禁（孤儿位也算红）

**最强的理由**：软报告没人看；硬门禁才有强制力。

**否定的原因**：

```text
孤儿可能是**合法设计**（danmaku 只影响一枚标签 —— 那是对的，
面板可用性由 DanmakuFeedContext 决定，那个判据比能力位更准）。
做成硬门禁会逼人去"给每个位加个读取点"——
那是**为门禁写代码**，会让代码变差以取悦门禁。
⇒ 先软跑一段时间，看孤儿位都是什么性质，再决定要不要硬。
```

### 用正则找 `capabilities { ... }` 块（不做括号配平）

**最强的理由**：正则更短、更好读。

**否定的原因**：实测被单行内联块打回（见陷阱 2）。配平只需十几行。

## Consequences

**收益**

```text
· 14 个能力位全部有读取点，覆盖度显式（本地 14/14，CI 6/14）
· 「零消费者」这个事实变成**持续可见**，而不是等某天有人恰好读文档
· 扫描器坏了会红（不会静默）；孤儿位只警告（不逼人写代码）
· 排除表自检防它腐化
```

**代价**

```text
· 脚本对文档格式敏感：改了速查表结构 / 标题格式，抽取规则要同步
  ⇒ 已用「解析不到能力位 ⇒ 红」兜底（扫描器失效不会被误读成"全绿"）
· CI 只覆盖 docs/PLUGINS.md 的 6 个位，私库那 8 个仍要本地跑
  ⇒ 已在汇总行显式写出「覆盖 6/14」+ 列出未覆盖清单
· 维护成本在三轮返工里已经付过了（21 假孤儿 / `?.` / 括号跨块）
```

## Testing

```text
本地跑（14 位）：✅ 覆盖 14/14 — 已接线 14 / 孤儿 0 / 未映射 0    exit 0
CI 模拟（6 位）：✅ 覆盖 6/14 — 已接线 6 / 孤儿 0 / 未映射 0     exit 0
                  ⚠ 未覆盖的 8 个位：epg, favorites, timeshift, ...

注入 A（文档加假能力位 fakeBit）  ⇒ ⚠ 孤儿 1 个，未映射 1 个    exit 0（软）
注入 B（注释掉 player_page.dart 真实读取点）
                                  ⇒ ⚠ danmakuSend 孤儿 1 个    exit 0（软）
注入 C（把真能力位 danmaku 塞进排除表）
                                  ⇒ ✗ 排除表里混进了真能力位    exit 1（红）
注入 D（--docs 指向不存在的文件）  ⇒ ✗ 扫描器自身失效           exit 1（红）
CI job 模拟：正常 ⇒ 绿；扫描器失效 ⇒ ::error:: + exit 1
```

**判据覆盖面**：孤儿（软）/ 未映射（软）/ 排除表腐化（硬）/ 扫描器失效（硬）
—— 四类都有对应的注入，且软硬边界与设计意图一致。
