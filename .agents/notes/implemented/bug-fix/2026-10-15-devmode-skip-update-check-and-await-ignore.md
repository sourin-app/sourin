# Agent Note: 开发模式跳过启动更新检查；「忽略此版本」必须等落盘

Status: implemented

## Problem

两条**现象相同**（都会弹更新窗）但成因与修法完全不同的缺陷。合并处理会互相掩盖。

```text
① 开发版每起一次就查一次、弹一次更新窗 —— 对开发者恒为噪声，没有一次有用。
② 用户点「忽略此版本」后窗又弹 —— 看起来像没记住。
```

## Decision

两条独立规则，**不要合并**：

```text
① 开发/探针构建（DATA_DIR_OVERRIDE 非空）⇒ 启动**不做**更新检查。
   关于页的「检查更新」手动入口照旧 —— 要验更新流程自己点一下。
② 「忽略此版本」必须**写完盘再关窗**（ignoreVersion 返回 Future，调用方 await）。
```

## Alternatives considered

- **用 `kDebugMode` 判开发模式** —— 它最强的论据是语义直白。
  否决理由：开发 / 探针构建全是 release 语义，判不出来。

- **开发模式下把「24 小时」调短，或给空目录塞一个假的 lastCheckAt** ——
  它最强的论据是改动面小、只碰配置值。否决理由：那是**掩盖**成因 ——
  `-Dev` 用的是一间空数据目录，没有 `appupdate.lastCheckAt`，节流形同不存在；
  下次目录被清空照样复发。

- **只补一句 `unawaited(flush())`** —— 它最强的论据是修法最小。
  否决理由：那只保证「开始写」，不保证「写完」。`UiPrefs.set()` 只改内存，
  真正写盘的是 300ms 去抖定时器，进程比它先走偏好就丢。
  本轮的回归测试正是靠这一点先变红，才把 `await` 逼出来的。

- **在开发模式下把「忽略」写进真实数据目录** —— 违反用户数据铁律。

## Consequences

- **收益**：开发者不再被恒噪声打扰；用户的「忽略」在关窗即退的场景下也不丢。
- **代价与已知上限**：开发版默认不验更新链路，需要手动点「检查更新」；
  这条闸门是**按数据目录**判的，不是按构建模式 —— 用真实数据目录跑 Release 构建时，
  启动检查照常进行。
- **重访条件**：第 ① 条若将来需要「开发时也自动验更新链路」，应改为**显式开关**
  （如 `-Dev -CheckUpdate`），而不是把闸门拿掉。第 ② 条不翻案。
