# Agent Note: 弹幕「不能发」的说明搬到发现点，且不依赖是否绑定某一路

Status: implemented

## Problem

弹幕设置面板里那句「此源不能发弹幕」的说明，改前的条件是
`biliBound && !canSendDanmaku`（**已绑定某一路** 且 源不支持发送）。

两种情况的用户观感完全不同：

```text
源不支持 + 已绑定某一路  → 有一行「本片源不支持发送弹幕（只能看）」，能看懂
源不支持 + 没绑定某一路  → 什么都不说：只看到「本片源没有提供」+ 没有发送框
                          用户分不清「这一路没内容」还是「这源根本发不了」
```

R6 已裁决过同一类问题：**入口可以不给，但不能让用户面对一片空白去猜**。
这里就是那个「说了但只在半条路径上说」的形态 —— 挂在「是否绑定」这个
**与发送能力无关**的条件上。

## Decision

条件改成只看能力：`if (!canSendDanmaku)`，文案同时换成**给「能做什么」**：

```text
弹幕可以看、调样式、合并多路来源；发送只在支持发送的片源里提供
```

原因必须指向**片源**。不许写成网络 / 登录 / 设置 / 出错 —— 那会把用户
指向不存在的问题（AGENTS §8「只到结论不到原因」的教训）。

## Alternatives considered

- **保持原样，只在已绑定时解释** —— 论据是「没绑定时用户看到的是『本片源没有提供』，
  已经算说了」。否决：那句话讲的是**这一路有没有弹幕内容**，不是**这个源能不能发**；
  两个事实不同，用一句话替代另一句就是"说了但说不清"。
- **把说明搬到发送框原来的位置（空白处放一行）** —— 论据是发现点最近。
  否决：那里在不支持时本来就没有控件，凭空多一行常驻文字会挤掉面板里
  真正可用的设置项；现有那句说明的位置（能力相关段落）已经是这个面板里
  「解释为什么没有」的固定落点。
- **对不支持发送的源直接隐藏整个「发送」分区** —— 论据是界面更干净。
  否决：用户就再也看不到"这个源不能发"这件事，等于把 R6 要修的形态
  从"看不懂的 !" 换成"根本不知道有这回事"。

## Consequences

- **收益**：无论是否绑定某一路，用户在同一处都能读到「为什么没有发送框」，
  且这句话给的是可执行信息（可以去支持发送的片源发）。
- **代价与已知上限**：多一行常驻文案；对**能发**的源不显示（条件是同一判据，
  不会两头都出现）。文案里没有站点名（站名门禁 `t98` 覆盖全仓文档与源码）。
- **门禁**：`test/zz_t66_danmaku_panel_semantics_test.dart` ⑤ 组三条成对断言
  （能发 ⇒ 无此句；不能发+已绑定 ⇒ 有此句；不能发+未绑定 ⇒ 仍要此句）。
  第三条正是"老条件"的反例：条件改回 `biliBound && …` 时**只有它**变红。
- **重访条件**：若将来给"能发/不能发"换成三态（能发 / 需登录才能发 / 源不支持），
  这行文案要按态拆分 —— 现在把"需登录"也归到"发送只在支持发送的片源里提供"，
  对"源支持但没登录"的情形不够准确（那条路径由发送时的 `unauthorized` 分类兜底）。
