# Agent Note: 门禁的 git 调用必须带 `-z` —— 否则中文路径静默逃检

Status: implemented

> 同域：本篇与
> [2026-10-18-gate-reads-worktree-not-blob.md](./2026-10-18-gate-reads-worktree-not-blob.md)
> 同源 —— 都是「门禁读错了对象」。区别是那篇读错了**版本**（工作区 vs blob），
> 本篇读错了**编码**（转义后 vs 原始路径）。总原则见
> [2026-10-12-gates-must-be-able-to-fail.md](../process/2026-10-12-gates-must-be-able-to-fail.md)。

## Problem

门禁脚本用 `git diff --name-status` 拿变更文件列表，然后按路径前缀判断
「这个文件算不算源码」。不带 `-z` 时，git 会对非 ASCII 路径做 C 风格转义
并加引号：

```text
A  "lib/\344\270\255\346\226\207.js"
```

于是 `startsWith('lib/')` 直接失败 ⇒ **中文路径的源码改动被静默放行**。

实测确认（不是理论风险）：一个叫 `lib/中文.js` 的文件改了代码，
门禁打印「改动未命中受管路径，无需笔记」并 `exit 0`。

反向同样坏：笔记文件名若是中文，`endsWith('.md')` 与
`startsWith('.agents/notes/')` 也会失败 ⇒ 人会看到「明明写了笔记却被拦」。

## Decision

所有 `git diff` 调用改用 `-z`（NUL 分隔），并用专门的解析函数读记录。

```js
git(['diff', '--no-ext-diff', '--no-textconv', '--no-renames',
     '--ignore-submodules=none', '--name-status', '-z', ...args, '--'])
```

`-z` 的记录格式是 `状态\0路径\0`；改名是 `R100\0旧路径\0新路径\0`，
取新路径（它才是当前存在的那个）。

**must**：同时钉住其余四个 flag。它们来自 `deepseek-harness` 的
`change-scope.ts`，逐条都有理由：

| flag | 防什么 |
|---|---|
| `--no-ext-diff` | `.gitattributes` 配了外部 diff 驱动 |
| `--no-textconv` | `.gitattributes` 配了 textconv，文件内容被换掉 |
| `--no-renames` | 改名检测受 `diff.renameLimit` 影响，大仓库行为不确定 |
| `--ignore-submodules=none` | 本地 `submodule.<name>.ignore = all` 让变更消失 |
| 结尾 `--` | 防参数被当成路径 |

**must**：`maxBuffer` 显式放大到 64MB。`spawnSync` 默认 1MB，大仓库
`git ls-files` 会 ENOBUFS。实测超限时 `status` 为 `null`（不会假绿，
会走失败分支），但会误报「无法判定」，让门禁在大仓库上不可用。

## Alternatives considered

- **不用 `-z`，改用 `-c core.quotepath=false`** — 一行配置就能让 git
  输出原始 UTF-8 路径，比改解析函数简单得多。否掉：它依赖调用方记得
  每次都在命令行加 `-c`，漏一次就回到静默逃检；而 `-z` 是**数据格式**
  层面的保证，解析端不会「忘记」。而且路径里若真有换行，换行分隔仍会坏，
  NUL 分隔不会。
- **不用 `-z`，把转义后的路径先 unescape 再判断** — 不必改 diff 调用。
  否掉：需要自己实现 git 的 C 风格转义解码（`\ooo` 八进制、`\t`、`\"` 等），
  等于重造 git 的编码逻辑；实现一旦有偏差就又是静默漏检，而这类偏差
  很难被日常使用发现。
- **只加 `-z`，不加其余四个 flag** — 少改一点。否掉：其余四个同样是
  「有人特意配置过才会触发」的防御。我最初判定它们「不必要」，
  理由是「我没能构造出受影响的场景」——那是**错误的判据**：
  防御性 flag 的价值恰恰在于防罕见配置，构造不出来不等于不会发生。
  而 `-z` 这一条一测就是真会踩到的，说明这类判断不能靠「想不出场景」。
- **改成用 `git status --porcelain -z` 而不是 `git diff`** — `status`
  天然带 `-z`。否掉：`status` 描述的是工作区状态，而门禁需要的是
  「某个提交/暂存区相对基准的变更」；用 `status` 无法表达 `sha^!` 这种
  单提交范围，会让逐提交检查实现不了。
- **假定仓库里不会有中文路径** — 零成本。否掉：本仓的笔记文件名、
  代码注释、文档全是中文，出现中文文件名只是时间问题；而且这是
  「假定用户不会做某事」式的防御，一旦不成立就静默失效。

## Consequences

- **收益**：中文/空格路径的源码改动第一次能被正确拦下。实测从
  「静默放行」变成「点名报错」。
- **收益**：反向也修好了 —— 中文文件名的笔记现在能被认作「带了笔记」，
  不会再出现「明明写了却被拦」。
- **收益**：其余四个 flag + `maxBuffer` 让判定在**大仓库**与
  **有人改过 git 配置**的机器上也稳定可复现。
- **代价**：解析逻辑复杂了一点（NUL 分隔 + 状态码 + 改名双路径）。
  这份复杂度换来的是编码正确性，值得。
- **代价**：`maxBuffer` 64MB 意味着单次 git 输出可能占 64MB 内存。
  在极端大仓库上仍是上限，超了会报「无法判定」而不是静默截断 ——
  方向是安全的。
- **已知缺口**：`-z` 解决了路径编码，但没解决**路径大小写**问题。
  Windows/macOS 上 `Lib/X.js` 与 `lib/x.js` 是同一文件，前缀判断
  可能漏。本次没处理（Linux CI 上不出现）。
  重访信号：Windows 开发机上出现「改了代码但门禁说没改」。
- **已知缺口**：改名被 `--no-renames` 强制表现为「删旧 + 增新」，
  所以「改名一篇笔记」在 supersession 检查里**不会**被当作新增
  （`A` 会被识别，但改名走的是 `D`+`A`，其中 `A` 仍会被计入）。
  这个行为是刻意的（改名后的笔记确实是一篇「新路径的笔记」），
  但值得知道。

## Verification

```sh
node --test tools/notes-coverage.test.mjs   # 21 项（新增 2 项中文路径）
```

两条新增断言：

| 场景 | 期望 |
|---|---|
| `lib/中文模块.js` 改动无笔记 | 红，且诊断里出现**原始**中文路径 |
| `lib/中文模块.js` + `2026-01-01-中文笔记.md` | 绿 |

**故障注入（真红）**：把 `-z` 去掉、退回换行分隔解析
⇒ 1 项失败。证明这两条断言确实在守 `-z`，不是恒绿。
