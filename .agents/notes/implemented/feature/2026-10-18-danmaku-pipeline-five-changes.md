# Agent Note: 弹幕体系五处改造 —— 发送入口、手动绑定、来源聚合、压缩解码、信息透明

Status: implemented

> 同域：[2026-10-17-player-danmaku-send-entry.md](./2026-10-17-player-danmaku-send-entry.md)
> 那篇定下「不支持发送就不显示入口」这条判据；本篇在其之上做了
> 入口位置（浮层→底栏）与来源聚合等五处改造，**没有推翻那条判据**。
> 另见提案 [登录态同步](../../../proposed/feature/2026-10-18-login-state-sync-and-export.md)：
> 插件侧的 danmakuSend 实现仍未落地，是本篇「未做」项的下游。

## Problem

本轮 Owner 对弹幕提了多条反馈，分散在发送入口、绑定策略、来源聚合、
错误可见性四件事上。它们表面是五个独立需求，实际共有一个根因：

```text
弹幕这条链路的**决策点是分散的**：
  · 发送栏是浮层，跟着控制条一起显隐 ⇒ 想发时找不到
  · 起播时自动绑定外部源 ⇒ 用户不知道自己的弹幕从哪来
  · 插件弹幕与「本片源自带」各走各的 ⇒ 手动绑定后插件那份就丢了
  · 宿主解不开压缩响应 ⇒ 一个源整个失效，日志里只有一句英文异常
  · 面板只显示条数，不显示「哪个源、多久前、上游给了多少」
```

## Decision

### ① 发送栏从浮层移进底栏，不支持时**整块不渲染**

`aedc29c`：`player_bottom_bar.dart` 新增 329 行，`player_page.dart` 净减 ~700 行
（删除原浮层实现）。

判据在**能力声明**，不在运行时探测：
```text
danmakuSendAllowed(providers, id)  ← 只看插件声明的 capabilities.danmakuSend
```
理由：探测要发一次真请求，而用户只是打开播放页时不该产生写操作。

### ② 取消起播自动绑定，只能手动绑

`25cd277`：起播不再自动挑一个外部源。

**为什么这条重要**：自动绑定会让用户以为自己看到的弹幕来自本片，
实际来自某个第三方源；而 Owner 明确要求「弹幕只能手动绑」。

### ③ 手动绑定外部源后，插件弹幕仍然聚合进来

`4aeb79a`：原来「绑了外部源」就只走外部源，插件那份被跳过。

★ 这不是 bug 修复那么简单 —— 它改变了「来源」的语义：
```text
改前：选一个源 = 只用那一个
改后：外部源与插件源**并存**，去重后合并
```

### ④ 宿主支持 `raw-deflate` 压缩响应

`9ca4076`：Rust 侧 `plugins/mod.rs` +214 行，`Cargo.toml` 加依赖。

**根因**：某些源的接口返回 `Content-Encoding: deflate` 的**裸 deflate**
（非 zlib 包装），宿主原来的解码器直接失败 ⇒ 该源在弹幕这条路上整个不可用，
而错误信息只有一句英文异常，看不出是压缩问题。

### ⑤ 信息面板显示「上游只返回了多少」

`c008a13`：面板新增 124 行，把「上游给的条数」与「最终渲染的条数」分开显示。

★ 这一条针对的是一类**用户无法自证**的困惑：
「为什么这部番弹幕这么少」—— 可能是上游就只有 2 条，也可能是我们丢了一条。
不显示两个数字，用户和开发者都无法区分。

### ⑥ 启动期一次探测有总耗时上界

`cacb83d`：给「一次探测」加总耗时上限，并加门禁用测试钉住
「dan-api 不许阻塞启动」。

**为什么需要**：探测是串行的，某个源无响应时会把启动拖到用户以为卡死。

## Alternatives considered

- **发送栏保留浮层，只改成常驻显示** —— 它最强的论据是改动最小，
  浮层实现已在，只需改显隐条件。
  否决理由：浮层会遮住画面底部（正是弹幕最密的位置），
  且与底栏的显隐逻辑互相打架（底栏收起时浮层该不该留？没有好答案）。

- **自动绑定 + UI 上标注来源** —— 它最强的论据是省用户一次操作，
  且「标注了来源」已经解决了「不知道从哪来」的问题。
  否决理由：Owner 明确要求「弹幕只能手动绑」。标注不等于用户同意，
  而且自动绑定会在用户没注意时产生一次外部请求。

- **外部源与插件源二选一，而不是合并** —— 它最强的论据是语义简单，
  「我选了哪个就是哪个」，不会出现「我要的那条到底算哪个源」。
  否决理由：实测中插件提供的是**本片源自带**的弹幕，与外部源的内容互补，
  二选一会让用户固定损失一部分。

- **压缩解码失败就当该源没有弹幕** —— 它最强的论据是不引入新依赖，
  少一个攻击面。
  否决理由：那等于把「源站用了常见的 HTTP 压缩」judged 成「这个源没弹幕」，
  用户永远查不出原因。属于本仓反复禁止的「静默降级」。

## Consequences

- **收益**：发送入口随手可达；来源语义从「二选一」变成「可叠加」；
  一类整源失效被修好；面板能自证「少是上游少，不是我们丢」。
- **代价**：
  · 来源合并带来新的复杂度（去重规则必须明确，否则同一条弹幕出现两次）
  · 新增 deflate 依赖（`Cargo.toml`），供应链面变大
  · 探测总耗时上界意味着**慢源会被砍掉**，用户可能看到「某个源没出弹幕」——
    这是刻意的取舍，已在门禁里写明理由
- **未做**：插件侧的 `danmakuSend()` 实现仍未落地（见计划 §十六）。
  应用侧的调用链、开关判定、UI 渲染、门禁均已就位，缺的是对面那句实现。
- **重访条件**：当「来源可叠加」出现重复弹幕投诉时，需要回头收紧去重规则；
  当启动探测被砍掉的源变多时，需要重新定这个上界。
