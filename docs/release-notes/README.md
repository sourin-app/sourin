# 人工确认稿（发版时「本版更新」的来源）

> 2026-10-22 建立。适用版本：v1.4.0-rc4 起。

## 这是什么

发版时 GitHub Release 正文里的「本版更新」这一节，默认由
`tools/gen_release_notes.py` 从 git 历史**自动归纳**。

自动归纳在提交标题写得规矩时很好用；但提交标题是给开发看的，
一旦写成 `fix(settings): 健康检测进度走独立 notifier` 这类工程黑话，
自动路径会**一条都产不出来**（实测 v1.4.0-rc3..HEAD 区间 16 条提交里
7 条真修复全灭）⇒ CI 的「本版更新至少一条 bullet」守卫会红 ⇒ **发不出去**。

本目录就是那条备用通道：**写一份人写的稿子，CI 优先用它。**

## 怎么用

```text
1. 在本目录建一份文件，文件名 = 这次的 tag（例：v1.4.0-rc4.md）
2. 内容 = 「本版更新」这一节的正文（只写这一节，别抄模板）
3. 提交并合进 main
4. Actions → 构建 → Run workflow，release_tag 填同一个 tag
   ⇒ CI 发现 docs/release-notes/<TAG>.md 存在 ⇒ 用它，不再自动归纳
```

稿子**没有**就照旧走自动归纳 —— 默认路径一个字没变。

## 稿子的格式要求（门禁会逐条检查）

| 要求 | 原因 |
|---|---|
| 至少一条 `- ` 开头的条目（`- - -` 这类分隔线**不算**条目） | 漏写 ⇒ 那一版又变成「默认说明」 |
| 不许有空条目（只有 `-` 没有内容） | 用户会看到一条什么都没有的项目符号 |
| 不许有表格 / 图片 / HTML 标签 / 围栏代码块 / 分隔线（`---`、`- - -`、`***`、`___`） | 客户端渲染器不支持这些，会原样漏给用户；分隔线还会截断这一节 |
| 不许有 HTML 注释（`<!-- -->`） | 渲染器**不剥**注释，它会被原样显示给用户 |
| 不许残留 `{{...}}` / `__VERSION__` | 占位符会原样出现在 Release 正文里 |
| 不许出现开发用语（门禁 / 探针 / 修复 / 缺陷 / Owner / 踩坑…） | 用户可见文案不许用工程黑话（`docs/AGENTS.md` §4） |
| 不许出现具体网站名 | 仓库硬约束 |
| 英文词只许是用户认识的那批（格式名、产品名白名单） | 「Material」「notifier」这类用户读不懂 |
| 分类小标题只许四个：新增 / 改进 / 修复 / 调整 | 与自动路径的分类一致；**其它小标题会被直接拒掉** |
| 小标题不许是空的（`###` 后面什么都不写） | 会渲染成一节空白 |

小标题里的「修复」**不算**开发用语 —— 那是分类名。

**唯一例外**：「健康检测」是设置页上那个按钮的正式叫法，允许出现
（但它里面的「检测」两个字在别的语境里是工程词，别单独用）。

校验由 `tools/gen_release_notes.py` 的 `validate_manual_notes()` 负责，
CI 门禁 `test/zz_t1022_manual_release_notes_gate_test.dart` **调用它**，
不在 Dart 里复刻一份规则（复刻必然漂移）。

报错**带行号，且行号对原文件**（不剥注释、不跳空行）—— 人工稿是人写的，
报错指错行比报错本身更坑人。

本地自查：

```bash
python tools/gen_release_notes.py --manual docs/release-notes/<TAG>.md --out /tmp/notes.md
```

退出码 0 = 合格；1 = 报错（每条错误带行号）。

## 一份稿子长什么样

```markdown
### 修复

- 健康检测页的进度条现在会实时走动，不再一直停在「0 / 26」。

### 改进

- 界面滚动到底或回顶时的手感更稳。
```
