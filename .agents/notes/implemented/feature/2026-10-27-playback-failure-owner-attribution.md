# Agent Note: 播放失败的「归属」维度 —— 是插件还是播放器本体

Status: implemented

## Problem

七档 `PlaybackFailureKind`（[2026-10-18-playback-failure-classify-http-first](../bug-fix/2026-10-18-playback-failure-classify-http-first.md)）
已经回答了「**发生了什么**」，但 Owner 拿到那句「这一条流取不到」之后仍然不知道**该找谁**：

```text
Owner 原话（2026-10-27，逐字）：
  播放失败定位与诊断，这个如果播放失败应该具体是谁的问题，
  在界面上显示出来是插件还是播放器本体的问题
```

「取不到这条流」在物理上对应至少三个完全不同的施动方 —— 插件没给地址、我们的内置代理转发失败、
源站把连接掐了 —— 而当时的界面把它们**说成同一句话**。

## Decision

在归因函数旁边新增**正交的第二维** `PlaybackFailureOwner`，由**纯函数** `ownerOf(kind)` 推出：

```text
plugin   插件侧（源解析失败 / 空列表 / 插件抛错）
player   播放器本体（取到流但本机解不了）
service  内置播放服务或网络（环回取不到、等太久）
remote   源站网络侧（限流 / 5xx / 连不上）
unknown  说不清
```

七档到归属的映射（`lib/core/sourin_api.dart` 的 `ownerOf`，**唯一映射表**）：

| 档 | 归属 | 判据理由 |
| --- | --- | --- |
| `source` | **plugin** | 插件真实取流失败 / 返回空列表 |
| `proxy` | **service** | 发生在**内置代理**那一段（环回被拒 / 转发失败） |
| `timeout` | **service** | 同样发生在内置代理那一段（等首字节超时） |
| `decode` | **player** | 取到了流，本机（libmpv）解不了 |
| `permission` | **unknown** | 见下：既非播放器也非插件的错 |
| `network` | **remote** | 源站限流 / 5xx / 连不上 |
| `unknown` | **unknown** | 归不到任何一类 |

三条**必须**守住的纪律：

1. `proxy` / `timeout` **never** 判成 `plugin`。这两个档的物理位置在**我们自己的**代理进程里；
   推给插件会让用户去换一个本来没问题的源（旧08「不要把代理的问题说成插件的问题」的延续）。
2. `permission` **never** 判成 `player` 或 `plugin`。源站要会员/地区限制时，播放器没错
   （它没被要求解码），插件也没错（它如实转述了源站的拒绝）。判成 `player` 会把用户引去查解码器，
   判成 `plugin` 会冤枉插件 —— **如实说"说不清"是唯一不误导的选项**。
3. `failure == null`（老路径 / 探针注入的裸串）**never** 画归属。归属判断错了比不显示更糟。

界面：`_OwnerBadge` 画在 headline **之下**、正文 **之上**。

```text
顺序 = 用户心里的三个问题：
  ① 发生了什么   ← headline（旧08）
  ② 这是谁的锅   ← 本行（本项）
  ③ 原文怎么说   ← 正文（旧08）
归属是"一句可执行的分诊"，必须在细节之前；反过来是"先读一堆原文再告诉你是谁的问题"。
```

## Alternatives considered

- **把归属并进 `PlaybackFailureKind`（扩成十几档）** —— 它最强的论据是"一个维度更好维护"。
  否决理由：`kind` 描述**事件**，归属描述**施动方**，两者不是同一根轴 ——
  `proxy` 与 `timeout` 是两个事件但同一个归属，合并会立刻产生同义档。
  正交两维还让"新增档位时归属必须表态"变成可机械检查的事（见下）。

- **在 UI 里按 kind 现写一个 switch** —— 它最强的论据是"离渲染近，改起来直观"。
  否决理由：本仓铁律「判据只有一个来源」。两份 switch 迟早漂移，
  而且纯函数能单测（不构造 `PlaybackFailure` 就能逐档断言）。

- **`permission` 判给 `player`（"播放器放不出来"）** —— 它最强的论据是用户在客户端里
  唯一能操作的就是播放器。
  否决理由：这是**把源站的商务限制说成客户端的缺陷**。用户照这个方向排查永远查不出来，
  而正确的动作是换源（或接受源站限制）。宁可说"说不清"。

- **`permission` 判给 `plugin`（"插件没给能播的地址"）** —— 它最强的论据是表面上看
  确实是插件没能给出可播地址。
  否决理由：插件对源站的 403 无能为力，判成插件缺陷会驱动一条**不可能有结果**的修复路径。

- **不做这一维，只把正文写得更详细** —— 它最强的论据是零新增概念。
  否决理由：Owner 明确要的是"在界面上显示出来是插件还是播放器本体的问题"，
  即**要一个结论**，不是更多细节。细节越多，越需要一句话先分诊。

## Consequences

- **收益**：用户拿到的不再是"这一条流取不到"，而是"插件侧问题 / 播放服务·网络问题 /
  播放器问题 / 源站问题 / 说不清是哪一侧"，直接对应一个可执行动作（换源 / 重试 / 换线路 / 等一会）。
- **代价**：归属是**恒定映射**，不感知上下文。例如同一个 `proxy` 档，真实原因可能是代理挂了
  也可能是这一条流特别慢 —— 归属只说"这一段是我们的"，不说"是谁的 bug"。
  这是刻意的上限：**归属的价值在排除一大片方向，不在定位到行**。
- **`permission ⇒ unknown` 的代价**：用户在这一档拿不到"该找谁"。这是**有意**的取舍 ——
  冤枉一个施动方比不给结论更糟（它会让用户去查一个不存在的问题）。
- **重访条件**：若 Owner 反馈"说不清"太频繁或太无用，应先回到**判据层**
  （能不能把 `permission` 拆得更细），而不是在归属层硬塞一个施动方。
