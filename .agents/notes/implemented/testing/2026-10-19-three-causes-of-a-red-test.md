# Agent Note: 红测试的三种成因 —— 断言漂移 / 仪器失效 / 真产品缺陷

Status: implemented

Independent: 与本仓其它 testing 笔记的不同 —— 那几篇讲**单条判据**的对错
（[恒绿断言的四种形态](../testing/2026-10-19-four-shapes-of-always-green-assertions.md)、
[固定字符窗口](2026-10-19-source-scan-judge-should-not-use-fixed-window.md)、
[删恒真断言](2026-10-19-delete-the-constant-true-assertion.md)）。
本篇讲**分类**：同一条红，处置方式完全不同，混淆会做错事。

## Problem

本轮全量从 `-43` 降到 `-25`，过程中反复遇到同一个问题：
**看到一条红，不知道该改产品、改测试、还是登记为仪器失效。**

把手上 `-25` 条按成因分类后，发现**三类混在一起**
⇒ 若不分类，最可能的误判是「把仪器失效当成产品缺陷去修产品」。

### 实测的三类

| 类别 | 判据 | 该动什么 | 实例（本轮） |
|---|---|---|---|
| **① 断言漂移** | 产品**有意**改了写法，断言还认旧形态 | **只改测试** | 7 条：`InkWell`→`_GlassTapSurface`、`TextButton`→`AppTextButton`、`Tooltip`→`AppTooltip` |
| **② 仪器失效** | 断言的前提**不再成立**，但产品行为是对的 | **重设计仪器**，不是改断言 | 4 条：`shelfLoads` 恒 0 |
| **③ 真产品缺陷** | 产品确实错了 | 改产品 | 1 条：5 处裸 `CircularProgressIndicator` |

## Decision

### ① 断言漂移：只改测试，且**必须先证明产品那次改动是有意的**

```text
★ 判据：那个新写法**更符合本仓规范**，还是**更差**？
  · TextButton → AppTextButton（自建，为摘掉 material_ui）
    ⇒ 更符合 ⇒ 改断言
  · 若是产品退化成了更差的写法 ⇒ **不许改断言**，要报给 Owner
★ 依据要看**文件头原文**，不是看类名：
  lib/design/widgets/app_text_button.dart:1-4
    「自建按钮 —— 取代 Material 的 TextButton / ElevatedButton」
    「实测用法（37 个文件用 TextButton）… 只覆盖这一种形态」
```

★ **不许只换类型名**：本轮他额外加了

```dart
expect(widget<AppTextButton>(mgrBtn).onPressed, isNotNull)
```

理由：断言本意是「入口能点」，只认 `byType(AppTextButton)`
会把 `onPressed: null` 这种**真退化**放过去。

### ② 仪器失效：**登记，不顺手修**

`test/t36_cache_refresh_test.dart` 那 4 条（①切tab ×2 / ②pop回 / ②失败重试）：

```text
仪器（t36:95）  shelfLoads = [SHELF] 行数 ~/ 3
产品（my_shelf.dart:550 注释原文）
  「成功的 load() **什么都不打印**（只有失败路径有 `[SHELF] ...失败`）」
实测输出全是  Expected: greaterThan(0) / Actual: 0
```

⇒ `[SHELF]` 打印点全在「切 tab」与「各种失败」
（`:557 / :662 / :668 / :674 / :792 / :1121`）
⇒ **成功的 `load()` 一行不打** ⇒ `~/3` 的前提已不成立 ⇒ 计数恒 0
⇒ ⇒ ★ **这 4 条红不代表产品有问题**，只代表仪器坏了。

★ 而且 `my_shelf.dart:721` 的注释还写着「÷3 = load() 调用次数」
  ⇒ **注释与实现已经不符**（本轮第 N 次「注释比行号更会骗人」）。

⇒ **不顺手修**，理由：修它要改仪器语义（让 `load()` 有可数的成功信号）
  或加产品打印 ⇒ **那是判据重写**，超出「只修漂移」的范围。

### ③ 真产品缺陷：改产品，但**先确认不是误报**

★ 本轮我在这里出过一次错：

```text
我说「全量 -31 里唯一那条真产品违规」——
复核指出：zz_t64 报的两处都是**误报**
  settings_page.dart 的 1 处在**注释**里（:510 是 ///）
  danmaku_settings_dialog 计数 0（已迁走）
⇒ 我看到门禁报 settings_page 有违规，没核它是注释里的那处。
★ 已独立核实并承认：**本轮 0 条真产品违规**（唯一那条已在上一个提交修掉）。
```

## Alternatives considered

**A. 把 ② 那 4 条红也「顺手修掉」——改成不断言。**
最强理由：红数归零，看着干净。
否决理由：**那是把仪器失效伪装成"已修"** ——
下一个人会以为那 4 个功能被验证过了，而它们其实**根本没被验证**。
⇒ 正确做法是登记为「已知仪器失效，判据待重设计」。

**B. 修仪器（让产品在成功路径也打一行 `[SHELF]`）。**
最强理由：一次性把 4 条红变成真绿。
否决理由：**改产品行为只为迁就测试仪器**，且要设计一个不会在 release
构建里白刷屏的 tag。⇒ 该由专门一轮做，并给出性能预算。

**C. 把仪器改成一个不依赖日志的显式计数器。**
最强理由：日志耦合是根本问题。
否决理由：更彻底但改动更大。
★ 这是 B 的正确形态 —— 但都属「判据重设计」，超出本轮。

## Consequences

**★ 全量红数的**真实含义**变了**

```text
-43（轮前） → -25（本轮）
  其中：漂移 -7（已修） / 真缺陷 -1（已修） / 仪器失效 -4（登记未修）
  / 基线既有其余 -13
⇒ ★ 「红数下降」不能单独作为交付指标 ——
  这次 -43 → -25 里，只有 8 条是「问题被解决」，
  其余要靠分类才知道红的是什么。
```

**★ 一条可迁移的判据**

```text
看到一条红，先问：**它的输出形态像不像「恒定」？**
  Actual 恒为 0 / 恒为 1 / 恒为同一个数 ⇒ 先怀疑**仪器失效**，不是产品
  Actual 随输入变化 ⇒ 更可能是真缺陷或断言漂移

本轮两例：
  Actual 恒 0  ⇒ 仪器失效（[SHELF] 计数）
  Actual 恒 1  ⇒ ★ 仪器共性噪声（AnimatedBuilder 每帧重建一次）
⇒ 这条判据两次都指向「先怀疑仪器」，而两次的处置完全不同
   （一次要重设计仪器，一次只要放宽阈值 + 写清解释）。
```

**★ 分类必须写进 plan，否则下一个人会重做一遍**

已在 `docs/notes/plan-round-66.md` 登记那 4 条的根因与修法方向。

**已知上限**

```text
· 本轮的「有意改动」判定基于**文件头注释**（自建组件取代 material）。
  若某次产品改动没有留下这样的注释，就只能靠 diff 判断意图
  ⇒ 那时应把判断权交回 Owner，而不是默认「产品是对的」。
· 那 4 条仪器失效**未修**，它们仍会出现在全量红数里。
  ⇒ 读全量红数的人必须知道这一点，否则会误判产品健康度。
```

**何时该翻案**

```text
· 若下一轮把 `[SHELF]` 改成显式计数器，这篇的 ② 应当关闭，
  并把「分类方法」保留（它仍然适用于其它仪器）。
· 若本仓将来要求「全量测试零红」作为交付门槛，
  必须在 CI 里把「已知仪器失效」做成一个**显式登记**而非注释 ——
  否则要么被迫删断言，要么被迫修产品。
```
