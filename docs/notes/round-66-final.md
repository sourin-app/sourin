## 一、数字（可复跑）

### 「本轮」的边界定义（强制）

```bash
# 本轮 = <第一个带轮次标记的提交>^..HEAD
git log --oneline 4fda18c^..HEAD | wc -l
⇒ 74
```

`4fda18c` = 「docs(round-66): 补第 66 轮计划」= 第一个 round-66 标记。

**❌ 不要用这些方式**（实测偏差）

| 方式 | 问题 | 实测 |
|---|---|---|
| `--since="2026-10-18 00:00"` | 卷进上一轮收尾 | **102**（多 28） |
| `--since="2026-10-17"` | 卷进整轮上一轮 | 98 |
| 目测 `git log` 输出 | 人眼数不准 | 「20 出头」（差 3.7 倍） |
| 看提交前缀推测归属 | 会把别人的提交算进来 | 4 个归属错 |

**✅ 正确做法**

```text
① 先用 `git log --grep="round-NN"` 找第一个标记提交
② 再用 `<那个提交>^..HEAD` 计数
③ 归属核实必须看 `git show <sha> --name-only`，不看提交信息前缀
```

**本轮 74 的补充事实**：`git log --format="%ad" --date=short 4fda18c^..HEAD`
去重后**全部是 2026-10-18**，无跨日。⇒ 边界不是靠日期切的，是靠语义切点。

## 三、★ 本轮的方法论收获

### 1. 假绿形态目录（20 条，`docs/notes/round-66-fake-green-catalog.md`）

本轮把「看起来完成、实际没生效」的形态整理成目录。核心判据：
**门禁必须读真实结果，不能读喂进去的那个值。**
判定方法：把要防的缺陷**人为还原**，门禁**必须变红**；还原后仍绿 ⇒ 假绿。

### 2. 「阳性对照 + 理论值比对」—— playback-fix 三次翻车的教训

不满足于「测试绿了」，而是拿一个**已知会失败的输入**做阳性对照，
并把读数与**理论值**比对（不是「看起来合理」）。

### 3. 「先查范围再动手」—— settings-ux 的 AppDialogShell、我的 SettingsBlock

```text
settings-ux 准备复用 AppDialogShell ⇒ 先查 ⇒ 查到它自带全屏 scrim，不能复用
我准备玻璃化 live_groups 卡片 ⇒ 先查 ⇒ 查到 SettingsBlock 是共享组件
  （lib/ui/ 下 32 处 / 13 个文件），live_groups 只占 3 处
  ⇒ 改它 = 一次性改动 13 个设置页外观，且让 live_groups 成为唯一异类
```

★ **本轮出现多次「范围错配」，这两次是在动手之前查出来的。**

### 4. 「下游判据够严 ≠ 上游给得够全」—— Lead 的三态缺陷

```text
门禁下游按三态判（null/false/true），上游却只给两态（bool）
⇒ 判据再严也测不出「没表态」被压成「要播/要停」
⇒ 缺陷在**上游的数据形状**，不在下游的断言强度
```

### 5. 「登记 vs 断言」—— settings-ux 的 Scaffold 结论

「登记一个事实」和「用断言钉住它」是两件事。把实现细节登记成断言，
下次重构必红（本轮 `keepForFade` 就是实例）。

### 6. 「历史记录型注释 ≠ 过时注释」—— Lead 纠正 perf-player 的误判

带日期的「改前是这样、后来改成那样」的注释是**决策留痕**，不是过期内容。
删掉它等于删掉「为什么不能走回头路」的依据。

## 五、★ 本轮最危险的 4 个发现

> 按危害排序，理由附后。

### ① 直播持久化写空数据（`bbf119c` / `9085c74`）

```text
1269 次请求白打，而且**下次还白打**。
Owner 的 P0「迟早要被拉黑」直接对应这一条。
★ 最危险的地方不是「有 bug」，而是「bug 的代价按每次启动累加」——
  用户每开一次软件，就多打一轮全量请求。
```

### ② raw-deflate「修了但没接线」（`9ca4076` → `4f77965`）

```text
上一版注释写着「★ 必须显式关掉自动解压：否则新请求会重踩同一个坑」
—— 代码用的还是那个会自动解压的 client。
⇒ 回退形同虚设，与不加回退完全一样。
⇒ 而且当时 **7 条 Dart 门禁全绿**。
★ 最危险的地方：注释与代码相反，且门禁测的是 Dart 侧，
  bug 在 Rust 侧（修复最终落在 rust/sourin_core/src/plugins/mod.rs）。
```

### ③ 「门禁覆盖 1/10 但全绿」（N10）

```text
上一版门禁全绿，但 90% 的 seek 路径没修。
⇒ 这是本轮**最普遍的形态**，比单个 bug 更危险：
  它让整个团队误以为「这条线已经收工了」。
★ 单个 bug 只损失一个功能；假绿损失的是「我们对质量的判断力」。
```

### ④ 采集站插件数量与独立站点数不符

```text
22 个采集站插件实为 16 个独立站点 ⇒ 用户看到 6 个假源
⇒ 直接解释了「某些源没内容」这个长期抱怨。
★ 危险在于：它伪装成「内容问题」，实际是「插件配置问题」，
  排查方向会被引到完全错误的地方。
```

**为什么把 ③ 排进前三**：① 和 ② 是具体的 P0，修掉就结束了；
③ 是**系统性的**——它会让后续每一轮的「已完成」都不可信。
我把它排在 ② 之后、④ 之前。
