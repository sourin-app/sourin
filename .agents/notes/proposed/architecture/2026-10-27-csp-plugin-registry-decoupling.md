# Agent Note: csp 类的插件化注册（可扩展、低耦合、面向多平台）

Status: proposed

## Problem

Owner 2026-10-27 下了架构约束（逐字）：

> 要插件化开发,不要耦合太严重,未来还可能兼容其他平台

而本仓现状正好与它相冲：**每加一个 csp 类都必须改核心文件**。

```text
rust/sourin_core/src/csp/mod.rs:259   type Builder = fn() -> Arc<dyn CspSite>;
rust/sourin_core/src/csp/mod.rs:261   fn build_registry() -> BTreeMap<&'static str, Builder> {
                                          let mut m = BTreeMap::new();
                                          m.insert(bili::Bili::CLASS, || { … });   ← 写死
                                          m.insert(app99::App99::CLASS, || { … });
                                          …
```

三条具体后果：

```text
① **新增类 = 改核心**：69 个待实现类（订阅实测）⇒ 69 行写死在 `build_registry()` 里。
   任何一次"加一个源"都触碰核心注册表 ⇒ 正是 Owner 说的"耦合太严重"。
② `Builder = fn()` 是**函数指针 + `&'static str` 键的静态表**
   ⇒ **外部无法注册**：第三方/其他平台要加类，只能 fork 核心。
   ⇒ "未来兼容其他平台"在现结构下**做不成**。
③ 注册表是 `once_cell::sync::Lazy` **进程内单例**，且键是 `&'static str`
   ⇒ 与"按配置动态增删"（用户导入订阅时才知道有哪些类）天然不合。
```

同时 R3 批要一次性补 69 个类（订阅实测 100 站只进 26 站、缺 74 站）——
**如果沿用现结构，这批交付会把上面三条各放大 69 倍**。

## Proposal

把"csp 类"的注册从**核心内写死**改成**可插拔注册**，并把"类实现"与"宿主细节"解耦：

```text
① **注册接口化**：核心只提供 `register(CspRegistration)` 的入口与一张表，
   每个类在自己的文件/module 里**自注册**；新增类 = **新增文件**，
   不要求改 `build_registry()` 的函数体。
   must：注册表支持**同名冲突检测**（两个 module 注册同一个 `CLASS` ⇒ 显式报错，
         不许后者静默覆盖前者 —— 那会让"我实现了但它没生效"变成静默故障）。
   must：未注册的类仍走既有 `unimplemented_reason` 逐字 `csp_X 尚未实现`
         （见 [csp 诚实契约](../../implemented/feature/2026-10-26-csp-honest-contract.md)）。

② **类实现只依赖契约，不依赖宿主**：
   允许 `use` 的只有 —— `CspSite` trait、领域模型（`model::MediaItem` 等）、
   以及与平台无关的工具（HTTP 客户端、cookie jar 之类的**注入接口**）。
   never：`crate::state` / `crate::hostpool` / `crate::proxy` / Flutter / FFI 细节。
   ⇒ 需要宿主能力时**通过注入的接口**拿（`with_proxy` / `with_data_dir` 这类已有形态是同一思路）。

③ **"外壳族"配置化**（这是"不要耦合"的最大杠杆）：
   若 R3 普查证实大量类其实共享同一套取数协议、只是 base URL / 盐 / 字段映射不同，
   则那一族 **1 个可配置实现** 覆盖 N 个类，而不是 N 份近似代码。
   ★ **普查已给出第一批数据**（`.probe/r3-shell-family-survey.log`，结构性读数）：
   ```text
   父类 → 子类数（剔除 merge.* 混淆类与匿名类）：
     crawler.Spider   84 个   ← 真正的"独立站点"队列，各写各的协议
     **Pan            32 个**  ← 最大杠杆：1 个可配置 Pan 插件 + 32 份配置
   Pan 族各子类"自有成员数"：PanBaidu 6 / QuPanSo 6 / GuiGui 5 … Pan123 22 …
                             GuanYing 69 / Juying 61 / Wn4k 61
   ⇒ **跨两个量级**：薄的（≈<12）可能纯配置驱动；厚的（>40）明显有各自协议。
   ```
   ⇒ **must：机制必须支持"一个实现 + N 份配置"**（task-18 的硬要求已据此加）。
   ⇒ **must not：假设整族都是纯配置** —— 5..69 的分布说明要**分层**，
     先按"自有成员数 / 重写方法集"分层，再决定哪些进配置、哪些单独实现。
   ⚠️ 上述是**结构性读数**（成员数/父类/API 重写集），**不是语义等价性判定**；
   哪些真能合并，要等 R3 普查（task-15）的语义层结论。
```

## Alternatives considered

1. **保持 `build_registry()` 写死**（现状）。
   它最强的论据是**真实可信的**：编译期就能查出"类没接上"，零运行时开销，
   而且本仓的"能力位必选手写"纪律（`supports_search` 无默认实现）正是靠编译期强制——
   动态注册会让"注册了但方法是空的"重新变成可能的静默故障。
   **否决**：它恰好就是 Owner 明确反对的那条（改一次源 = 改一次核心），
   且 `fn()` + `&'static str` 结构上排除了"外部/其他平台注册"。

2. **用 Cargo feature 门控**（`#[cfg(feature = "csp-appdrama")]`）。
   论据：零运行时成本、仍走编译期检查，比手写表更"可裁剪"。
   **否决**（两条，第二条是落地前复核时补的、比第一条更硬）：
   ① 69 个类 = 69 个 feature，组合空间 `2^69` 爆炸；
   ② ★ **feature 门控只是把 `m.insert(...)` 包进 `#[cfg]` ⇒ 注册行仍在 `build_registry()` 里**
      ⇒ 验收①「新增类不改核心」**依然不满足** —— 它根本没解决 Owner 的诉求，只换了写法。

3. **自动注册宏/链接期收集**（`inventory` / `linkme` / `ctor` 一类）。
   论据：**最贴合 Owner 的诉求** —— 每个类在自己的文件里自注册，
   新增类真的只需新增文件、零改核心；也是 `&'static str` 静态表的天然替代。
   **暂不否决，列为 task-18 的首选候选**：代价是**新增一个依赖**
   （本仓有"不新增运行时"纪律，见诚实契约第 4 条），且它依赖平台链接器特性，
   不是所有目标平台都支持 —— 但这**恰好是 task-18 要去实测的点**，不该在这里先拍。

4. **改走本仓既有的 JS 插件沙箱**（`plugins/mod.rs`，rquickjs + `SCRIPT_BUDGET_MS` 熔断）。
   论据很强：宿主**已经有**完整的插件系统 —— 安装、沙箱、热重载、能力位声明全都现成；
   走这条路"未来其他平台"几乎免费，而且用户能自己加源、不必等新构建。
   **否决（本批不做）**：69 个类的参考实现是 **Java 字节码**（RSA / protobuf / 设备指纹 / AES），
   转 JS 等于**再重写一遍**且要撞 `SCRIPT_BUDGET_MS`；
   本批要的是"补齐覆盖率"，不是"换插件语言"。⇒ 作为**未来方向**记录，不在本批。

5. **把 csp 类编成外部动态库**（`cdylib`，运行时 `dlopen`）。
   论据：真正意义上的"插件化"，可跨语言、可独立分发。
   **否决（本批）**：要新增 ABI 稳定性设计 + 符号表 + 版本协商，
   是**比 69 个类本身更大**的工程；且本仓已经为"跨语言"付过一次代价（Rust ↔ Flutter FFI），
   再叠一层插件 ABI 需要单独排期。

## Acceptance criteria

```text
① 新增一个 csp 类**不需要修改 `build_registry()` 函数体**
   —— 判据：一个只加"新文件 + 注册"的 commit 里，`build_registry` 的 diff 为 0 行。
② 同名 `CLASS` 冲突 ⇒ **显式报错**（注入验证：注册两个同名类必须失败/报错，不许静默）。
③ 类实现文件里 `grep` 不到宿主细节符号
   （`crate::state` / `crate::hostpool` / `crate::proxy` / `flutter`）——
   机器可验的源码断言。
④ 未注册的类**逐字**仍报 `csp_X 尚未实现`（既有门禁不许红）。
⑤ 既有 6 个已实现类行为**零变化**（`cargo test --lib` 全绿 + 既有 n9 门禁全绿）。
```

## Risks

```text
· **动态注册会把"编译期保障"换成"运行时可能为空"**：本仓刚在
  [能力位可撒谎](../../implemented/feature/2026-10-19-capability-bit-can-lie.md) 里吃过
  "声明了但方法不存在"的亏。⇒ 缓解：注册时**校验**（类名非空 / `CLASS` 与注册键一致），
  并把"注册了但方法抛 unimplemented"仍按既有契约逐字报错。
· **新增依赖**（候选 3）与本仓"不新增运行时"纪律冲突 ⇒ 要在 task-18 里
  当场判定"算不算新增运行时"（构建期注册 vs 运行期引擎，性质不同），并写进笔记。
· **本批 69 个类如果先按老结构写、后面再改注册**⇒ 会返工。
  ⇒ 缓解：R3 实现卡已下令"**类实现照写、注册方式先别定死**"，等本节落地再统一接。
· **"未来兼容其他平台"是长期目标，本节不承诺完成它**：本节只保证
  "不再让新增类必须改核心"，这是该目标**必要但非充分**的条件。
```
