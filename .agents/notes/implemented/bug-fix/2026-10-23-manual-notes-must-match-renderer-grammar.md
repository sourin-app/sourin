# Agent Note: 人工稿的输入约束必须按「渲染器认不认」写全

Status: implemented

- 日期：2026-10-23
- 适用：`tools/gen_release_notes.py` 的 `validate_manual_notes()`、`docs/release-notes/<TAG>.md`

## Problem

`lib/ui/widgets/release_notes.dart` 自己渲染更新说明，认的行首形态只有三种：
`#` 标题、`-`/`*`/`序号.` 列表项、其余当段落；行内只认 `**粗**`、`` `代码` ``、
`[文字]（地址）`。**别的语法不报错、原样显示** —— 这是刻意的（不为一个包拖进整套解析器）。

于是「不支持的语法」要由**写稿那一侧**拦住。模板层（`.github/release-notes.md`）
有 `test/zz_t66_release_notes_syntax_gate_test.dart` 反查 `markdown` 包的 BlockSyntax
白名单，覆盖表格、图片、引用块、HTML 内联。但人工确认稿那条路（`--manual`，
2026-10-21 新增）只有一份逐条正则，它拦了表格、图片、HTML、围栏、分隔线、占位符，
**没拦引用块、删除线、下划线粗体** ⇒ 同一件事两处判据，其中一处更弱。

实测：`> 旧版需要手动重连。`、`~~旧的说明~~`、`__重要__` 三种都通过校验，
到客户端就原样漏给用户。这正是当初在渲染器笔记里预测过的那条
「没做成通用 Markdown 支持 ⇒ 未来再遇到又一种未知语法还会漏一次」。
同一轮还发现收紧方向上的一个误伤：链接目标里的英文词（`[帮助页]（https://example.com/help）`
里的 `help`）被「英文词用户读不懂」判据拒掉 —— 链接地址根本不显示给用户。

## Decision

人工稿的输入约束按**渲染器认不认**列全，而不是按 Markdown 规不规范：

- 新增三条拒绝：行首 `>`（引用块）、成对的 `~~`（删除线）、成对的 `__`（下划线粗体），
  每条都写清「渲染器不支持」以及会看到什么。
- 英文词判据只看**去掉链接目标之后**的文本：圆括号里的地址不是用户可见文案。
  站名判据仍扫整行（仓库文本里不该出现具体站名，与是否显示无关）。
- 渲染器认识的写法必须有**不许误拒**的用例钉住（`**粗**`、反引号、链接、有序列表），
  否则收紧判据的代价会以「逼人改写稿子」的形式落在下一次发版上。
- **更要紧的一步：把「两处判据对账」做成可执行的事**，不再靠我再想一遍漏了哪种写法。
  `test/zz_t1024_release_notes_grammar_matrix_test.dart` 立一张语法矩阵：
  每种写法 → 跑真校验 → **若放行就拿真渲染器渲染，断言标记没漏给用户**，
  同时断言哨兵文字确实渲染出来（否则「没漏标记」可以被「整段丢掉」满足 = 假绿）。
  新写法的处置因此变成机械的：加一行，测试立刻告诉你它属于「已被拒」「已渲染干净」
  还是**两边都没管**（第三种会红）。
- 矩阵当场就抓出第四种：**Setext 标题**（`标题` 下一行 `====`）。校验放行、渲染器
  把 `====` 原样画出来。已补第四条拒绝（`=+` 整行），并加进 t1022 的拒收用例。

## Alternatives considered

**① 让渲染器支持这几种语法（引用块、删除线、下划线粗体），不加拒绝判据。**
最强的理由：用户读到的就是内容，而不是「这几种写法不许用」。引用块在更新说明里
不算稀奇，删除线表示「旧行为不再」也很自然；加判据等于把客户端能力不足变成作者的
书写限制。
否掉的原因：渲染器每多认一种语法就多一处「跳过还是显示」的判断，而这类判断已经
漏过一次（注释与分隔线）。真正长期稳妥的做法是换解析器，那是一次独立决定；
在那之前，先把**两处判据对齐**，比让渲染能力继续单点扩张更划算 —— 而且
「不许用」是可被机械验证的，「渲染得对」不是（只能靠肉眼与布局断言）。

**② 把 Dart 那份 BlockSyntax 白名单搬到 Python 里，拿 markdown 包的判据当唯一真相。**
最强的理由：两处判据合成一处，不会再有「一处更强一处更弱」。
否掉的原因：Dart 那份是拿 `package:markdown` 的解析器类反查的（`SetextHeadingSyntax`、
`BlockquoteSyntax`…），Python 侧没有同一个解析器；照抄类名等于抄一份不知道对不对的
影子清单。现在两边各按自己的语言写、用**同一份渲染器能力清单**做对账依据，
是零依赖下能做到的最接近真相的形态。

**③ 只加拒绝，不加「不许误拒」的用例。**
最强的理由：少写两条用例，判据更少更容易读。
否掉的原因：本轮实测就误伤了一次（链接目标里的 `help`）。收紧类判据的失效方向是
**假红**，而假红会逼人改写稿子 —— 不钉住「认识的写法必须过」，下次收紧还会再误伤一次。

## Consequences

收益：

- 三条新语法在写稿阶段就被拦住，用户不会再看到 `>` / `~~` / `__` 原样出现。
- 链接地址与「用户读不懂」解耦：带英文路径的链接不再把合规稿拒掉。
- 「渲染器认出什么」与「稿件允许写什么」在两边各有一份、可对账 ——
  而且这个对账**有执行体**（语法矩阵），不再只靠我下次还记得要想一遍。
  矩阵第一次跑就抓出了我没想到的 Setext 标题。

代价与残留：

- 判据清单会随渲染器演化而漂移：渲染器哪天支持引用块，这几条就得跟着删。
  缓解是两边都写了「按渲染器能力写」的理由，改的人能看到为什么要一起改；
  矩阵的放行/拒收清单会打印在测试日志里，漂移看得见。
- 仍然不是通用 Markdown：`_斜体_`、嵌套引用、任务列表等写法矩阵里还没列
  （列了就只是「还没被谁想到」，不是「已经验过」）。真正的解法仍是换解析器，
  这条笔记不改变那个判断。
- 矩阵只覆盖**列出来的**写法：它把「下一次再加一种语法」从「靠记性」变成
  「加一行」，但**不会**自己发现没人想到的语法。这是本轮能到的最远处，写清楚。
- 站名判据仍扫整行 ⇒ 链接地址里出现站名会被拒（当前判断：仓库文本本身不该有，
  与模板层一致，先留着）。
