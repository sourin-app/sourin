# Agent Note: 播放失败归因 —— 先认 HTTP 状态码，再认关键词

Status: implemented

## Problem

播放失败时给用户看的提示，改前只认中文关键词：

```text
判据只有：「大会员」「会员」「VIP」「付费」「地区」「版权」「无权」…
```

实测到的漏判（`.probe/round65-c/samples_run6.log`，32 个源 35 条样本）：

```text
代理把上游的 403 原样转出来，正文是一张 **HTML 错误页**：
  <h1>403 Forbidden</h1>
  <p>The region has been denied.</p>
而改前的判据**完全没有 403/401 这两个数字**
⇒ 这条真实的「源站地区限制」落到 unknown，
  用户看到的是那张 HTML 错误页原文 —— 既看不懂也不知道该找谁。
```

## Decision

`1f8674e`：把 **HTTP 状态码判定排在所有关键词之前**。

```text
顺序理由：数字是**协议层事实**，关键词是我们从人话里猜的。
  403 / 401        ⇒ permission（源站权限）
  404 / 410        ⇒ source（地址没了）
  429 / 5xx        ⇒ network（限流或临时故障）
  其余（含无状态码）⇒ 继续往下走关键词判定
```

★ 这不是"多加几个词"，而是**改变了判据的优先级**：
改前是「先猜语义，猜不到再说」，改后是「先看事实，事实不足再猜语义」。

同期修的另一处（同批）：
```text
「取流失败」归 source（上游连不上），不是 proxy（代理挂了）
理由：代理明明是好的，坏的是那个源。
     归错会让用户去重启客户端，而正确动作是换源。
```

## Alternatives considered

- **继续扩充中文关键词表** —— 它最强的论据是不改结构，只加词，风险最低。
  否决理由：HTML 错误页里的文案是**源站自己写的**，语言和措辞都不受我们控制
  （英文、日文、各种 CDN 的默认页）。关键词表永远追不上。

- **把 HTML 错误页整体展示给用户** —— 它最强的论据是最诚实，
  不加工原文，用户能自己判断。
  否决理由：用户看到 `<h1>403 Forbidden</h1>` 既不知道是谁的问题，
  也不知道该怎么办。实测这就是改前的行为，且被明确反馈为「看不懂」。

- **只按状态码，完全不用关键词** —— 它最强的论据是判据单一、不会自相矛盾。
  否决理由：很多失败根本没有 HTTP 状态码（mpv 层的解码失败、
  插件抛的异常、DNS 失败）。纯状态码会把它们全部归到 unknown。

- **在归因里同时返回多个候选让 UI 挑** —— 它最强的论据是避免误判。
  否决理由：UI 无法在运行时判断哪个候选更对，最终还是会挑第一个 ——
  等于把排序逻辑藏进 UI，更难测。

## Consequences

- **收益**：地区限制、限流、地址失效这三类最常见的失败现在能正确归类；
  用户拿到的是「换源」「等一下再试」这类可执行建议，而不是一张 HTML。
- **代价**：状态码优先意味着**一旦代理改写了状态码**（例如把上游 403
  统一转成 502），归因会跟着错。这是已知上限，靠日志里的原始状态码排查。
- **关联**：本批之后又发现同函数的另一处判据错误（把「给用户看的改写文本」
  喂进了归因）—— 见
  [2026-10-18-proxy-misjudge-read-display-text.md](../bug-fix/2026-10-18-proxy-misjudge-read-display-text.md)。
  两篇合起来说明同一件事：**归因函数的输入必须是原始事实。**
- **重访条件**：当出现「状态码对但归因错」的稳定复现时，说明中间有层改写了状态码，
  届时应在那一层记录原始码而不是调整归因顺序。
