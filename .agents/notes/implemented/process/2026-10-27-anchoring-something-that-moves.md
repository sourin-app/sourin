# Agent Note: 锚定"会变的东西" —— 时点 / 上游 / 文档自身，三者都要分档

Status: implemented

## Problem

本批（R3，多执行者并行补 csp 类）反复出现同一类失败：
**把判据锚在一个"会变的东西"上，于是"锚"本身过期，而依赖它的推理跟着错。**

三个实例（都不是假设，本批实测）：

```text
① 锚在**时间**上：上游活/死读数
   · Yinhai 的后端②：**同一天内**先 "HTTP 200 包 502 页"、后 "真 502"（两种死法）
   · AppDrama 取域：**域会轮换**（天堂 ↔ 橘汁 在两次探测里反过来）
   · 复核者复跑同一批真网络用例，条数变了：sou4k 470 → 483、yinhai 793 → 638
   ⇒ 任何"上游当前可用/不可用"的结论，**不加时点就是错的**。

② 锚在**上游**上：一份档里的存活表被当成"现在"
   · `.probe/r3-g-tier1-evidence.log` 的存活读数是**跑的那一刻**的快照；
     复核者读它时上游可能已变 ⇒ "带了时间戳"只告诉人"什么时候该怀疑它"，
     不构成"它现在成立"。

③ 锚在**文档自身**上：交付物的 md5
   · `.probe/r3-g-delivery-ledger.md` 是**持续增长的证据档**（322 行 / 11 节），
     每轮补一节 ⇒ 它的 md5 **每轮都变**。
   · 实测序列：`3faee1f1… → 568a561d… → 2f3033b7… → 156ff7ba…`
     ⇒ **三次**让 Lead 与复核者手里的值过期，每次都诱发"文件被改坏了吗"的排查。
```

## Decision

**判据要按"被锚定的对象会不会动"分档**：

```text
· 锚定**时间**（上游读数、真网络条数、性能读数）
  ⇒ 必须带**取值时点**，且**明确它是时点值**（不是"当前值"）。
  ⇒ 用它的判据**不得**写成全称（"该站可用"），只能写"**<时点> 实测…**"。

· 锚定**上游**（存活表、端点探测）
  ⇒ 同上，且**复核者应重测**，不能引用前人的快照当现状。

· 锚定**文档自身**（交付物 md5）
  ⇒ 先分性质：
     · **冻结版本**（一次性交付物：一份报告定稿、一个源码文件）⇒ 核 md5
     · **活文档**（持续增长的台账/日志）⇒ **不要用单一 md5 当锚**；
       要么"**冻结一版 + 新开续档**"（v1 顶部写"已被 v2 取代，见 …"），
       要么**明确标注"会持续更新"**，让引用者知道它必然会变。
```

★ 落地（本批）：`r3-g-delivery-ledger.md` **冻结在 `156ff7ba…`**，
   顶部加一行指向后续的 `-final.md`；将来的补记写在**新档**里，
   使"历史版本不再变"（引用任一版本都拿得到）。

## ★ 第 5 型（本批新增，**危害最大**）：**过期的恢复源（stale）**

```text
本批实测：多执行者共享一棵源码树时，每个执行者都留了"注入前备份 / 恢复基线"。
而这些备份**会随别人继续改动而过期** —— 但**没有任何东西提示它过期了**。

★ 实例（tvbox-ui 逐个 `md5sum` 核出 **7 份**，含一份最危险）：
  · `csp/mod.rs` 的备份 = **21** 个 `pub mod`；现盘 = **28** 个
    （多出的 7 行是别的执行者新增的类）
    ⇒ 若谁拿它"恢复" ⇒ **7 个已实现的类从注册表里消失**
    ⇒ 而**编译可能仍然通过**（那些 `.rs` 文件都还在，只是**不再被 `pub mod` 声明**）
    ⇒ **静默丢失**，且没有任何报错指向它。★ 这是本条最危险的形态。
  · `ffi.rs` / `tvbox_aggregate.rs` / `settings_page.dart` 的备份同样落后于现盘
  · 另有一份 **注入失败态**残留（看着像正常代码，其实是注入打在了注释上的产物）
```

**处置（本批落地的形态）**：

```text
① **不删历史快照**，而是把"不得当恢复源"**写进文件名** ——
   `…-STALE-do-not-restore.rs` / `…-BOTCHED-INJECT-never-restore.dart` /
   唯一可用的标 `…-AUTHORITATIVE.ext`
   ★ 理由（tvbox-ui 给的）：**用的人不会先读文件内容** ⇒ 判据要落在**看得见的地方**。
② 落一份清单（`.probe/r2-restore-source-ledger-tvbox-ui.md`）：哪些**不得用**（附过期原因与两边 md5）、
   哪些**仍可用**（逐份核过与现盘一致）。
③ 用恢复源的硬规矩：**先 `diff -q` 备份 vs 现盘**再决定用不用；改完立刻重核 md5。
```

### ★★ 第二次实战（同日，**另一位执行者自己栽的**）—— 由此补出一条**必需字段**

```text
一位执行者对 7 个类做"注入 ⇒ 跑 ⇒ 恢复"，恢复源用 `/tmp/np8/<类>.rs` ——
  而那是**插入修复之前**建的备份 ⇒ **恢复 = 把修复与门禁一起抹掉**。
实测损失：**4 个类被抹回修复前**、1 个半损（门禁在、代码行没了）。

★ 它**怎么发现的**：用**行首锚定判据**复核
  `grep -cE '^\s+\.no_proxy\(\)\s*$'` ⇒ **0** ⇒ 当场抓到。
  ★ 关键：**若只 `grep "no_proxy"`，会命中注释里的字样，看不出问题** ——
    这一步是本仓"判据形态"那条教训的**正确应用**。

★ 根因（它自己给的）：「**"备份"没有标它代表哪个状态** ⇒
  拿"注入前备份"去恢复"注入后状态" ⇒ **用错了恢复源**。」
  ★ 而**它先前已经给一份备份标过"代表修复态"** ⇒ 说明**它记住了这条教训，
    但没在其余 7 份上执行** ⇒ **"记住了"不等于"做到了"**。
```

**⇒ 由此补出的必需字段（本批采纳）**：

```text
备份文件名必须同时标明**两件事**：
  ① **哪些文件**（`<class>.rs`）
  ② ★ **它代表哪个状态**（注入前 / 注入后 / 修复态 / 交付态）
⇒ **状态标签是必需字段，不是可选注释**。
  理由：同一份文件在流程中有**多个合法快照**，而"哪个能用"取决于**你要恢复到哪个状态**——
  光有文件名**不足以判断**（这正是本次两次实战的共同成因）。
★ 落地：本次改用 `/tmp/fixed/` 作**修复态**备份，恢复后 `cmp` 逐字节核过 8/8。
```

★ **为什么它是第 5 型、且与前四型不同**：

```text
前四型（环境/平台/噪声/两态同值）都属"**读数错**" —— 代价是判错。
本型属"**状态错**" —— 仅仅"用了一份看起来完全正常的旧文件"，就会**真的改坏产品**。
★ 而它的共同点仍是那个母题：**"看起来完全正常，但不是你要的那件事"**
  （它是真实存在、格式正确、内容自洽的文件，只是**落后于现盘**）。
```

## ★ 第 6 型：**"工具的'空结果'不等于'对象不存在'"**

```text
本批一位执行者做"抽文档里所有数字声称、逐条对照实测"的审计脚本时，连续踩了**四次同形**：
  ① `md5sum {…} | md5sum` 含文件名 ⇒ 换目录值就变（**判据混入环境**）
  ② 同上（他修了两次才改成路径无关）
  ③ 审计脚本的**搜索范围不含源码目录** ⇒ "0 匹配"被误读成"**文件丢了**"（**范围不足**）
  ④ 提取正则**不匹配实际输出形态** ⇒ "0 条"被误读成"**门禁不存在**"（**解析错**）

⇒ 四次的后果**完全相同**：**工具返回"0"/空，而人容易把它读成"那东西不存在"。**
   ★ 而②③④里的"那东西"都**真实存在**（文件在、门禁在、路径无关哈希也算得出）。
```

**处置（本批落地的判据）**：

```text
对任何"0 / 空"结果，**先做一次正对照** ——
  拿一个**已知存在**的样本跑**同一段判据**，确认它能返回非 0。
  若正对照也返回 0 ⇒ 是**判据/正则/范围**没对准，不是对象不存在。
```

★ 实证：本批那四次**都是靠"正对照"或"换算法复核"才发现**的（其中一次是切成两条
  命令对比，才看出"含文件名"与"不含文件名"给出**两个不同的值**）。

★ 与第 5 型的区别：第 5 型是"**资源太多且过时**"（用了会改坏产品），
  本型是"**资源明明在、但工具说没有**"（于是可能**白做一遍**或**误报缺失**）。
  两者都源于同一个动作：**把工具的返回值直接当成事实**。

## Alternatives considered

1. **只要求"读数带时间戳"**（最省事）。
   论据：时间戳能让人知道什么时候该怀疑它，一条规则覆盖①②。
   **否决** —— 它**不覆盖③**（文档 md5 的问题不是"没标时点"，而是
   "**用一个会变的量当锚**"）。且实测证明"带了时间戳"仍会被当现状引用
   （`.probe/r3-g-tier1-evidence.log` 带了时点，复核者仍须重测）。
   ⇒ 需要把"**标时点**"与"**分档**"分开：前者是标注，后者是结构。

2. **台账保持单文件、每次更新后主动通知所有引用者新 md5**。
   论据：单一来源，不产生版本分叉。
   **否决** —— 本批实测它**失效过三次**：更新方（执行者）确实通知了，
   但**引用方（Lead / 复核者）手里的值仍会过期**，因为通知是异步的、
   而"排查过期"的成本每次都要重走一遍。⇒ 分档让"过期"变成**可预期**，而不是靠通知。

3. **索性不报 md5，只报"内容摘要"**。
   论据：摘要比 md5 对内容更敏感，且不随无关改动漂移。
   **否决** —— 本批的 md5 判据**有独立价值**（它抓过"改坏了"的真实情形，
   也是"私有文件 vs 共享文件"分档的依据）；取消它会把那一层的保护一起去掉。
   ⇒ 正解是**分层**（冻结物核 md5 / 活文档核"我的增量在位"），不是取消。

## Consequences

- **收益**：把"锚过期"从**偶发事故**变成**可预期的分档问题**；
  并且与另两族接上（下节）。
- **代价**：交付时**多一次判断**（"我这份东西是冻结的还是活的？"），
  且活文档要多一个 `-final.md` 档（多一个文件）。
  ★ 这个代价是**执行者自己先提出来的**（csp-batch-c），不是 Lead 要求后才做。
- **已知上限（如实记）**：
  本批只处理了"活文档 vs 冻结版本"这一层；**没有**做更强的形态
  （如内容寻址的摘要锚、或"版本号 + 变更日志"）。
  ⇒ 若将来活文档再多，可能需要真的版本机制；本批**未证明必要**。
- **与另两族的关系**（批末按族记）：
  ```text
  A 族「判据适用范围」：判据放错位置（太宽 / 太窄 / 混入环境 / 触发条件不清）
  B 族「被锚定的对象会动」：时间 / 上游 / 文档自身 ← 本条
  C 族「表述强度与实际不符」：说成"不能"实为"不做"；概括说成逐字引用
  ⇒ 三族都表现为"**看起来判过了 / 看起来引对了**"，而实际不是。
  ```

## ★ 落地补充（2026-10-27 同日）：**共享树上的读数，两侧各有一条动作**

```text
本批实测到的两种错法（都是"读到中间态")：
 ① **写入侧**：执行者跑注入脚本（改 → 跑测试 → 恢复），秒级窗口内树在变
    ⇒ 我恰在那几秒跑编译 ⇒ 抓到"md5 未变但测试红"（位置逐次漂移）。
 ② **读取侧**：我改 `t98` 时，执行者在同一窗口内连读 `行级豁免命中` ⇒ 读到 71 / 69 / 71
    ⇒ 它一度以为"读数不稳定"。
```

⇒ **两侧各一条固定动作**（本批采纳）：

```text
· 写入侧：**改完静止 ≥2 分钟**再报"可复跑"（别让"改→恢复"跨到别人的编译）。
  ★ 若要跑注入脚本，**先看目标文件的 mtime 是否刚被别人动过**（尤其 `mod.rs` —— 那是加行动作）。
· 读取侧：**取数前记被测文件的 mtime**。
  若 mtime 落在最近的秒级窗口内 ⇒ **该读数不得用于下结论**（先等稳定）。
  ★ 本批实测：加上这个动作后，执行者才确认"69 是新的、71 是旧的"，
    而不是报"读数不稳定"。
```

★ **为什么这两条必须成对**：单有写入侧的纪律，读取侧仍可能**恰好在窗口内取数**；
  单有读取侧的检查，写入侧仍可能**不预告就动树**。
  ⇒ 只有**两侧都做**，"共享树上的读数"才是可信的 —— 这是**协作产生的新失败模式**
  （单人工作时不存在：自己改自己读，本来就知道是不是中间态）。

### 批末可操作推论（来自执行者的观察）

```text
「**"双方共享的判据"比"单方持有的判据"更容易被审出问题** ——
   因为两边都要依赖它 ⇒ 谁都不会让它含糊。
  ⇒ 反过来说：**只被一方使用的判据，天然缺少第二个读者 ⇒ 更该被点名复核**。」

⇒ 落地：**收口前把"只有一手在用的判据"列出来，点名让别人复核** ——
  而不是只让执行者互相复核（那样会漏掉"Lead 私有的判据"）。
```
