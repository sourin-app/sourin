# Agent Note: 发版模板的语法必须落在渲染器的支持面内

Status: implemented

- 日期：2026-10-21
- 适用：`.github/release-notes.md`、`lib/ui/widgets/release_notes.dart`、
  `test/zz_t66_release_notes_syntax_gate_test.dart`

## Problem

`lib/ui/widgets/release_notes.dart` 是一个**故意做窄**的 Markdown 渲染器
（不支持表格、图片、引用块、HTML 内联、围栏代码块），
而 `.github/release-notes.md` 是它的内容来源。

两侧各自都对，但**没有任何机制保证内容落在渲染器的支持面内**：

```text
· 2026-10-21 真机验证：模板里的 4 张表 / 31 行表格语法在更新弹窗里原样漏出
· 同一天，语法门禁第一次运行又抓到第二处：
  macOS「绕过方法 → 3. 命令行」用了三反引号围栏块
  ⇒ 用户看到的是三连反引号本身
```

已有的 `zz_t66_release_notes_no_table_test.dart` 只钉了**表格一种**语法。
下次有人写行内图片、引用块、HTML 标签，同样会漏给用户，而那条门禁**不会红**。

更深一层：渲染器的支持面是**代码里分散的分支**（`startsWith('#')`、
`startsWith('- ')`、有序列表正则、`_inline()` 的三分支正则），
没有一处集中声明"支持什么"。⇒ 想写门禁的人只能靠读代码 + 记忆，
而记忆会漂移。

## Decision

新增 `test/zz_t66_release_notes_syntax_gate_test.dart`，做两件事：

**① 白名单从渲染器代码推导，不是手写常量。**
门禁从 `release_notes.dart` 的**实际分支**提取支持集，并 assert 这些依据
仍在代码里。渲染器加了语法 ⇒ 白名单自动跟上；删了 ⇒ 模板立刻红，逼人同步。

**② 扫模板求差集。**
不支持清单（`table` / `image` / `inline-image` / `html-tag` / `fenced-code`）
逐行扫描，命中即报「语法 + 行号」。

配套要求：

```text
· HTML 注释区间内的内容不扫（不渲染，不会漏给用户）
· 报告打印覆盖度「扫了 N 行 / 非空 M 行」，并断言非空行 > 50
  ⇒ 否则「扫错文件」与「文件很干净」在输出上无法区分
· 阳性对照与阴性对照独立成条，不依赖故障注入
```

同时修掉门禁当天抓到的真缺陷：`.github/release-notes.md` 第 149 行的
围栏代码块改成行内代码。

## Alternatives considered

**① 给渲染器加表格支持**

最强理由：一次修好所有版本（含已发布的 v1.3.0），用户立刻看到效果，
且以后写 release notes 可以自由用表格。

否定：`release_notes.dart` 的设计意图明写「语法很窄，不值得为此加包
（它还会拖进 markdown 与一整套解析器，而本仓正在为安装包体积把关）」。
加表格要处理对齐 / 嵌套 / 转义 / 超宽 / 合并单元格 —— 每一样都是新 bug 面，
而收益只是「我们自己写的表格能显示」。
★ 而且它**不解决这次的问题**：已发布的 body 是旧内容，
加了解析器反而会让旧表格「显示成表格」而不是列表 —— 换一种错法。

**② 手动改 GitHub 上 v1.3.0 的 Release body**

最强理由：立刻修复已发版用户看到的内容，不需要等下次发版。

否定：属「对外发布」动作，需 Owner 授权；且改的是历史内容，不可逆。

**③ 只加门禁，不改模板**

最强理由：防止将来再犯，零风险。

否定：不修当前缺陷 —— 模板里还有 1 处围栏代码块会让用户看到三连反引号。

**④ 继续只钉「不许有表格」，靠人工记住其它语法**

最强理由：改动最小。

否定：这正是已经失败过的做法。`release_notes.dart:12-14` 把「不支持的」
写成注释，而注释不会执行 —— 表格就是这么漏出去的。

**⑤（采用）改模板 + 加从渲染器推导的白名单门禁**

理由：门禁的判据来自渲染器代码本身，所以「渲染器不支持什么，模板就不许写什么」
是可机械核对的，不依赖任何人的记忆。落地当天即抓到 1 个真缺陷。

## Consequences

收益：

```text
· 门禁在落地当天抓到 1 个真缺陷（md:149 围栏代码块）
· 白名单从渲染器代码推导 ⇒ 可机械核对，不依赖记忆
· 4 种注入全红 + 双侧对照独立成条 ⇒ 判据承重已证
```

代价：

```text
· 门禁只扫 .github/release-notes.md 一个文件；若有第二个来源需加路径
· 白名单的"支持集"是从代码里提取的形态（heading / list / inline），
  若渲染器改用法（例如改成解析 AST），提取逻辑要同步改
· 已发布的 v1.3.0 仍是坏的 —— 本修复只保证下次发版正确
· 新增约束：模板里不能用围栏代码块，长命令只能写成一行行内代码
```

何时该翻案：

```text
· 若将来因别的需求已引入完整 Markdown 解析器 ⇒ 表格是附带能力，
  可撤销本约束，但**要新开一篇笔记并删本门禁**
  （不要就地改这篇的 Decision —— 决定不能改写，事实才能就地同步）
· 若 v1.3.0 确认对外且用户量大 ⇒ 需重新评估是否值得手动改 Release body
· 若渲染器的语法白名单扩大（新增支持某种标记）⇒ 提取逻辑必须同步
```

未覆盖（诚实边界）：

```text
· 不查「已发布的 body」—— 门禁只看本地模板
· 不查语义 —— 表格行内的加粗其实渲染正常（我靠放大图确认过），
  本门禁只按语法形态判，不判断"这段文字读起来对不对"
· 不查真机排版（字宽 / 换行；见 PITFALLS「中文宽度恒 12.000」）
```

## 附带的流程判据（本轮踩到）

做故障注入时，还原写在了 `run_test()` 之后：

```text
for old, new in injections:
    inject(old, new)
    run_test()      # 读到的是上一次的注入残留
    restore()       # 太晚
```

⇒ 注入 B（图片）报出的是 `table`，差点被当成门禁 bug。
**判据：每次 `run_test()` 之前，必须先断言「文件处于基线状态」**，
断言不成立就报错退出。
已落成 `.probe/_inject_guard.py`（基线 RC=0 / 有残留 RC=1 并拒绝继续）。
