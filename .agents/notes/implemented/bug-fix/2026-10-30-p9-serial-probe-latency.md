# Agent Note: P9 —— task-8 的清单探测把起播延迟拖成线性，实测 8 条 9615ms 后改并发

Status: implemented

Independent: 本篇修的是 `2026-10-30-hls-playlist-total-ms.md`（task-8 把清单真实时长带进候选）**引入的连带性能回归**：
那篇让"时长读数变准"，本篇保证"读数变准不以起播延迟为代价"。两条是同一功能的正确性与性能两面。

## Problem

task-8 在 `playback.rs` 的 resolve 出口给每个 HLS 候选读一次清单，实现是：

```rust
for c in &mut list {
    crate::hls_facts::probe_candidate(c).await;   // 单候选预算 1500ms
    …
}
```

按候选**串行 await**。真机形态里多线路内容很常见（本批实测：思君如故 8 线路、
聚合条目十几条候选），这些时间**全部堆在首帧之前**。

Owner 在 1.3 明确过「先试缓存方案（不增加起播延迟）」。为了修时长读数而换来
"点开转圈十几秒"，是把一个缺陷换成另一个。

## Decision

三步，顺序不可换（先量化、再修、再证）：

```text
① 先建延迟门禁把最坏情况量化（不许靠读代码断言"应该没事"）
   - axum 假站起 N 个慢清单端点（每条故意 1200ms）
   - 走批处理入口测总墙钟 + 校验每条候选都拿到真事实
② 修：抽 probe_candidates() 批处理入口，内部 JoinSet 并发 + 限流 8
   + 整批硬截止 PROBE_BATCH_DEADLINE_MS=2500；超截止的候选留 None
③ 证：门禁转绿 + 全量口径带退出码
```

关键实现点：

- **守卫前置**：只有通过 `should_probe_candidate`（kind==Hls 或 URL 以 `.m3u8` 结尾）
  的候选才进批处理 ⇒ mp4 直链零成本，不给它们加一次 RTT。
- **超时不编读数**：批截止到点后未回填的候选保持 `None/false`（约束③语义），
  绝不为了"凑齐"编一个数字 —— 宁可这条线路退回 mpv 广播值（行为与修复前一致）。
- **不许只探第一条**：那会让没探到的线路继续留错读数，等于把缺陷藏起来。
  门禁专门断言"N 条候选全部拿到 82720"，堵死这条偷懒路。
- **接线在循环之前**：`probe_candidates(&mut list).await` 必须早于 `maybe_proxy`
  （代理后的本地地址读不到上游清单），门禁用 `find` 下标比较钉住顺序。

## Alternatives considered

- **只调小单候选预算（1500 → 300ms）**：上游慢时全变 None，读数全丢，等于把功能废掉。否决。
- **只探第一条候选**：没探到的线路读数仍是错的，缺陷被藏起来。否决（门禁已堵）。
- **把探测挪到起播后台回填**：根治，但要新增推送通道、改 FFI 契约与 Dart 侧消费，
  属另一个命题；本篇先用并发+截止把最坏情况压到可接受，后台回填记在边界里待议。
- **按候选数动态调并发**：并发上限的意义是"不给同一上游砸满"，与候选数无关。否决。
- **给延迟门禁放宽到 10s 让它绿**：那是把判据改到能过，正是禁止的假绿。否决。

## Consequences

**修前实测（门禁 `p9_batch_probe_wallclock_has_hard_cap` 与 `_scales_without_fabricating`，
每条清单故意慢 1200ms）**：

```text
8  条候选 = 9615ms     ← 完全线性（8×1200）
32 条候选 = 38457ms    ← 完全线性（32×1200）
两条门禁此时都是红的（红即立案成立）
```

**修后实测**：

```text
8  条候选 ≤ 2500ms 硬上限内通过（8 条正好一批，≈ 单候选耗时）
32 条候选 = 2502ms，拿到事实 16/32，其余 16 条为 None（未编造）
```

32 条拿 16 条是**有意取舍**：批截止 2500ms 内跑完两批（8+8），剩余候选留 None。
这比"等 38 秒把所有读数凑齐"好得多——用户要的是能马上播，时长读数是次要信息，
且没探到的线路退回修复前行为（mpv 广播值），不会更差。

**门禁读数（2026-10-30 批末复跑，带退出码）**：

```text
cargo test --lib --release   ⇒ 1933 passed / 0 failed（RC=0）
flutter test 本批三门禁       ⇒ 25 passed / 0 failed（RC=0）
flutter analyze              ⇒ errors=0（warnings=385 / info=1609，均非本批引入）
agent_notes_gate             ⇒ tree / format / archived 三绿
```

源码级门禁同时钉住反向约束：`!src.contains("probe_candidate(c).await;")`
——不许退回循环内逐个 await。

## 真机复核（2026-10-30 23:07 / 23:10，appqk「仙逆」第1集）

并发化后在真机上补测过。遥控 `play_item` → `/api/state` 轮询到 `playing=true` 的墙钟：

```text
23:07:25.531 [PLAY] 清单事实 id~=csp-appyqk-af741cf6::129 total_ms=Some(1315633) discontinuous=true
             ⇒ /api/state 同上：dur=1315（清单真值，非 mpv 分片伪影）
23:07:58.821 又一次 total_ms=Some(1235833) ⇒ dur=1235
```

即：并发化后**清单事实照样条条拿到**（这两条都走了 master.m3u8 追子清单的路径），
起播没有被 2500ms 批截止截掉 —— 修 P9 没有以牺牲 P7 的读数为代价。

**必须如实记的反例（同一条目第三次，23:10:01）**：

```text
23:10:01.129 [PLAY] 起播 kind=mp4 url=…master.m3u8?sign=…&t=1793372999
             —— 前一行没有「清单事实」，/api/state dur=6（mpv 分片伪影读数）
23:10:30.305 [PLAY] 起播 kind=mp4 url=…/2478077/…/master.m3u8?t=1793373028
23:10:36.161 [PLAY] 起播失败：Failed to open …（耗时 5.88s，network-timeout=5s）
```

三次起播的是同一条内容、同一个上游域名，前两次拿到事实、第三次留 None。
差异在**上游对这次探测的响应速度**，不在代码分支 —— 候选都是 kind=mp4 但 URL 以
`.m3u8` 结尾，走的是同一个 `should_probe_candidate` 判据，`t=` 时间戳参数每次都不同。
最合理的解释：单候选 1500ms 预算内这次上游没应答（或整体撞上 2500ms 批截止），
按约束③留 None，于是 Dart 侧退回 mpv 广播值 6。

**结论：这是设计内行为，不是回归。** 约束③本来就是"读不到就留 None，绝不编读数"，
代价是这次的时长读数退回修复前形态。反面印证了当初**不许**为了凑齐读数而放宽预算
的取舍是对的：若为了这次拿到事实去加预算，就是拿起播延迟换次要信息。

**仍未闭环的一项（如实记录）**：真机「多线路内容点开变快了多少」至今没有可信数字。
本批实测到的都是单候选形态（sources=1，聚合条目 resolve 后只剩 1 条可播候选），
修前 9615ms/38457ms 那两个数是**门禁里构造的 8/32 候选慢清单**，真机里没有出现过
8 条候选同时需探测的样本。所以"真机上 N×1500ms 的排队到底消没消"这个问题，
本批**证到并发化没拖慢起播、没丢读数即可，加速幅度无真机样本，不编数字**。

如实记录的边界：

- 仍会为首帧前探测花最多 2500ms（只在候选多且上游慢时）。彻底消除需后台回填，另议。
- `drop JoinSet` 是**脱管**而非 abort：超时后已在飞的探测任务会跑完自己那 1500ms，
  只是没人接收结果。安全性来自"回填只在 drain 循环里发生"，那个循环随 future 一起被丢弃，
  不会有任务往 list 写。代价是多几个后台网络往返，不影响起播。
- 本次全程离线验证，**未做真机延迟实测**（Owner 当时正在使用 App，遥控驱动会打断他）。
  真机侧的"多线路内容点开是否变快"应在 Owner 空窗时补一次，记入待办。
