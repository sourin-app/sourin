# Agent Note: 把两处「静默的不一致」改成 CI 里的显式失败 —— 发布凭据预检与坑表条数门禁

Status: implemented

> 同域：[外部弹幕凭证在构建期由 secrets 注入](2026-10-12-danmaku-credentials-build-time-secrets.md)
> ——同一条链上的上游，讲**凭证从哪来、挂在哪一级**；本篇改的是**它为空时怎么办**，
> 并**部分取代**那一篇 `Consequences` 里「空串回落、行为不变（这是可接受的上限）」这句判断。
> 同域：[CI 上「静默 skip」比「红」更危险](2026-10-19-silent-skip-is-worse-than-red-in-ci.md)
> （同一族：把静默失效变成显式失败，代价只是重跑）。
> 同域：[给「用户可见文案」加防腐守卫](2026-10-19-guard-user-facing-copy-from-rotting-numbers.md)
> （同一族：人写的数字会烂，所以要机器算）。
> 同域：[门禁要的「提交区间」在 `fetch-depth: 1` 的检出上根本不存在](2026-10-21-ci-gate-needs-full-git-history.md)
> （同一个 job 的邻居：新门禁要么真在跑，要么红着把原因说清）。
> Independent: 本篇讲的是**判据本身该不该存在**，既不是「判据放在了错误的位置」，
> 也不是「文案里的数字会烂」。两条改动的共同形状只有一句：
> **过去靠人记得保持一致的地方，现在让机器在 CI 里大声失败。**

## Problem

两处「不一致」都在静默发生，而且都属于**修好之后没人会知道曾经错过**的那一类。

### 一、发布包缺少外部服务凭证时，构建照常绿

```text
.github/workflows/build.yml:468-470   Windows「构建 Windows 发布版」步骤级 env:
    DANDANPLAY_APP_ID:     ${{ secrets.DANDANPLAY_APP_ID }}
    DANDANPLAY_APP_SECRET: ${{ secrets.DANDANPLAY_APP_SECRET }}
.github/workflows/build.yml:880-882   macOS 同构
```

GitHub Actions 对**不存在的 secret 不报错**，它渲染成空串：

```text
secret 未配置（fork PR / 新建仓库 / Owner 忘了配）
  ⇒ env 是空串 ⇒ --dart-define 也是空串（build.yml:472 的注释自己写着这一条）
  ⇒ 构建成功、测试全绿、产物照常上传
  ⇒ 用户装上一个**不带凭证**的包，回落到「让用户自己填 AppId/Secret」的旧路径
```

`2026-10-12` 那篇把这段记成「行为不变（这是可接受的上限）」。
★ 那句话只算了「App 仍能跑」，**没算「用户不知道自己装的是不带凭证的包」** ——
对一个要交给 Owner 的安装包来说，后者才是代价：它既不坏（能跑）、也不对（缺东西），
而**没有任何一处输出会提到它**。

★ 本轮实测（不是假设）：`GET /repos/{o}/{r}/actions/secrets → total_count = 0`，
即这两个 secret **现在确实没配**。上面那段就是当前的发布路径。

⚠️ 而取这个数本身先踩了一次坑：`gh secret list` 打出的是**一张空表头**，
因为本机 `github.com:443` 经代理被断（`CONNECT … aborted`），gh 根本没查成 ——
「取数失败」被渲染成「空结果」。换 `curl` 直打 `api.github.com` 才读到真值。
这条已记进 `docs/PITFALLS.md` C 组（「`gh` 输出一张空表头 ≠「没配 secret」」）。

### 二、坑表的三组条数靠人肉维护，已经漂了

`docs/PITFALLS.md:20-24` 那张汇总表写着三组各有几条。它是**手写的三个数字**，
与 A/B/C 三张表的实际行数**没有任何机制保证相等**。本轮实测：

```text
docs/AGENTS.md           写的是 A17 / B19 / C28
docs/PITFALLS.md:22-24   写的是 A17 / B18 / C23
按「组标记之间、首格加粗的行」实测    A17 / B18 / C23
```

⇒ 同一件事在两个文件里给出**两个不同答案**，而其中至少一组**不等于实测**。
这与 A 组「一个事实只应有一个权威陈述处；其余处必须是指针，不能是副本」是同一个病：
**副本存在就会漂移** —— 不是「这次有人忘了更新」，而是「下一次也会」。

## Decision

### 一、凭据为空从「静默降级」改成「预检失败」，并留一个显式豁免口

新增 `tools/check_required_secrets.sh` —— **本地与 CI 跑同一份**：对 `REQUIRED` 名单里
每个变量名检查其**值**，把缺的一次报全后 `exit 1`。判据两条（写在脚本头部注释里，那里是唯一权威）：

```text
① 值去掉所有空白后为空        ⇒ 缺（「空串 / 纯空格 / 变量不存在」三种同形）
② 值里含未展开的 ${{ 记号     ⇒ 缺（workflow 把表达式字面量当值传了出来）
```

★ ②比①阴：那种值**非空**、看上去像配好了，实际编进二进制的是 `${{ secrets.X }}` 这串字符。
判据只写「非空」会放行它。

豁免只有一条路径：**仓库变量** `ALLOW_EMPTY_CREDENTIALS`（取 `true` / `1` / `yes` / `on`，
大小写与空白不敏感）⇒ 打 `::warning::` 并 `exit 0`。
★ 关键是它**不静默**：「这批包确实不带凭证」是一个需要留痕的决定，warning 就是那条留痕。

四条设计要点，每条都在防「豁免变成默认」：

```text
① 默认是红，不是绿 —— 缺凭据 = 这次构建产出的东西不该发出去
② 豁免必须由**仓库变量**显式打开，而不是「检测到 fork PR 就自动放过」
   ⇒ 「我知道这个包不带凭证」由人声明，机器不替人猜
③ 失败信息必须说清是哪几个变量、以及怎么合法豁免
   ⇒ 否则下一个人只会把这一步从 workflow 里删掉（门禁被删掉的唯一原因就是它读不懂）
④ 只打**变量名**，不打值、不打长度、不打前几位、不打哈希 ——
   日志是公开的（fork PR 的日志尤其），任何由值派生的量都是在往外漏
```

### 一·补（2026-10-21 Lead 复核）：预检的**生效范围**只到「会发版」为止

```yaml
# windows job :150 / macos job :932
if: github.event_name == 'workflow_dispatch' && inputs.release_tag != ''
```

★ 这一条是**放宽**，必须写清它凭什么不算假绿：

```text
要防的事：装到用户机器上的包内嵌空凭据（用户以为这是官方包，其实弹幕不可用）。
不防的事：一个跑在 PR 上的、谁也不会去装的构建产物。

而本仓现在的实际状态是 secrets 总数 = 0。若预检无条件跑：
  ⇒ 每一个 PR / push 的 Windows job 都会红
  ⇒ 分支保护要求的 Windows 检查**永远绿不了**
  ⇒ 结果是「必须配凭据才能发版」变成「必须配凭据才能合任何代码」
前者是我们要的摩擦，后者是把门禁变成路障 —— 路障的下场是被删掉。

所以判据挂在「会不会发布」（release_tag 非空，或 tag push），不挂在「会不会编译」。
真正产出的发布包（zip / NSIS / DMG）本来就只在 release_tag 非空时才打
（build.yml:684 / :712 / :1042 / :1078），两者范围一致。
```

★ 同时把预检**补进了 macOS job**（原先只有 Windows）：凭证是两个平台**各自**
`--dart-define` 编进二进制的（windows :549-557 / macOS :961-966），
只查 Windows 等于放过一半的发布包。两个 job 调的是同一份脚本。


★ 脚本用 `set -uo pipefail` 而**不用 `set -e`**：要把所有缺的变量一次报全，
而不是撞到第一个就退 —— 修的人只需要来回一轮。

★ 豁免为什么不用 `if: secrets.X != ''`：`secrets` 上下文**不能**出现在 `if:` 里
（GitHub 只允许它出现在 `env:` / `with:` / `run:` 这类注入点）；而在 shell 里判「有没有配」，
本来就只能判**值** —— Actions 不提供「列出 secret 名」的能力（那需要 PAT）。
⇒ 「判值 + 显式豁免开关」是不需要额外凭据的唯一落地方式（见下方被否决的方案 A）。

★ 为什么不在 Dart 侧判：`String.fromEnvironment` 拿到的也是一个空串，
**「凭证没配」与「用户真的没填」在运行期同形**。判据必须落在**构建期** ——
只有那里知道「这一次构建的输入本该有凭证」。

### 二、坑表条数从人肉维护改成脚本门禁

新增 `tools/count_pitfalls.py`，口径写在它自己的 docstring 里（**唯一权威，别处不许再解释一遍**）：

```text
范围 = 两个显式标记（<!-- X组开始 --> … <!-- X组结束 -->）之间的块
条目 = 块内**首格加粗**的表格行，即 | **标题** | … |
剔除 = 标记 / 空行 / 分隔行（|---|）/ 非表格行 / 首格不加粗的表格行
```

★ 判据为什么是「首格加粗」而不是「任何 `|` 行」：
C 组块首那张「症状 → 怎么办」速查表（`docs/PITFALLS.md:84-89`，6 行）**首格不加粗**。
按「任何表格行」数，C 组会被数成 **28** —— 而 `docs/AGENTS.md` 里那个错数正好是 **C28**。
⇒ 推断（未取证，只作为线索）：那个数字当初很可能是「数了所有表格行」得到的。
**这正是「人肉维护的口径」的第二个失真源：不只是数字过期，是连数什么都在人脑子里。**

退出码分三档，第三档是关键：

```text
0  一致
1  不一致（文档里的数 != 实测数）
2  查不到（文件缺失 / 标记缺失 / 汇总表缺失）
⇒ ★ 2 不能退化成 0。「我没查到」不是「没问题」—— 这是 A 组那条硬判据在脚本上的落点。
```

`--check` 默认只打印，`--write` 把实测值写回文档。
写回时先 `rpartition("|")` 切掉最后一格再拼 —— 否则会写出「见下 17」这种多一格的行。

★ 脚本第一件事是 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`：
它的成功回执里带 `⇒`（U+21C4）和 `✅`（U+2705），在本机 GBK 控制台上会在
**成功路径上**抛 `UnicodeEncodeError`。这条不是新知识，
是 [门禁在自己的成功消息上崩掉](../bug-fix/2026-10-21-gate-crashes-on-its-own-success-message.md) 那篇的直接复用。

## Alternatives considered

**A. 在 CI 里用 REST 列 secret 名来判断「到底配了几个」（`GET /repos/{o}/{r}/actions/secrets`）。**
最强理由：这是**事实核查**，比「环境变量是不是空」强 —— 它区分得开
「没配 secret」与「配了但 review 环境里读不到」，而且不需要把凭证值透传给任何脚本
（本机实测过：`curl` 直打该端点能拿到 `total_count`）。
否决理由：**Actions 里的 `GITHUB_TOKEN` 没有读 secrets 的权限**，要读就得另配一个
具 `secrets: read` 权限的 PAT。⇒ 等于**为了保护一个凭据，先给门禁自己加一个新的凭据依赖**，
而且那个 PAT 一旦过期，门禁与发布**同时**静默失效 —— 用一个更脆的东西去守一个脆的东西。

**B. 把「A/B/C 分别是几」直接硬编码成门禁的期望值。**
最强理由：零依赖、纯文本比对，连 Python 都不用装，一条 `grep` 就能写出来。
否决理由：**加一条就红**。新增条目时两边都得改，而改的人只会看到「门禁红了」，
第一反应是改数字 —— 于是门禁从「校验一致性」退化成「提醒你再抄一遍」，
最终被习惯性忽略。且它校验的仍是**两份人写的数字是否相等**，
而不是**文档与实测是否一致**（两边一起写错它照样绿）。

**C. 让人 `--write` 之前先跑一次、CI 只跑 `--write`（自动修复，永不红）。**
最强理由：CI 永不因为「忘了刷数字」而红，红只留给代码问题 —— 摩擦最小。
否决理由：**它会悄悄改写仓库文件而 CI 仍然是绿的**，于是「文档里的数与实测一致」
这条不再由任何人负责：没人会去读那次自动提交的 diff。⇒ 报错是可审计的，自动修复不是。

## Consequences

- **收益**：两处「不一致」都变成**有名字的失败**。缺凭据时 CI 红在那一步并报出变量名；
  条数漂移时本地 `python tools/count_pitfalls.py` 立刻退出 1 并打印每组的剔除明细。
- **代价**：发布路径多一步；每次改坑表要再跑一次脚本（这正是它存在的理由）。
- **生效范围（2026-10-21 Lead 复核后收窄过一次，务必按现在的样子理解）**：
  预检挂在 `if: ... inputs.release_tag != ''` 上 ⇒ **非发版构建根本不跑它**。
  所以「fork PR 会不会被预检拦住」这个问题已经不存在了 —— fork PR 不跑这一步。
  代价换来的收益是：分支保护的 Windows 检查不会因为「仓库里没配凭据」而永久红
  （那会让「必须配凭据才能发版」退化成「必须配凭据才能合代码」）。
  要留意的反面风险：**非发版构建里凭证是否为空，现在无人检查**；
  若将来有人把 CI 的 zip 直接拿去发，这个缺口就真的会漏 —— 那时应恢复无条件检查。
- **`ALLOW_EMPTY_CREDENTIALS` 的边界**：它只表示「**这一次构建**允许不带凭证」，
  **不表示**「这个包可以发布」。发版仍要有人确认凭证就位；脚本不替人做这个判断。
  它也不许被当成「promote 前的后备开关」：开一次就是一次 warning 留痕。
- **已接线（同一批改动内完成，不再是上限）**：
  ```text
  · tools/check_required_secrets.sh 已接进 build.yml 的 **windows 与 macos 两个 job**
    （windows :150 / macos :932，各自 `if: inputs.release_tag != ''`）。
  · tools/count_pitfalls.py 已接进 windows job（:305 附近，`python … --check`），
    紧跟在「发布说明守卫」后面 —— 两个都是「文档里的数会烂」的守卫，放一起。
  · docs/AGENTS.md 的 A17/B19/C28 已收口：AGENTS 那张表删掉了「条数」列
    （只留「何时读哪组」），条数与「什么时候看」只住在 docs/PITFALLS.md 一处，
    实测 A=17 / B=18 / C=24。
  ```
- **已知上限**：
  ```text
  · 口径依赖「首格加粗」这一约定 —— 将来若有人给 C 组速查表也加粗，C 的计数会跳 6。
    改口径时必须同步改 docs/PITFALLS.md 顶部汇总表那三格，否则又制造一份新副本。
  · 预检判的是「环境变量此刻是否为空」，不是「凭证是否有效」——
    配了一个错的值它照样放行。验有效性要有一次真的网络调用，
    那是发版验收的事，不是 CI 预检的事。
  ```
- **何时翻案**：
  ```text
  · 若 GitHub 给 GITHUB_TOKEN 加上读 secrets 元数据的权限（方案 A 的否决理由消失），
    预检就该改成「查事实」而不是「查环境变量」。
  · 若坑表改由工具生成（条目从 note / 台账派生），汇总表就不该再手写条数：
    那时应删掉汇总表里的三格数字，让脚本成为唯一输出处。
  ```

### 给下一个人的一句话

```text
「结果为空」与「取数失败」在终端上完全同形。
凡是要据「空」下结论，先换一条独立路径把同一个事实再读一遍。
```
