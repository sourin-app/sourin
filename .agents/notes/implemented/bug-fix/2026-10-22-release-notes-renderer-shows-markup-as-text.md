# Agent Note: 更新说明的渲染器把「非内容标记」当正文显示

Status: implemented

- 日期：2026-10-22
- 适用：`lib/ui/widgets/release_notes.dart`、`test/zz_t1023_release_notes_renderer_skips_non_content_test.dart`

接在 [./2026-10-21-release-notes-no-tables.md](./2026-10-21-release-notes-no-tables.md) 之后：
那一篇定的是「内容别写渲染器不支持的东西」（表格改列表），
本篇定的是「**万一还是写了，别原样显示给用户**」。
两篇是同一条链的两端：源头拦、末端也兜。都保留，不归档。

## Problem

`buildReleaseNotes(String md, {Color? linkColor})` 按行分类，只认三类：

```text
'#' 开头          → 标题
'- ' / '* ' 开头  → 列表项
其余非空行        → 正文段落（原样拼进去）
```

这个「其余一律当正文」的兜底，把 Markdown 的**非内容标记**也变成了可见文本：

```text
<!-- 维护者注释 -->       → 用户看到 "<!-- 维护者注释 -->"
---                      → 用户看到 "---"
***  / ___               → 同上
```

2026-10-22 的 rc3 更新说明里就有一整段 26 行的维护者注释
（`.github/release-notes.md` 第 12–37 行那段「占位标记别写第二份」的提醒），
它被当成正文渲染 —— 用户在更新弹窗里能读到维护者写给下一个人的内部说明。
这不是排版问题：那是**读者不该看到的内容**。
（取证：`gh release view v1.4.0-rc3 --json body` 读回的服务端正文里，
`<!--` 到 `-->` 原样存在，说明它确实进了已发布的 Release body。）

为什么现在才发现：`docs/release-notes/` 的人工稿通道才刚建（见
[../process/2026-10-22-release-notes-manual-override.md](../process/2026-10-22-release-notes-manual-override.md)），
而这条通道的校验只拦「稿子里写的坏东西」；**自动路径产出的说明**
从来没有被这条校验管过 —— 而泄漏恰好发生在自动路径上（注释在模板里，
生成器只替换占位符、不动模板其余部分）。
唯一一处「注释不该显示」的说法，原本只写在另一条门禁的注释里
（`test/zz_t66_release_notes_syntax_gate_test.dart`），是**注释不是判据** ——
没人执行它，所以它一直是假的。

## Decision

按字节形态**跳过**非内容行，不改渲染器的其余行为：

```text
① 跨行 `<!-- … -->`：整段跳过（同一条能跨行，靠一个 `inComment` 状态位）
② 同一行内开闭的 `<!-- x -->`：跳过
③ 注释未闭合：从 `<!--` 起全部跳过，且**后面没有真内容可吞**（不崩）
④ `---` / `***` / `___`（分隔线）：跳过
```

四条都在「分类之前」判断，且不影响标题/列表/正文的既有分支 ——
**阳性对照用例**钉住「注释修好之后，标题/列表/段落照样渲染」。

## Alternatives considered

**① 让渲染器支持更多语法（真解析 Markdown）。**
最强的理由：一次性解决所有「未知语法被当正文」的形态，不用一种一种补。
否掉的原因：本仓库零第三方 Markdown 依赖（`pubspec.yaml` 里没有
`flutter_markdown` / `markdown`），自己写解析器意味着长期维护一套语法实现；
而更新说明的**内容面本来就窄**（四类小标题 + 条目），补四个形态就够用。
真需要富文本时应当换一个成熟解析器，而不是在这条窄路径上继续加分支。

**② 只在「源头」拦：把 `<!--`、`---` 加进生成器的校验，渲染器不动。**
最强的理由：源头拦住了，末端就不用兜，逻辑只有一份。
否掉的原因：源头管不到**已经发出去的 release 正文**（`gh release view v1.4.0-rc3`
读回的服务端 body 里，那段 26 行注释原样在里面 —— 已发布的正文改不了，
只有渲染器跳过，老版本用户才不用再看到）；也管不到自动路径在宽松模式下产出的内容；
而且这条通道之外还有别的地方给 `buildReleaseNotes` 喂字符串（测试与未来的入口）。
末端兜一层是防御纵深，代价只是四个判断。

**③ 把 `<!--` 当正文但**转义**显示。**
否掉的原因：用户不需要知道那里有注释，显示 `&lt;!--` 更糟；
而且注释里的内容本来就是给维护者看的，转义后依然是泄漏。

## Consequences

收益：

- 维护者注释、分隔线不再出现在用户眼前；rc3 那种 26 行交接说明的形态被堵死。
- 渲染器对**坏输入**（注释未闭合）不崩、也不吞掉后面的真内容。
- 补上了一条本来只写在注释里的判据 —— 那条「注释不该显示」的说法现在有执行体了。
代价：

- 渲染器里多了四个形态判断，且**跳过的是字节序列而不是语法**：
  正文里若真要显示 `---`（极少），现在会被静默丢弃。这是刻意的取舍：
  在更新说明这条窄路径上，「别泄漏」优先于「别丢字」。
- 这是末端兜底，源头那层仍要继续拦（人工稿校验已拦 `---` 与 HTML 注释）
  ⇒ 同一类问题有两处判据。**接受**：两处的输入集合不同（一处是稿子，
  一处是所有调用方），不是同一份真相的副本。
- 没有做成通用 Markdown 支持 ⇒ 未来再遇到「又一种未知语法」还会漏一次。
  下一次的正确做法是换解析器，不是再加第五个判断。
