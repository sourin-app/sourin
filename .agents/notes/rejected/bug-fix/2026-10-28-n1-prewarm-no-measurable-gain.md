# Agent Note: N1 预热首段连接 —— 量过，没有收益，撤回

Status: rejected — A/B 实测两臂无差别（起播 ttfb 732ms vs 740ms，区间完全重叠），不值得为它多打一次上游请求

## Problem

N1（目标站播放卡）的取流侧读数显示：**首次** `range=bytes=0-` 的 ttfb 明显高于后续 range

```text
首次 range ttfb ：894 / 1352 / 1688 / 2858 ms（4 个不同时刻）
后续 range ttfb ：192~624 ms（同一会话内）
⇒ 差额看起来就是"建连 + TLS 握手"，而这段握手理论上可以**提前做掉**。
```

于是提出：在 streamproxy **登记流**的那一刻（已经知道上游 URL、播放器还没来要数据）
异步发一个 `Range: bytes=0-0` 的 1 字节 GET，把 TCP+TLS 放进共享连接池，
让 mpv 的第一段直接复用 —— 握手成本就藏进了"播放器正在启动"的那几百毫秒里。

## Proposal

```text
① `maybe_proxy()` 里 `登记流` 日之后 spawn 一次预热；
② 预热复用 `proxy.client`（同一个连接池），超时 2s（比首段更早放弃）；
③ 失败只记日志，绝不改动返回给播放器的本地地址；
④ 门禁：本地 axum 起服务，按**对端端口**去重计数，断言
   「预热与首段走**同一条 TCP**」+「恰好一条 Range: bytes=0-0」+「非 http(s) 不预热」。
   （只断言"发了个请求"没有意义 —— 若两条各开各的连接，既没省握手还多打一次上游。）
```

实现完成、门禁写成、注入两向都真红（不预热 ⇒ 断言红；预热用独立 Client ⇒ "同一条 TCP"红），
还原后 md5 一致、复跑全绿。

## Why rejected

在**同一小时内、同一台机、同一个探针**上做 A/B（不含预热 / 含预热各 3 轮）：

```text
A（关预热）起播 ttfb：740 / 646 / 1033 ms   median 740
B（开预热）起播 ttfb：657 / 748 / 732 ms    median 732
预热自身耗时        ：668 / 739 / 837 ms
⇒ 两臂**无差别**（差值 8ms，远小于轮间波动 ±190ms）。
```

判读：**上游首字节不是握手成本，是服务端思考时间**（CDN 冷启/回源）。
预热那 700ms 也在等同一件事 —— 它只是把等待挪了个地方，没有把它变短。
⇒ 结论：这条修法**不解决任何用户可感知的延迟**，却让每次起播多打一次上游请求
（对站点是多出来的流量与频次），按"净收益为负"处理。

★ 顺带推翻一个更重要的旧读数：那 4 个"首次 ttfb 894~2858ms"**本身是高方差样本**。
同一小时内关掉预热的 A 臂只有 646~1033ms ⇒ 原先"首次比后续慢一个量级"的部分，
有相当一块是**采样时段的网络波动**，不是稳定的握手税。

## Alternatives considered

1. **合并同一 URL 的重复分段请求 / 缓存已完成区间**。
   最强理由：Owner 的日志里 `range=798084184-` 出现过两次，说明确实有重复取。
   **否决（有读数支撑）** —— 2026-10-28 复查 6 轮真机读数（`n1-probe-stdout-run{1,3,4}.log`
   与 `n1-after-stdout-{1,2,3}.log`），把每轮的 `range=bytes=<偏移>-` 去重后：
   **每一轮里每个偏移都恰好出现 1 次，没有任何重复取**。
   ```text
   run1 : 798084184 / 162942930 / 1028413 / 0            （各 1 次）
   run3 : 798084184 / 162942930 / 1028413 / 0            （各 1 次）
   run4 : 798084184 / 176953018 / 162942930 / 1028413 / 0（各 1 次）
   后三轮（带预热）: 同上 + 1~2 个 seek 目标偏移，同样各 1 次
   ⇒ 同一个偏移只在**跨会话/跨 seek** 时重复出现（那是两次独立的新请求，不是重复取），
     在**一次播放会话内**没有可合并的对象。
   ```
   ⇒ 这条修法没有可优化对象；Owner 日志里那两个 `798084184-` 是两次独立起播/seek 各取一次。
2. **seek 目标附近预取**。
   **否决** —— seek 是用户随机动作，预取只能覆盖"他知道要 seek 到哪里"的情形；
   实测 seek 那一段 ttfb 621~2410ms，与起播同一量级，同样是服务端首字节。
3. **从渲染侧下手（raster 优化）**。
   **否决** —— 同批读数已证：播放页 raster 超预算只 0.14%~0.22%（5343 帧），不是主因；
   且旧13 结论（不动模糊）仍有效。

## Consequences

- 收益：省掉一条"看上去很对但没有收益"的改动，以及它带来的每次起播一次额外上游请求；
  同时把"首次 ttfb 高"这个读数**降级为高方差样本**，避免后来人据此继续优化握手。
- 代价：N1 在客户端侧**目前没有已验证有效的修法** —— 这一项以"实测判不做"收口，
  而不是"修好了"。剩余可做的只有上面备选 1（重复分段），需要单独立项 + 自己的判据。
- 验证方式（可复跑）：`.probe/n1-prewarm-ab.sh`（A/B 各 3 轮，含 md5 还原核验）、
  `.probe/n1-prewarm-inject.log`（门禁两向注入）、`.probe/n1-weights-readout.md`（两半读数）。
