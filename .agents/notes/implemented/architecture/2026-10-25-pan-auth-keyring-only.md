# Agent Note: 网盘登录凭据走系统钥匙串，cookie 绝不落盘

Status: implemented

与既有决定的关系（部分重叠）：本模块复刻 `proxy.rs` 里代理密码的存储纪律 ——
敏感值进系统钥匙串，数据目录只留非敏感元数据。那条纪律由既有代码确立，
本模块只是把它用在网盘 cookie 上，两处互不影响（服务名不同）。

与登录态同步那边的关系是**边界互补、不重叠**：
[登录态单向同步](../feature/2026-10-19-login-state-sync-one-way.md) 讨论的是
"把哪些登录态写到云端/备份"（`*credential*` 的 gitignore 规则就来自那条线），
本模块讨论的是"网盘 cookie 在本机怎么存"。两者共同遵守一条底线：
**凭据不进任何会被复制的地方** —— 那边不进备份，这边不进数据目录。

## Problem

Owner 要求"网盘账号登录解锁源"。完整链路需要真账号，而测试账号尚未提供。

但这条链路上有**一块不依赖账号、又能把安全做扎实**的部分：
**cookie 的存 / 取 / 清 / 过期判定**。而且它是后面每一跳的前提 ——
凭据存不住，登录做了也白做。

同时有一个必须现在就定死的约束：**cookie 不能写进数据目录**。
理由不是洁癖：数据目录会被**备份、云同步、用户手动拷贝**，
本仓 `DATA-DIR.md` 已经点过 `sync-settings.json` 含凭据的风险。
cookie 一旦落盘就跟着到处跑，而用户完全不知道。

## Decision

新增 `src/pan_auth.rs`，四件事：

1. **cookie 只进系统钥匙串**，键名 `pan/<kind.code()>`，
   服务名 `dsh-media-client-pan`（与代理的 `dsh-media-client-proxy` 并列互不干扰）。
   实现区**没有任何文件操作**。
2. **一个盘一份凭据**。同一账号重复登录 = 覆盖；空 cookie = 登出（清掉旧值）。
   不做多账号 —— 本仓没有"切换网盘账号"的用例，加多账号是无用例的机制。
3. **`expires_at = None` 视为未过期**。网盘会话 cookie 大多没有明确有效期，
   只能"用起来失效了再说"。反过来（None 当过期）会让用户每次启动都要重登。
4. **`keyring_available()` 探测**：某些精简 Linux 没有 secret-service，
   那种环境下 UI 不该假装登录可用。

序列化用 `\u{1f}` 拼接而非 JSON：少一次依赖，也不会因为 JSON 转义
让 cookie 里的引号出问题。字段固定 5 个，顺序可接受。

## Alternatives considered

### A. cookie 存进数据目录（明文或简单编码）
**最强理由**：实现最简单，跨平台一致，不依赖系统组件。
**否掉的原因**：会跟着备份/云同步到处跑。用户不会知道自己的网盘会话
被复制到了哪台机器上。而且本仓已经有相反的先例（代理密码走钥匙串），
两种做法并存会让后来者不知道该跟哪个。

### B. 复用 `sync/credentials.rs` 的口令加密（AES + 用户口令）
**最强理由**：仓里已有成熟实现，加密强度高。
**否掉的原因**：那套需要**用户每次输入口令**（它是为云同步备份设计的）。
网盘登录态是"登录一次长期有效"的语义，每次启动都要输口令不可接受。
若为它单独存一个派生密钥，那密钥又该存哪儿 —— 回到同一个问题。

### C. 支持多账号（每个盘可存多份，UI 可切换）
**最强理由**：重度用户可能同时有两个账号。
**否掉的原因**：本仓没有任何"切换网盘账号"的界面与路由设计，
现在加多账号等于先造一套没有入口的机制。真出现需求时再加，
届时键名改成 `pan/<kind>/<accountId>` 即可（向后兼容旧键）。

### D. `None` 过期当作"已过期"，强制刷新
**最强理由**：更保守，避免用过期的 cookie 发请求。
**否掉的原因**：实测网盘会话大多数不给有效期，那等于**每次启动都要求重登**。
正确做法是"用起来失败再提示重登"，而不是预先假定过期。

## Consequences

**收益**
- 登录功能的**安全底座**现在是对的：cookie 不落盘，且有源码门禁钉死。
- 存取/覆盖/登出/过期判定全部可离线验证，不依赖账号。
- `keyring_available()` 让 UI 能如实反映"这个环境能不能存凭据"。

**代价与边界**
- **登录本身没做**。调网盘 API 换 token、取文件列表、换直链**全部未实现**，
  需要真账号才能验证。
- 依赖 `keyring` 后端；Linux 上若无 secret-service，功能不可用（已用探测暴露，
  不静默降级）。
- 单账号限制已记录；将来若要多账号，键名需扩展且要处理旧键迁移。
- `\u{1f}` 编码是私有格式，**不是跨版本契约** —— 若将来字段变化，
  需要能识别旧格式并丢弃（当前 `decode` 字段数不符即返回 None，安全）。

## 验证结果（已发生）

- `cargo test --lib pan_auth --release` → **9 passed**
  纯逻辑 5 条（编码往返含 cookie 里带 `=`/`;`/`"`、垃圾输入拒绝、
  None 不算过期、边界含等号、各盘键唯一）+ 钥匙串 3 条
  （真实存→读→覆盖→清除、空 cookie 等于登出、跨盘不串）+ 源码门禁 1 条。
  **本机钥匙串可用，3 条真跑了**（无 SKIP 输出）。
- **故障注入两次**：
  1. `encode` 里把 cookie 丢掉 ⇒ 4 条测试 FAILED（含真实钥匙串往返）。
  2. 实现区偷偷加 `std::fs::write` ⇒ `impl_never_touches_filesystem`
     **FAILED**，报「cookie 绝不许落盘，但实现区出现了 `std::fs::`」。
  恢复后 9 passed。

## 何时该翻案

拿到测试账号后，应在 `pan_auth` 之上补"调 API 换 token"这一跳，
并把 `expires_at` 真正填上（而不是恒 None）。
若某网盘的会话不再支持 cookie（改 token 体系），应扩展 `PanCredential`
而不是另起一套存储。
