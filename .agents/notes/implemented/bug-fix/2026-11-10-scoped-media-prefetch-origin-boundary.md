# Agent Note: Scoped media keeps its origin boundary when prefetch is enabled

Status: implemented

Applies: 2026-11-10, media requests carrying an internal scoped HLS policy.

## Problem

The initial media request uses a scoped client that rejects undeclared redirect
origins. Optional generic Range prefetch creates secondary requests through a
client source that reselects the current global media route. That reselection
does not retain the additional scoped redirect restriction. A large non-TS media
object can therefore disclose an issued query or registered request context to
a foreign redirect during secondary Range reads, although the initial request
was correctly guarded.

Prefetch is off by default and ordinary HLS TS resources are excluded from it.
The missing guard is reachable when prefetch is enabled and scoped media has
the large Range-capable response shape. It is separate from the already
verified TS playback path.

This partially overlaps the [declared HLS query contract](2026-11-10-declared-hls-query-inheritance.md)
and [per-instance prefetch switch](2026-10-08-prefetch-switch-per-instance.md).
Those decisions remain; this decision limits the optimizer's eligible requests.
The note audit found no proposed or rejected decision superseded by this
source-origin boundary.

## Decision

The prefetch planning guard disables generic Range fan-out whenever the current
request carries a scoped HLS policy. That media stays on the already-opened
guarded upstream connection and streams its bytes normally. Parallel windows
and their serial Range fallback cannot create an unscoped secondary path.

Unscoped media retains optional generic prefetch. Source opt-in, source disable
configuration, global Direct/System/Custom and ApiOnly/All routing, headers,
issued query spelling, Range response delivery and subscription/source address
fallback remain governed by their existing boundaries. This change does not
select a new route, origin, identity or media candidate.

## Alternatives considered

- Pin the initial scoped client in the prefetch worker: would ignore global
  proxy policy revisions that existing secondary requests deliberately reselect.
- Carry the scoped policy through every prefetch constructor, parallel request
  and serial fallback: can preserve the optimization, but adds state and paths
  without evidence that scoped large non-TS media needs parallel throughput.
- Disable all prefetch: removes an existing optimization from unrelated sources
  without addressing a requirement in those paths.
- Check origin after a redirect response completes: a foreign request may
  already have disclosed the issued query or registered context.

## Consequences

The regression goes through the real wrapper and HTTP request path. A local
origin returns a valid large open-ended Range response; only finite Range
requests generated by prefetch redirect to another loopback origin. Byte
delivery remains valid in both cases, so the scoped failure identifies the
actual foreign-request ledger rather than a download or decoding error. Its
unscoped control requires multiple finite Range requests and preserves ordinary
redirect behavior. Both use instance state without environment mutation or
accounts.

The coordinating tests-first baseline compiles and yields one scoped
foreign-request failure and one passing unscoped control. The regression source
remains byte-identical while the production eligibility guard changes. The
corrected regressions pass both cases, and the affected stream-forwarding suite
passes 78 cases with one pre-existing ignored case. Source hashes remain unchanged
during each Cargo run.

Scoped large non-TS media uses single-connection throughput when prefetch is
enabled. Current TS media already uses that path. If future measured product
requirements need scoped parallel fetch, carry the complete scope through all
secondary requests and re-establish origin, route-revision and byte-integrity
regressions. These local request tests do not establish remote-source
availability, decoder behavior or UI/package acceptance.
