# Agent Note: Fresh selected-source media and bounded decoder verification

Status: implemented

Related: [Bound local decoder PCM verification](2026-11-16-local-decoder-pcm-verification.md)
and [source routing preserves engine recipes](../architecture/2026-11-09-csp-global-routing-retains-engine-recipes.md).
The local-file amplitude decision remains applicable. This note additionally
binds fresh source detail, exact selection and original core forwarding.

## Problem

Catalog or resolve success does not establish current decoded media. An
offline sample does not bind a fresh selected episode. Native dimensions also
coexist with empty files when the packaged image encoder cannot open.

## Decision

Keep provider, native identity, line, episode title, order and opaque recipe
from accepted catalog and fresh detail. Resolve the exact request with the
original packaged core C ABI, preserving headers, permission checks, query
spelling and configured proxy. Review actual anonymous media authorities and
cloud boundaries; freeze public DNS and retain every request outcome. No
guessed identity, parser, header, account or transfer path is substituted.

Read real core-forwarded HLS and verify every child stays on the core loopback
listener. Run independent three-second file-PCM muted/nonzero controls with
packaged libmpv. Independently parse WAV samples and rehash loaded libraries.
Require normal destruction and eight seconds of naturally empty owned Job.

For offscreen video, use the qualified typed `screenshot-raw` C API with
`vo=null`, no audio, scripts or window. Copy native pixels before freeing the
node. Retain four raw frames and PNGs with advancing native timestamps,
contrast and independently recomputed changed color pixels. Keep PlayerPage
presentation and device output acceptance separate.

## Alternatives considered

- Catalog, resolve, duration and codec fields do not measure pixels or amplitude.
- Default audio output can emit device audio or include unrelated sessions.
- Packaged `vo=image` cannot open its PNG encoder; zero-byte outputs stay rejected.
- Increasing the product response-header timeout changes the path being observed.

## Consequences

The direct no-parser family forwards a 193-byte master HLS and outputs two
264598-sample PCM controls: muted nonzero count zero, positive count 256488.
Four altered controls fail. The encrypted episode family forwards 150415
bytes with 394 rewritten children and outputs three seconds of PCM: muted
count zero, positive count 120615. Five altered controls fail. The guest-handshake
family forwards a 200-byte master and 143476-byte variant with 863 rewritten
children; its three-second PCM controls yield muted count zero and positive
count 264499. Five altered controls fail. All three retain the unchanged
core/libmpv, exit zero and naturally drain for at least eight seconds. The
guest-handshake candidate's returned `mp4` kind remains recorded while its
actual HLS bytes are decoded; no metadata correction is inferred.

The direct family's separate video diagnostic preserves the fresh public DNS
set but orders a previously observed successful endpoint first. It removes no
addresses and changes no product timeout. Four 1920x1080 frames advance by
1.8 seconds; first/last changes are 566793 color pixels. Seven altered controls
fail, including an inflated original-DNS-order claim. Two original-order
requests retain three-second response-header timeout and HTTP502. This accepts
a short introductory sequence through the explicitly ordered diagnostic relay;
original DNS order, PlayerPage rendering and sustained film playback are unqualified.

Source-issued media query identifiers remain distinct from episode identifiers
when actual values differ. Incomplete tunnel cancellation/reset stays recorded.
Evidence is retained in
`.probe/protocol-final-20261117/DIRECT_SOURCE_CURRENT_MEDIA_PCM_AUDIT_V2.json`,
`DIRECT_SOURCE_NATIVE_RAW_VIDEO_ENDPOINT_DIAGNOSTIC_AUDIT_V1.json` there, and
`.probe/protocol-parallel-20261117/HXQ_CURRENT_CORE_HLS_PCM_AUDIT_V1.json`
and `APP99_CURRENT_CORE_HLS_PCM_AUDIT_V1.json` there. The full stage/receipt
binding is `THREE_PROTOCOL_CURRENT_PARALLEL_SUMMARY_V1.json` in that directory.
Real accounts, cloud transfers, device output and whole-delivery acceptance
remain outside these observations.
