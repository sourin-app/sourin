# Agent Note: 更新说明增加「人工确认稿」通道（自动归纳产不出可读说明时的逃生阀）

Status: implemented

本篇接在 [./2026-10-19-release-notes-generated-from-git.md](./2026-10-19-release-notes-generated-from-git.md) 之后：
那一篇确立了「更新说明从 git 历史归纳 + 缺说明时 CI 直接红」，
本篇不动那条强制点，只在它**旁边**加一条人工通道 ——
当自动归纳**结构性地**产不出用户能读懂的说明时，人可以写一份稿子顶上。

## Problem

v1.4.0-rc4 发版前实测：`python tools/gen_release_notes.py --from v1.4.0-rc3 --to HEAD`
以退出码 1 结束，报「归纳结果为空（v1.4.0-rc3..HEAD，16 条提交）」。

逐条诊断（实测，不是推测）——区间里 16 条提交中 7 条是**真修复**，
用户全都感知得到，但自动归纳**一条都产不出来**：

```text
① 健康检测进度走独立 notifier，二级页才真的看得见
   → 「检测」在 _ENGINEERING_TERMS 里 ⇒ 该段被按段删空
② Material 本地化改用 material_ui 的 GlobalMaterialLocalizations
   → 残留「Material 本地化改用 的」⇒ _final_form_ok 判 False
     （Material / 本地化 不在 ASCII 白名单；中文后又黏一个「的」）
③ App 外层补 ScrollConfiguration，门禁改成判「真挂载」
   → 「门禁」整段删 + ScrollConfiguration 是未知 ASCII 词
④ raw-deflate 回退只在真解压失败时重发，且回退不丢代理与 UA
   → **唯一自动活下来的**（补了「代理」到 _USER_SURFACE 之后）
⑤ 过期条目的时间戳从不刷新 —— 新鲜度保护改成按 TTL
   → 仍空
⑥ 让路窗口的定时器回调接住 async 异常
   → 残留但 _final_form_ok 判 False
```

根因不是「词表漏了几个词」，而是**三个结构性问题**：

```text
① 清洗层与用户面词典**互相拆台**：「健康检测」是界面上的正式叫法，
   而「检测」在工程语境里是门禁词 ⇒ 按段删的机制把它连同整句删掉。
② 「正文只许有用户认识的 ASCII 词」这条形态闸门**不认识产品名**：
   Material / ScrollConfiguration / notifier 都不在白名单 ⇒ 整条判 False。
   白名单是**穷举**的 ⇒ 每加一个产品名就要补一次 ⇒ 永远补不完。
③ 删词后剩下的残句不通过形态闸门 ⇒ 静默丢弃（无 stderr 提示的那条路径）。
```

⇒ 自动路径对这一区间**结构性失效**。而
`build.yml` 的守卫「『本版更新』这一节里必须至少有一条 bullet」会红
⇒ **这一版根本发不出去**（不是发出去一份坏说明，是发不出去）。

## Decision

**在自动归纳旁边加一条「人工确认稿」通道，两条路都留下。**

1. **稿子落点**：`docs/release-notes/<TAG>.md`（逐版本一份）。
2. **生成器加 `--manual <file>`**（`tools/gen_release_notes.py`）：
   给了就用该文件当本版更新正文，**跳过**自动归纳；没给则**一个字不变**地走原路径。
   `--manual` 路径**不需要 `--from`**（它不是从 git log 归纳出来的）。
3. **CI 接线**（`.github/workflows/build.yml` 的 publish job）：
   `docs/release-notes/$TAG.md` 存在 ⇒ `--manual`；否则按原逻辑自动归纳。
   判定放在 `PREV` 计算之后，所以「首个 release 允许留空」那条分支的语义不变。
4. **人工稿仍然被机械校验**（`validate_manual_notes()`，与自动路径共用同一套校验口径）：
   - 至少一条 `- ` 条目（漏写 ⇒ 又变成「默认说明」，那正是 Owner 报过的形态）
   - 不许表格 / 图片 / HTML 标签 / 围栏代码块 / `---` 分隔线
     （客户端渲染器 `lib/ui/widgets/release_notes.dart` 不支持这些，会原样漏出）
   - 不许模板占位符残留（`{{…}}` / `__VERSION__`）
   - 不许开发用语（AGENTS §4 那批 + 本仓工程词表），
     唯一例外是产品界面上的正式叫法「健康检测」
   - 不许具体站名
   - 正文里的英文词只许是用户认识的那批（`_FINAL_KEEP_ASCII ∪ _MEDIA_FORMAT_TOKENS`）
   - 每条错误**带行号**（人工稿是人写的，报错必须能直接定位到那一行）
5. **门禁**（`test/zz_t1022_manual_release_notes_gate_test.dart`）：
   目录存在、每份稿能过生成器校验、文件名是版本号、
   **不合格的稿会被拒**（守卫不是恒绿）、CI 里确实接上了 `--manual`。
   门禁**不在 Dart 里复刻规则**，而是**调用生成器自己的校验函数**
   ⇒ 规则只写一份，不会出现「门禁抄了一份、两边各说一套」。

## Alternatives considered

- **A. 继续放宽清洗（把「检测」从工程词表拿掉、把 Material 等产品名加进 ASCII 白名单）。**
  最强理由：改动最小、风险最低，黑名单是纯加法，漏了一条立刻能补；
  而且自动路径保住了「人不用写」这个优势。
  否掉的理由：实测里第 ② 条的失败形态是**白名单穷举**（每来一个产品名就要补一次），
  第 ① 条的失败形态是**同一句话里的两个词互相拆台**（用户面词典与工程词表冲突）；
  这两类都要靠继续调表解决，而表是**开放集合**。调表能把这一版凑过，
  下一版出现新产品名时又得再调一次 ⇒ 只是把阻塞点推后。

- **B. 改提交信息规范，让每条提交都写成用户能读懂的话。**
  最强理由：治本 —— 提交标题就是用户可见说明的来源，
  规范一旦立住，自动路径的产出天然可读，不需要任何人工环节。
  否掉的理由：本仓的提交标题**同时**服务 CodeRabbit 评审与 git 历史检索
  （`fix(settings): …`、`test(gate): …` 这类 scope 是评审定位用的），
  要求它同时是营销文案会两头不讨好；且改规范**管不住存量提交**，
  区间里已经有 16 条历史提交。

- **C. 引入模型在发布时把提交标题改写成用户语言。**
  最强理由：这是唯一能真正「按用户视角重写」的方案，
  规则永远做不到归纳（同一功能的 6 条提交合成一句）。
  否掉的理由：那一篇笔记的「何时该翻案」里已经写明这件事的条件是
  「改成『生成草稿 + 人工确认』」，而不是把门禁换成模型 ——
  发版链路要求**离线、可复现、无密钥**，同一区间两次跑出的说明必须相同。

- **D. 每次发版让人手写更新说明（不加任何自动路径）。**
  最强理由：手写能写清「用户能感知到什么」，这是本篇选人工稿的直接动机。
  否掉的理由：**这正是 2026-10-19 那一轮失败的原因** ——
  流程里没有强制点，靠自觉的步骤在连续 4 个版本里一次都没被执行。
  本篇保留自动路径作为默认，只在它失效时**显式**走人工稿
  ⇒ 有人**必须**在某处按下「这一版用人工稿」这个动作，而那个动作留下了文件。

- **E. 走 `--allow-empty`，发一版「本版无用户可见变更」。**
  最强理由：一条命令的事，不改任何代码。
  否掉的理由：那正是 Owner 抱怨的形态换了个说法
  （那一篇里两个守卫「都不可达」的分析就是为此写的）。

## Consequences

- **收益**：
  - 自动归纳失效时**有路可走**，且人工稿的合格性由**机械判定**保证
    （条目 / 表格 / 开发用语 / 占位符 / 站名 / 英文词六道检查）。
  - 默认路径**一个字没改**：没有人工稿的版本仍走自动归纳，
    「说明为空 ⇒ CI 红」那条强制点仍然有效。
  - 规则只有一份（生成器里的 `validate_manual_notes`），
    门禁调用它而不是复刻它 ⇒ 不会两边漂移。
- **代价与已知上限**：
  - 人工稿**要人写**，且写得对不对**机器只管形式不管语义** ——
    一条读得通但没说清用户影响的句子会顺利通过。
  - 人工稿的分类小标题只认四个（新增 / 改进 / 修复 / 调整），与自动路径的 order 一致；
    分类小标题里的「修复」不算开发用语（那是分类名，不是黑话）。
  - 人工稿里若要写「健康检测」以外的界面正式叫法，需要往
    `_MANUAL_ALLOWED_TERMS` 里加 —— 这是**有意的例外表**，不是漏洞。
  - 人工稿按 tag 命名 ⇒ **同一版重跑**（`gh workflow run` 同一个 tag）
    读到的是同一份稿，改稿需要重新提交。
- **何时该重访**：
  - 若自动归纳的清洗层被重写（产品名不再靠穷举白名单），
    人工稿的 ASCII 词检查应跟着收敛。
  - 若 Owner 认为人工稿的语义质量不够（机器管形式管不了内容），
    下一步是「人工稿 + 逐条对照本区间的真实改动清单」的双人复核，
    而不是放宽校验。
